# 第 1 章　设计目标与首版边界

## 1.1 设计目标

本方案面向需要多阶段交付、跨职责协作和持续质量检查的长程任务，在 Pi Agent 之上构建由组织流程控制的多智能体执行体系。重点解决任务要求在多次交接中失真、执行职责与批准职责混杂、问题到最终交付才集中暴露，以及流程推进依赖 Agent 自觉维护等风险。其基本思路是先明确职责、交付和评审关系，再让专业 Agent 在限定范围内完成工作。[^1]

系统应将一次用户请求转化为可校验、可执行、可追溯的工作流：工作有明确的负责人和输入输出，交付有对应的证据和准出标准，返工能够回到原执行者，外部能够查询真实的运行状态。设计目标不是增加 Agent 数量或管理层级，而是建立稳定的协作闭环。

首版从两个维度验证效果：一是最终产物是否满足用户要求，二是流程约束、独立评审、并行协作、上下文交接和会话连续性是否有效。质量与效率收益需要通过实际运行及单 Pi Agent 对照验证，不作为架构成立后自然获得的结果。

## 1.2 IPD 在系统中的定位

本方案将 IPD 体现为**可选择、可版本化的流程治理规范**，借鉴其组织分工、结构化交付和阶段评审思想，不完整复刻企业产品经营管理体系。规范既约束节点内部如何工作，也约束节点之间如何组织、交接和评审，不能等同于一套节点字段或一张固定流程图。

三类对象应保持区分：**流程规范**规定一类任务必须遵守的规则；**工作流定义**将选定规范落实为当前任务的节点、员工绑定、依赖和验收标准；**节点 IR**是表达与执行这些配置的结构化载体。规范可以约束多种合法工作流，通用节点结构也可以被不同规范复用。

IPD Tool 只承担任务入口，通过 `create_run` 引出整个过程。图引擎位于 Pi Agent 之上，推动 ST 选择规范、工作流架构设计师编写配置、独立 Compiler 校验编译，以及后续调度执行；节点内的 Agent Session 则由 Pi Agent 实例承载。复杂流程控制不堆入外部 Agent 的提示词，也不放入入口 Tool，与《极简 Agent 设计方案》的模块化方向保持一致。[^2]

## 1.3 架构原则

**忠实传递需求，不补造业务前提。** 外部 Agent 将用户原始任务、目标、明确要求、材料引用和待确认事实封装为任务输入，结构化整理不能替代原始内容。ST 负责选择规范并传递任务依据，不进行二次需求改写，也不引入系统推断的前提。

**先设计和校验，再按冻结基线执行。** 工作流架构设计师在设计阶段选择数字员工并完成节点配置，Compiler 负责规则校验和编译。执行期间不得隐式增删节点、替换员工或放宽条件；结构变更必须经过显式 replan 并形成新版本。单次 Run 不修改验收标准，失败和低效证据留作后续优化依据。

**Agent 承担专业工作，引擎掌握流程控制权。** Agent 提交产物、证据和评审意见；状态迁移、节点调度、权限检查、下游放行和任务收口由运行时执行。可判定的流程与权限约束必须落实到代码，不能仅靠提示词要求 Agent 遵守；语义质量仍由相应的专业执行与评审承担。[^3]

**独立评审与返工构成正常作业闭环。** 执行与评审由不同节点承担，Gate 根据预先固定的标准检查确定版本的交付物和证据，过审后才释放受其约束的下游。打回、修订和复审不属于异常。执行者的原 Session 必须持续承担交付责任，直至相关评审责任解除；仍可能被后续 Gate 退回时不得提前销毁，也不能以新实例读取快照代替原实例返工。

**交接和进度以结构化事实为依据。** 节点间传递必要的任务约束、结构化交接信息、产物及证据引用，不转贴全部对话历史。[^4] 产物提交、评审决策和状态迁移由运行时统一登记；对外进度由这些事实派生，不能以 Agent 的自述或一次响应结束作为完成依据。

## 1.4 首版能力范围与实施边界

首版交付从任务接入到最终收口的完整执行链路，范围如下。

| 能力域 | 首版范围 |
|---|---|
| 任务接入与规范选择 | 支持 `create_run`、任务输入保存和 ST 选择预置规范；ST 的单／多 Agent 组织形式暂不固定，不影响其交付契约。 |
| 资产与工作流设计 | 建立规范、数字员工、节点模板及 Skill 等资产的加载与版本引用能力。设计师同样由数字员工实例化，拟以 Project Shepherd 为角色基础，通过专门 Skill 和增量构建工具生成配置，不要求一次输出完整大型 JSON。 |
| 校验与编译 | 独立检查配置结构、资产引用、节点关系和已形式化的规范要求，反馈设计问题并形成冻结的执行基线。 |
| 图执行与质量闭环 | 每个执行节点、评审节点各绑定一个 Agent 实例；支持多节点并行、Fan-out／Fan-in、独立 Gate 和返回原 Session 的返工。控制节点不额外配置 Agent。 |
| 数据与对外状态 | 保存运行状态、产物版本、证据和评审记录；区分业务阻塞与运行时故障，向用户及外部 Agent 提供进度、状态和最终结果。 |

**首版不实现**流程规范的裁剪、组合或自动修改，单节点多 Agent 协作，Token／时间预算与动态资源投资管理，HITL，以及资产自演进。资产可人工维护和发布新版本，但运行记录不会自动改写本轮适用规范、角色资产或验收标准。

目前尚未取得华为内部 IPD 流程规范模板的一手资料，首版先由项目侧手写一份最小流程规范，作为启动与联调资产；该模板不标称为华为正式规范。模板与引擎机制必须分离，不将其阶段、角色或具体拓扑固化到引擎代码。后续取得一手资料后，再按统一资产契约整理接入。

具体任务仅作为端到端验证场景，不决定通用架构、节点语义或资产模型。本章确定目标与边界，后续章节分别定义配置契约、编译规则和运行机制。

# 第 2 章　系统总体架构与端到端流程

## 2.1 外部 Agent、IPD Tool、图引擎与 Pi Agent 的分层关系

系统采用**外部 Agent 接入、图引擎统筹、Pi Agent 执行**的分层架构。外部 Agent 负责与用户交互并判断是否使用 IPD；IPD Tool 将任务输入交给图引擎，创建一次运行；图引擎负责从规范选择到最终交付的完整过程。Tool 是调用入口，不承载流程设计、编译或调度逻辑。这一划分延续极简 Agent 的模块化方向，将长程任务治理从外部 Agent 的对话与工具调用循环中分离出来。[^1]

图引擎架构由主控流程、独立 Compiler、执行 Runtime、Pi 适配层及资产与运行数据支撑组成。ST 和工作流架构设计师承担需要专业判断的工作，Compiler 与 Runtime 分别承担确定性的校验编译和运行控制。这里是逻辑职责划分，不要求各组件部署为独立服务。

Pi Agent 是数字员工的执行载体，而不是整个任务图的调度者。工作流架构设计师及任务节点中的数字员工，通过 Pi 适配层实例化；每个执行节点、评审节点拥有独立的 Pi Agent Session。即使外部 Agent 也使用 Pi，它与这些内部 Session 仍是不同的执行实体，内部完整状态不回填到外部会话历史中。

资产库提供流程规范、数字员工、节点模板和 Skill 等可复用定义；运行数据层保存本轮任务输入、工作流版本、执行状态、产物及证据。两者分别回答“可以按什么规则、由谁工作”和“本轮实际执行到了哪里”，不能用角色说明或会话记录代替运行事实。

## 2.2 从任务接入到最终交付的主链路

一次 `create_run` 建立一个 `run_id`，贯穿规范选择、工作流设计、编译和正式执行。入口返回运行标识后，后续过程由引擎继续推动，外部 Agent 无需逐步唤起内部角色。调用返回、状态订阅断开或外部对话结束，不作为 Run 的完成条件。

```text
外部 Agent → IPD Tool.create_run → 建立 Run、保存任务输入
  → ST 选择预置规范
  → 工作流架构设计师通过 Skill 和构建工具生成配置
  → Compiler 校验与编译 → 冻结执行基线
  → Runtime 调度执行节点、评审节点及既定返工闭环
  → 满足完成条件 → 登记最终交付、向外部提供结果
```

**规范选择。** 主控流程将任务输入交给 ST，由其选定适用规范及版本。交付内容包含规范引用、原始任务与明确要求的引用、待确认事实，以及必要的选择依据。ST 不裁剪规范、不改写用户要求，也不构造推断性的业务前提。首版手写规范作为普通资产参与选择，不在引擎中获得特殊处理。

**工作流设计。** 主控流程启动工作流架构设计师，首版拟以适配后的 Project Shepherd 为角色基础。设计师读取任务、选定规范及可用资产，通过专门 Skill 和增量构建工具建立节点、绑定数字员工、补全工作契约并连接依赖与评审关系，最终提交机器可读的完整配置。工具维护结构化草稿，设计师对任务拆解、员工选择和配置内容负责。

**校验与编译。** Compiler 检查配置、资产引用及已形式化的流程约束，未通过时将结构化诊断返回设计师修订；通过后解析有效配置，形成可执行图并冻结相应版本。校验反馈属于设计阶段的修订，不是正式执行中的产物返工。Runtime 只接收编译通过的执行定义，不临场补齐流程或重新匹配员工。

**执行与交付。** Runtime 根据准入条件调度节点，通过 Pi 适配层创建对应 Session，并向其提供节点契约与必要输入。执行者提交产物及证据后，由关联评审节点检查确定版本的提交；通过后释放受其约束的下游，打回则由原执行 Session 修订并重新提交。并行分支分别推进，Fan-in 按已声明的准出条件汇聚，而不是仅等待各 Agent 停止输出。

当必需交付及关联评审满足工作流的完成条件后，由 Runtime 登记最终产物清单并收口。规范选择、设计或执行中无法继续的情况同样记录在该 Run 下，向外部说明当前阶段与原因，不能被包装为成功结果。

## 2.3 固定主控流程与任务工作流的关系

**固定主控流程负责产生并启动工作流，任务工作流负责完成当前任务。** 前者预先由系统实现，管理 ST 选择规范、设计师编写配置、Compiler 校验修订和启动执行等步骤；后者由本次设计产生，定义具体的专业分工、交付物、依赖关系和质量门。两者是同一架构中的两个控制层次，不需要各建一套引擎，也不额外设置一个依靠自由判断推进全局的总控 Agent。

ST 与工作流架构设计师的启动配置由系统预置，不能依赖尚未生成的任务工作流。设计师的角色资产、设计 Skill 和构建工具在启动时即已确定；任务工作流中各执行者和评审者的选择则由设计师完成。ST 的内部单／多 Agent 形式仍不在本章固定，其对主控流程暴露统一的选择结果契约。

固定的是“选择—设计—编译—执行”的生产过程，不是某种业务的阶段和拓扑。任务工作流可以按规范包含不同数量的节点、并行分支与汇聚点。其前向依赖按 DAG 表达，评审与返工通过预先声明的闭环和运行状态推进；产物修订、重新提交和复审不会隐式改变工作流结构或验收标准。需要改变结构时，遵循第 1 章确定的显式 replan 与版本管理原则。

两个层次共用 `run_id` 和运行数据管理机制，但保留不同粒度的状态：Run 当前处于设计、编译还是执行阶段，与某个节点正在工作、等待评审还是返工，是不同的信息，不能由一个笼统状态互相覆盖。

## 2.4 组件职责、控制权与核心数据交接

各组件通过明确的交付对象衔接，后续阶段不依赖重新解读前一角色的全部对话。核心交接边界如下，具体字段与接口在后续章节定义。

| 交接边界 | 核心交付对象 | 接收方职责 |
|---|---|---|
| 外部 Agent → 图引擎 | 任务输入包：原始任务、目标、明确要求、材料引用和待确认事实 | 保存任务依据，建立 Run 并启动主控流程。 |
| ST → 工作流架构设计师 | 选定规范及版本、任务输入引用、选择依据 | 在规范约束内完成本次任务的具体工作流设计。 |
| 设计师 → Compiler | 工作流配置：节点契约、员工绑定、依赖及交付评审关系 | 检查合法性与规范符合性，返回诊断或生成执行基线。 |
| Compiler → Runtime | 可执行图、解析后的有效配置及版本绑定 | 按冻结定义调度，不擅自改图、换员工或放宽标准。 |
| Runtime → 节点 Session | 节点任务、允许使用的能力、结构化交接包及产物和证据引用 | 在授权范围内执行专业工作或开展评审。 |
| 节点 Session → Runtime | 产物提交、证据清单、评审结论或明确的阻塞说明 | 校验并登记结果，依据既定规则迁移状态和推进流程。 |
| Runtime → 外部 | Run 状态、进度事件、等待原因、已准出产物及最终结果 | 供用户查看或外部 Agent 获取，不要求其重新接管内部调度。 |

**专业内容由 Agent 负责，流程状态由引擎负责。** 设计师决定配置内容，但不能绕过 Compiler 启动执行；评审者依据固定标准形成结论，但由 Runtime 校验评审对象、记录结果并实施放行；执行者可以提交成果或报告问题，但不能直接写入任意节点状态、调用未授权的下游或宣布整个 Run 成功。流程推进不能依赖 Agent 自觉完成一串状态更新操作。[^2]

节点上下文由 Runtime 根据配置组织，通过 Pi 适配层交付，采用必要任务约束、结构化交接信息和可定位的产物引用，而不是全量会话转贴。[^3] 原执行 Session 在评审和返工期间保持存活，释放条件以交付责任解除为准；持久化记录用于追溯与状态管理，不替代原 Session 的执行连续性。

对外查询、订阅和最终结果读取统一来自运行状态与事件记录。Agent 的工作说明可以作为补充，但实际进度以产物提交、评审决策和状态迁移为依据。由此，入口、数字员工和对外展示均不另行维护一份相互独立的任务状态。

# 第 3 章　IPD 流程规范与数字员工资产体系

## 3.1 流程规范的组成与约束范围

流程规范是 ST 的选择对象，也是工作流架构设计师和 Compiler 的共同依据。它规定一类任务必须遵守的作业、职责、交付和评审关系，不预先绑定本次任务的具体员工与全部节点。规范与数字员工分开管理，使同一员工池能够服务不同流程，同一规范也能够产生不同的合法工作流。[^1]

一份流程规范应包含以下内容，具体字段在配置模型中统一定义。

| 内容 | 规范应表达的要求 |
|---|---|
| 标识与适用范围 | 规范标识、版本、来源、适用任务及不适用条件，供 ST 判断能否采用。 |
| 必要作业与职责 | 必须完成的活动或里程碑、所需专业能力及职责分离要求，不直接指定某个员工实例。 |
| 交付与证据要求 | 各类工作必须形成的交付物、证据类别和必要内容，供设计师具体化节点契约。 |
| 评审与交接关系 | 哪些成果必须经过评审、评审应覆盖哪些方面、哪些下游依赖其准出，以及必要的汇聚检查。 |
| 工作流设计约束 | 必须保留的依赖和组织关系、可采用的节点模板，以及设计师进行工作拆分和并行组织时必须满足的条件。 |

**规范同时包含结构化规则与自然语言作业要求，但两者的执行方式不同。** 必经活动、必要交付声明、评审关联等已形式化规则，应具有稳定标识，并由 Compiler 检查工作流是否配置了对应内容；专业内容是否充分、证据是否有效，则需在节点执行和评审中判断。自然语言中写明“必须”，不代表 Compiler 已具备自动判断其全部语义的能力。

规范可以引用通用节点模板，但不能自行改变引擎的节点语义或绕过系统级约束。设计师可以在规范允许的范围内拆分工作、安排并行，并为本次任务补全具体要求；这属于规范实例化，不是裁剪规范。首版 ST 只选择完整的预置规范，设计师也无权删除其中的强制要求。

首版先由项目侧手写一份最小规范，明确标注为项目自定义启动资产，不标称为华为正式模板。它至少应覆盖必要作业、职责、交付与证据、独立评审及完成条件，并采用与后续规范相同的资产契约。取得一手资料后再整理接入；资料中的规则如超出现有表达能力，应显式扩展契约与检查能力，而不是仅替换一段说明就视为引擎已经支持。

## 3.2 数字员工资产与 Agency-Agents 模板适配

数字员工以 **AgentCard** 作为可检索、可绑定的定义，Pi Agent Session 是其在某个节点中的运行实例。员工资产描述稳定的专业职责和可用能力，不保存某次任务的会话状态、交付物或评审进度。同一资产可被多个节点复用，但各节点仍分别实例化 Session，不因使用同一角色定义而共享会话。

AgentCard 应登记员工标识与版本、职责与非职责、能力标签、适用工作类型、基础角色提示词，以及模型配置、Skill、工具、知识库和权限边界的声明。这些信息既用于设计师判断员工能否胜任，也用于 Compiler 解析节点的实际配置。能力描述不等于真实可用能力，工具和知识库等引用仍需能够解析到已接入、可授权的资源。

Agency-Agents 的角色结构可作为资产整理起点，但不直接将整份角色文本作为系统提示词使用。其 Persona 与 Operations 的区分，适合分别承载稳定职责和按需加载的作业方法。[^2] 适配时保留专业职责、交付责任及有价值的工作原则，将具体场景预设与通用角色分离，工具操作和专业方法整理为 Skill；有关持久记忆、自动调度或维护流程状态的文字，不作为已经实现的能力或实际授权。

**员工资产提供稳定职责和配置基础，节点契约定义本次具体工作。** 任务目标、输入、交付清单、评审标准和工作区范围在工作流中配置，不写死到通用 AgentCard。模型及能力配置可以在授权范围内由设计师选定，但不能通过节点覆盖项扩大既定权限或改变强制职责边界。具体配置合并和冲突检查在编译章节定义。

工作流架构设计师同样遵循这套资产模型，首版拟以 Project Shepherd 为适配基础，绑定专门的工作流设计 Skill 和增量构建工具。该员工负责设计与修订配置，不因具备项目协调职责而获得运行时任意调度、改写状态或放宽验收标准的权限。其作业流程在第 6 章展开。

## 3.3 节点模板、Skill、工具与知识库的组织

除规范和员工外，资产库还需要提供可组合的作业资源。各类资产的边界如下。

| 资产 | 主要作用 | 与其他对象的边界 |
|---|---|---|
| 节点模板 | 为某类执行或评审工作提供配置骨架、必填项、默认指引及交付要求。 | 是对通用节点 IR 的复用，不是新的引擎节点类型，也不是已经绑定员工的任务节点。 |
| Skill | 描述如何完成一类工作，包括步骤、工具使用方法及必要检查。 | 引导节点内作业，不代替流程规范、准出标准或运行时权限控制。 |
| 工具定义 | 描述可调用操作、参数与结果契约、权限要求及实现引用。 | 声明工具并不等于已接入或已授权；实际调用仍受适配层和运行时检查。 |
| 知识库定义 | 描述知识范围、检索入口与访问条件，供专业工作获取依据。 | 不等同于节点会话，也不替代运行中产物和证据的登记。 |

这些资产通过引用组合，而不是将相同内容复制进多份员工或节点配置。节点模板中的默认项可由设计师具体化，但不能覆盖规范和引擎的强约束；员工绑定某个 Skill，也不意味着自动获得该 Skill 提到的全部工具权限。

加载方式延续极简 Agent 的按需检索方向：先提供职责、能力摘要及必要目录，再按当前工作读取相关 Skill 或知识内容，不把全部作业手册长期堆入系统提示词。[^3] **按需加载发生在已授权的资产范围内，不等于执行者可以临时增加能力或替换配置。** 运行时可以延迟加载已绑定资源，但不得借检索之名绕过工作流基线。

## 3.4 资产检索、版本管理与运行绑定

首版采用文件化资产包和轻量索引，支持人工维护、校验与发布，不另行引入复杂资产管理服务。资产包保存结构化元数据、正文或实现引用及其依赖；统一登记资产类型、标识、版本、说明和来源。索引由资产定义生成，用于检索和定位，不另行维护一份独立内容。单一来源与一致性校验的思路来自 Agency-Agents 的资产管理分析。[^4]

**检索用于设计决策，绑定用于确定实际执行对象。** ST 检索规范的适用范围，选中后读取完整规范；设计师根据职责和能力检索员工，再检查详细定义及关联资源，并将选定员工和配置写入节点。模型、工具或 Skill 等能力缺失时，应在设计和校验阶段暴露，不能依赖 Runtime 临时寻找替代员工。主控流程使用的 ST 启动配置和设计师资产由系统预置，遵循同样的版本绑定规则。

检索结果和设计草稿应记录明确版本，而不是只保存名称或浮动的 `latest`。Compiler 核对直接引用及其依赖，解析最终生效配置，并在执行基线中保存资产版本、内容摘要及必要内容或可读取的不可变引用。已发布版本不得原地覆盖；新版本仅供后续设计或显式版本变更采用，不自动影响正在执行的 Run。无法取得已绑定版本或内容不一致时，返回诊断，不静默替换。

对于知识库，资产版本固定的是检索配置和访问范围；能够版本化的知识内容应同时绑定相应版本，动态检索得到的材料则作为本轮证据另行记录，不能将连接配置版本当作知识内容已经完整冻结。

ST、设计师和执行节点只在各自授权范围内读取资产；设计师通过构建工具修改本轮工作流草稿，不改写公共规范或员工定义。资产更新由项目侧人工校验并发布，执行中的失败案例、返工记录和低效证据保存在运行数据层，作为后续优化依据，不直接回写本轮资产。由此，资产库负责可复用定义，执行基线负责本轮绑定，运行数据负责实际发生的事实，三者保持清晰分离。

# 第 4 章　任务接入与 ST 规范选择

## 4.1 IPD Tool 的入口参数与任务输入契约

外部 Agent 判断用户任务需要采用 IPD 执行后，通过 `create_run` 提交任务输入包。外部 Agent 负责忠实整理用户请求，IPD Tool 负责调用封装，图引擎的接入组件负责检查和保存输入、建立 Run 并启动规范选择。入口不要求调用方预先选择流程、拆分节点或指定执行员工，也不承担这些设计工作。

任务输入包统一称为 **TaskInput**，其内容范围如下。这里定义信息契约，完整接口与字段 Schema 在后续章节及附录中给出。

| 内容 | 输入要求 |
|---|---|
| 用户原始任务 | 保留原文或引擎可读取的原文引用；涉及多轮已明确要求时，保留相应片段及来源，不仅提交外部 Agent 的摘要。 |
| 任务目标 | 提取用户明确希望达成的结果，并关联原始表述；未单独说明的内容不强行补写。 |
| 明确要求与约束 | 保存用户对范围、交付形式、质量及禁止事项等的明确规定，能够定位其来源。 |
| 材料引用 | 登记用户提供或本次任务明确引用的文件、数据及其他材料，保留定位信息与必要说明。 |
| 待确认事实 | 记录输入中明确未定、缺失或存在冲突且与任务相关的事项，说明对应问题及来源；没有此类事项时可为空。 |

**原始任务是依据，结构化字段是索引和组织方式，不是另一份可以替代原文的需求。** 目标、要求等字段未单独填写，不等于可以忽略原文中的相应内容；也不要求外部 Agent 为了填满字段补充推断性业务前提。输入只携带本次任务所需内容，不将整个外部会话历史作为默认附件。

接入组件检查输入结构、必要内容和原文引用是否可解析，并保存任务输入。通过后建立 `run_id`，返回已受理状态，由主控流程继续推进；原始任务缺失或输入结构不合法时，返回明确错误，不启动 ST。材料后续读取失败或内容不足，与入口结构错误分开记录。受理成功仅表示任务进入系统，不表示已经选到规范或保证最终能够完成。

## 4.2 原始要求、材料与待确认事实的保留

任务输入保存后，ST 和工作流架构设计师通过同一份输入引用读取内容，不各自复制并改写一份任务说明。结构化目标与约束应关联到原始消息片段、文件位置或其他可定位来源；需要读取长材料时可以按需检索，但不能让摘要成为唯一可访问内容。材料的持久化与版本记录由运行数据层负责，具体机制在第 10 章展开。

**待确认事实只表达“哪里尚不明确”，不表达“系统认为答案应该是什么”。** 例如，用户要求使用某份材料但未提供可用引用，可以记录材料尚未取得；不能据此假定材料内容、所属业务或用户接受某种替代方案。来自附件的陈述应保留其来源，不自动升级为用户新增的目标、约束或流程授权。

ST 可以记录在匹配过程中发现的具体缺项或冲突，但必须指向现有任务输入，并写入选择阶段记录，而不是原地修改 TaskInput。ST 对规范适用性的判断记录为选择依据，不写入任务事实。原始要求之间存在无法消解的冲突时，也不能通过静默选取其中一项来继续推进。

并非所有待确认事实都必须在规范选择前解决。若任务目标和适用范围已经明确，剩余事实能够通过后续工作取得，ST 可以连同规范一起传递，由设计师安排相应工作及输入依赖；若缺项直接影响规范适用性或使任务目标无法确定，则不能带着假定答案进入工作流设计。这一判断只决定是否具备继续设计的依据，不将 ST 扩展为研究、需求补写或业务决策角色。

## 4.3 ST 的职责、规范检索与选择过程

ST 由固定主控流程启动，使用系统预置的启动配置和规范检索能力，不依赖尚未生成的任务工作流。其内部采用单个还是多个 Agent，暂不在本章固定；对外均提交统一的选择结果。ST 只负责从已登记规范中选择一个确定版本，不裁剪、组合、修改或新建规范，不选择具体执行员工，也不承担节点拆解和配置编写。

**先依据任务检索候选，再读取完整规范作出选择。** ST 从原始目标、预期交付和明确约束提取匹配条件，查询第 3 章定义的资产索引；索引用于缩小候选范围，不能替代规范正文。对候选规范，应检查适用与不适用条件、必要作业、交付与评审要求，以及它们与用户明确要求是否冲突。选择围绕任务所需的组织方式展开，而不是先固定一条流程，再改变任务解释使其适配。[^1]

存在多个适用候选时，ST 根据任务目标、必要交付及协作要求选择更贴合的一份，并记录简明依据。依据应指出相关任务要求与规范条款，不要求输出完整推理过程，也不另建一套无来源的风险标签或业务前提。规范引用必须包含明确版本；不能只提交显示名称、检索摘要或浮动的 `latest`。

首版即使只登记一份项目手写规范，仍执行相同的适用性检查和交付流程。只有该规范适用于当前任务时才能选用，不能把“资产库只有一个候选”当作适用依据。无适用规范时如实报告，不在运行中放宽规范要求或临时生成替代模板。规范补充由项目侧维护资产，不属于 ST 本轮职责。

## 4.4 ST 的交付格式与无法继续时的处理边界

成功选定规范后，ST 提交 **ProcessSelection**，作为交给工作流架构设计师的选择记录。它不是一份经过改造的新规范，也不是任务工作流草稿。

| 交付内容 | 作用与边界 |
|---|---|
| Run 与任务输入引用 | 关联本轮运行及已保存的 TaskInput，使设计师直接读取同一份原始任务、明确要求和材料。 |
| 规范引用 | 指定已登记的规范标识与确定版本，由资产层解析完整内容；不包含裁剪或覆盖项。 |
| 选择依据 | 简要说明该规范如何匹配任务，引用必要的任务要求和规范条款，不补充业务前提。 |
| 待确认事实记录 | 关联输入中已有的待确认事项，并列出匹配时发现的、有来源的缺项；说明哪些事项需在后续工作中处理。 |

主控流程接收结果后，检查其是否属于当前 Run、任务输入引用是否一致、所选规范及版本是否存在且可读取，以及交付结构是否完整。检查通过后保存选择记录和规范版本绑定，再启动工作流架构设计师；设计师同时取得任务输入、选择记录和完整规范，不仅接收 ST 的总结。上述检查不替代 ST 的适用性判断，也不替代第 7 章对具体工作流的规范符合性校验。状态推进由主控流程负责，不要求 ST 自行更新多个状态或直接调用设计师。[^2]

无法继续时，按原因分别处理，不能统一归为“选择失败后重试”：

**没有适用规范。** ST 提交无匹配结果，说明已检查的相关候选及不适用原因。主控流程登记当前阻塞原因，不启动设计师，也不静默退回某个默认流程。该结果可以作为后续人工补充规范资产的依据，但不会自动触发资产生成或修改。

**输入不足或要求冲突。** ST 指出影响选择的具体事项及来源，主控流程登记并向外部暴露。首版不自行发起 HITL 澄清，也不通过补造业务前提消除阻塞。若缺项不影响选择，则按前述交付契约传给设计师，不要求所有未知事实都在此阶段解决。

**交付无效或读取故障。** 规范引用不存在、版本遗漏或交付结构不完整时，由主控流程返回结构化诊断，交给 ST 修订；合法引用因存储、连接等原因暂时无法读取，则按运行时故障处理，不误记为没有适用规范。具体技术重试与故障收口机制在第 11 章定义。

规范已选定、因无匹配或输入问题而阻塞、正在修订交付，以及发生技术故障，均记录在同一个 Run 的规范选择阶段，并供外部查询。只有选择结果通过检查并完成登记后，主控流程才进入工作流设计阶段。

# 第 5 章　工作流配置模型与节点 IR

## 5.1 工作流配置的整体结构与标识引用

工作流架构设计师以第 4 章的 TaskInput 和 ProcessSelection 为依据，生成本次任务的 **WorkflowDefinition**。它是提交给 Compiler 的机器可读工作流定义，描述具体工作、员工绑定、交付契约和流程关系；不保存执行中的会话、节点状态或产物修订记录。编译后的有效配置与运行时事实分别由执行基线和运行数据承载。

首版使用 JSON 作为正式配置文件格式，由增量构建工具维护草稿并导出。配置模型按以下内容组织，本章确定信息结构与引用语义，完整 Schema 放入工程附录。

| 配置分组 | 核心内容 |
|---|---|
| 标识与版本 | `schema_version`、`workflow_id`、`workflow_version`，分别标识配置格式、工作流及其定义版本。 |
| 任务与规范依据 | TaskInput 和 ProcessSelection 的引用，关联原始要求及选定的规范版本，不重新复制、改写一套任务与规范。 |
| 节点定义 | 节点类型、员工引用、工作契约、能力配置，以及可选的节点模板引用。 |
| 准出标准 | 具有稳定标识的标准定义，明确适用对象、检查要求和证据依据，供执行者及评审者共同引用。 |
| 流程关系 | 前向依赖、输入绑定、汇聚条件、评审对象和预先允许的返工目标。 |
| 要求覆盖与完成条件 | 用户要求对应的工作与验证责任、最终交付引用，以及 Run 成功收口必须满足的条件。 |

工作流内的 `node_id` 唯一且在本轮执行中稳定，节点交付物通过“节点标识 + 输出标识”定位，标准使用 `criterion_id` 引用。公共资产采用第 3 章约定的确定版本引用。节点名称、文件显示名和说明文字仅用于理解，不承担关联主键的作用。

**定义版本与提交版本分开管理。** 正常返工只产生新的产物提交和评审记录，不改变工作流版本或节点身份。`session_id`、`submission_id`、实际产物位置及评审结果由运行时登记，不由设计师预填到 WorkflowDefinition。本章的字段与分组是项目侧对既有节点契约思想的工程化表达，不是华为内部模板的字段复述。[^1]

## 5.2 执行节点、评审节点与单 Agent 配置

首版 Agent 作业节点分为 **执行节点（execution）** 和 **评审节点（review）**。二者共用节点标识、目标、员工绑定、输入和能力配置等基础结构，但工作责任和提交结果不同。每个节点只绑定一个数字员工资产，并由 Runtime 为该节点创建一个独立 Pi Agent Session；不配置参与者列表或节点内部的多 Agent 协作拓扑。

执行节点负责完成专业工作，正式提交约定的交付物与证据。评审节点负责检查指定提交，形成与标准、产物和证据对应的评审结果，不直接修改被评审产物。评审者与被评审执行者必须属于不同节点、不同 Session，并满足所选规范的职责分离要求。复用同一员工资产不等于复用节点实例或共享会话。

评审节点还需明确评审对象、适用的标准引用和允许的返工目标。一名评审者可以检查多个执行节点的成果，例如进行汇聚后一致性评审；这仍然是单 Agent 评审节点，不属于节点内多 Agent 协作。普通执行节点自检可以作为作业步骤，但不能替代规范要求的独立 Gate。

Fan-out、Fan-in 和准入判定属于引擎控制语义，不配置数字员工。首版优先通过依赖关系和汇聚条件表达这些控制，不为了分支或汇聚额外增加管理 Agent。ST、工作流架构设计师的启动配置仍归固定主控流程管理，不混入本次任务的节点列表。

## 5.3 节点工作契约与交付、评审标准

节点 IR 的核心是可供执行、交接和评审共同使用的工作契约，而不是一段宽泛的角色提示词。其内容如下。

| 契约项 | 配置要求 |
|---|---|
| 目标与职责范围 | 说明本节点要解决什么问题、对哪些结果负责，以及不承担哪些工作；关联相应任务要求或规范条款。 |
| 输入绑定 | 明确输入来自任务材料、哪个节点的哪项交付或哪次待评审提交，并声明必要性、内容或格式要求及使用条件。 |
| 执行要求 | 给出必须完成的作业、必要检查和应遵循的方法；专业操作细节可以引用 Skill。 |
| 约束 | 明确内容、行为和交接限制，并关联需要运行时实施的权限配置。 |
| 交付物与证据 | 为输出设置稳定标识，规定交付形式、必需内容和证据要求；存在结构化格式时引用对应 Schema。 |
| 准出标准引用 | 关联本节点交付必须满足的标准，使执行者提前知道验收依据，关联 Gate 按同一依据评审。 |

输入通过结构化绑定取得，不要求下游从上游聊天中寻找材料。执行节点通常使用已准出的上游成果，评审节点则必须能够读取尚未过审的正式提交；两类输入的使用条件应明确区分，否则会出现评审必须等待自己批准才能启动的依赖错误。交接包保留必要约束、产物与证据引用，详细内容按需读取。[^2]

交付物定义描述预期提交的对象，不使用可被任意覆盖的共享路径充当产物身份。Runtime 在正式提交时登记具体版本，评审绑定该版本，下游取得对应的获准使用版本，而不是读取一个含义不明的“最新文件”。证据应说明支持哪项产物或标准，并能定位原始材料、验证结果或操作回执；执行者自述“已完成”不构成验证证据。

**每条准出标准在配置中只定义一次，由执行节点和 Gate 引用。** 标准包含评审对象、具体要求、验证方式和证据要求；局部交付标准与跨产物的一致性标准可以分别定义。可机械检查的格式、必需项等交给确定性检查，内容正确性与完整性等交给相应评审者。单次 Run 不允许执行者或评审者临时增删标准、调整阈值或以新增偏好打回成果。

输入中尚待确认的事实仍以待处理事项传入，设计师为其指定调查或验证责任，并设置依赖它的后续工作条件。无法取得必要依据时报告阻塞，不把未经确认的答案写成节点前提。

## 5.4 员工绑定与节点能力配置

每个 Agent 作业节点通过唯一的 `agent_ref` 绑定已登记数字员工及其确定版本。设计师在设计阶段完成选择，并配置本节点实际使用的模型、系统提示词补充、任务提示词、Skill、工具、知识库和权限范围；Runtime 不重新匹配员工。员工资产和节点模板中已有的内容通过引用复用，不在配置文件中整段复制。[^3]

节点能力配置应区分**内容组合**和**权限授权**。稳定职责来自 AgentCard，本次目标、作业要求和输入构成节点任务上下文；节点补充提示词不得覆盖员工的强制职责边界、流程规范或系统规则。具体合并顺序和冲突诊断在第 7 章定义，编译后形成唯一的有效配置，避免运行时依靠提示词排列顺序猜测哪条规则优先。

Skill、工具和知识库分别声明预置资源、允许按需检索的范围及相应访问条件。按需加载只改变已授权内容何时进入上下文，不扩大可用能力。工具权限、数据读取范围、工作区写入范围及对外操作权限必须能够映射到实际执行限制；某项限制无法实施时应在校验中暴露，不能只写成一句禁止事项。模型和资源引用中不包含明文凭据，认证由接入配置提供。

首版不在节点配置中加入 Token／时间预算或动态投资字段。模型请求、工具连接等底层故障处理由运行时统一承担，不要求设计师为每个节点配置一套技术重试机制。

## 5.5 依赖、并行、汇聚与正常返工关系

**前向依赖表达推进条件，输入绑定表达消费对象。** 一个节点需要哪些材料，与这些材料满足什么条件后才允许使用，应相互对应。Compiler 检查引用和准入关系的一致性，避免出现已有数据绑定却没有必要的准出约束，或依赖了无法满足的条件。配置只使用引擎支持的结构化条件，不把任意脚本作为流程路由逻辑。

前向关系保持 DAG。多个节点的必需输入分别就绪后可并行执行，形成 Fan-out；Fan-in 在声明的必需输入及其准出条件全部满足后继续。某个分支被打回只阻塞依赖它的工作，不自动阻塞其他独立分支。各分支是否允许共享可变工作区，由明确权限和产物整合安排决定，不能因为图上允许并行就默认共同覆盖同一份文件。

评审关系应同时说明“检查谁的提交”和“批准后释放哪些依赖”。例如，执行节点 A 的正式提交使 Gate G 就绪，G 对该提交准出后才使下游 B 就绪；B 的业务输入仍是 A 的获准产物，G 提供的是准出依据。受控交付物不得通过一条绕过 G 的直接依赖交给 B。综合 Gate 可以同时关联多个提交，并验证它们能否共同支撑后续工作。

返工关系与前向依赖分开表达，由评审节点预先关联允许退回的执行节点。评审者提交具体问题、标准引用、证据及涉及的返工对象，Runtime 校验后将反馈交回原执行 Session。返工不新增节点、不替换员工，也不修改标准；修订后重新提交并复审，属于正常作业闭环，而不是异常重试。[^4]

后续 Gate 允许退回较早节点时，必须在配置中保留相应关系。由此产生的下游输入失效、重新评审和 Session 责任保留，由 Runtime 根据依赖与提交版本处理，具体机制在第 8、9 章展开。问题无法落入既定返工关系时，应报告流程无法继续或请求显式 replan，不由评审者临时创建回退边。

## 5.6 任务要求覆盖与最终完成条件

工作流必须保留从原始要求到工作责任、交付及验证依据的追溯关系。设计师通过任务输入中的要求引用或原文定位，关联负责节点、输出和准出标准；Gate 再引用相应标准承担验证。交付目标需要对应成果，禁止事项等约束则可以对应节点约束或权限规则，不强制为每条要求额外制造一份文档。

这份覆盖关系不代替原始需求，也不允许设计师为了满足表格完整性改写用户要求。Compiler 能检查引用是否有效、必需要求是否声明了责任和验证安排，但不能仅凭关系存在就证明任务拆解充分或标准合理；这些语义质量仍由设计与评审工作承担。

完成条件明确本轮最终交付由哪些节点输出组成、必须通过哪些 Gate，以及哪些必要作业和依赖必须闭合。Runtime 在确认对应提交版本仍然有效、所需评审已通过且没有未解决的必需条件后，登记最终交付清单并将 Run 收口。所有 Agent 停止响应、某节点自行宣布成功或文件已经存在，都不能替代上述判断。

设计期配置错误交给设计师修订，执行中的业务阻塞与技术故障按第 11 章分别处理；本章只定义正常作业和成功收口所需的配置契约，不将底层故障处理混入工作流结构。

# 第 6 章　工作流架构设计师与配置构建机制

## 6.1 基于 Project Shepherd 的角色适配与职责边界

工作流架构设计师由固定主控流程启动，首版拟以适配后的 **Project Shepherd** 作为数字员工资产，通过 Pi 适配层创建独立 Session，并预置工作流设计 Skill、资产检索与配置构建工具。其启动配置由系统确定，不依赖尚未生成的任务工作流，也不作为当前任务图中的一个执行节点。

本项目将该角色的职责限定为：依据任务与规范拆分工作，选择执行者和评审者，设计节点契约、依赖及评审关系，建立要求覆盖与完成条件，并根据校验反馈修订配置。角色资产承载稳定职责，设计 Skill 承载作业方法，构建工具承载结构化编辑能力；采用 Project Shepherd 并不表示原角色模板已经具备生成本项目配置的能力。[^1]

设计师接收已保存的 TaskInput、ProcessSelection 及其引用的完整规范，同时获得配置 Schema、节点模板和可用资产的检索入口。原始要求与规范是共同设计依据，ST 的选择摘要不能替代二者。待确认事实应安排相应的调查或验证责任；缺少必要依据且无法通过任务内工作补齐时，报告具体阻塞，不补造业务前提。

**设计师有权编写本轮草稿，无权修改任务依据、公共资产或实际运行状态。** 它不能重新选择或裁剪规范，不能为满足节点配置而临时创建未登记员工，也不能绕过 Compiler 启动执行。该角色负责组织未来的专业工作，不直接代替执行节点生产最终业务产物；工作流运行期间的调度、评审放行和状态维护仍归 Runtime。

## 6.2 工作流设计 Skill 的结构与作业流程

设计 Skill 规定如何把任务与规范转化为第 5 章的 WorkflowDefinition，不再定义另一套工作流格式。主 Skill 保留作业步骤、阶段检查点、工具用途及提交条件；节点配置说明、关系样例和诊断解释按需读取。工具参数和字段约束以同版本 Schema 为准，Skill 引用这些契约，不手工维护一套可能与实现脱节的字段说明。这延续极简 Agent 的静态职责与按需作业知识分离方式。[^2]

设计过程按以下顺序逐步收敛，允许根据检查结果返回前面步骤修订，不要求一次性生成完整 JSON。

| 设计阶段 | 主要工作与阶段检查 |
|---|---|
| 核对依据 | 读取原始任务与完整规范，识别必须覆盖的要求、作业和评审关系，登记待处理事实，确认设计所需资产可检索。 |
| 建立骨架 | 围绕可验收交付物拆分执行工作，配置必要的独立评审，初步确定前向依赖、并行分支与汇聚位置；不把每次工具调用拆成一个节点。 |
| 配置节点 | 按职责和能力检索、读取员工定义，绑定确定版本，补全目标、输入、执行要求、交付物、证据、准出标准及能力权限配置。 |
| 闭合关系 | 核对输入来源与准入条件，补齐评审对象和返工目标，建立原始要求到节点、交付与验证的覆盖关系，明确最终完成条件。 |
| 检查并提交 | 执行局部与整图校验，修订受影响配置，复核工作责任和验收依据，再由工具生成正式配置并提交 Compiler。 |

员工选择不能只依赖角色名称。设计师应检查 AgentCard 的职责边界、能力标签及已接入资源是否满足节点工作，评审者还需满足规范的职责分离要求。工具可以返回候选与配置诊断，但具体选择及任务契约由设计师负责；资产缺失不能通过填写一个看似合理的名称解决。

设计 Skill 只用于组织设计师的作业，不自动注入后续执行节点。节点所需的专业 Skill 由设计师分别绑定，具体工作要求则落入节点契约。上述设计步骤也不额外生成一组业务管理节点；主控流程负责启动设计师、接收配置及推进编译，不需要设计师再调用下游 Agent。

## 6.3 草稿管理与增量构建工具

**工作流草稿由构建组件持久化，设计师通过小范围、结构化操作逐步修改。** 草稿沿用 WorkflowDefinition 的内容模型，但允许尚未补全的节点和关系，并在编辑元数据中记录缺项、修订号与诊断。它不是第二种可执行格式，也不把草稿编辑状态写成任务节点的运行状态。

首版采用单设计师顺序编辑，不引入多人协同编辑或额外的配置生成 Agent。资产检索复用第 3 章能力，构建工具按以下职责组织；名称用于界定接口，完整参数在工程附录中定义。

| 工具 | 主要职责 |
|---|---|
| `asset_search`／`asset_read` | 检索候选资产并读取确定版本的完整定义，供员工选择、模板复用和能力配置使用。 |
| `workflow_draft.open` | 根据当前 Run、TaskInput 和 ProcessSelection 建立或取得设计草稿，返回草稿标识及当前修订号，不重复创建多份独立草稿。 |
| `workflow_draft.read` | 读取整体结构摘要、指定节点、标准或关系，以及相应缺项和诊断；需要核对某个部分时不默认返回全部 JSON。 |
| `workflow_draft.apply` | 按明确操作类型新增、更新或删除配置对象，支持节点配置、员工绑定、标准、输入与依赖、评审返工关系、要求覆盖和完成条件的局部编辑。 |
| `workflow_draft.validate` | 对当前修订执行局部或整图检查，返回结构化诊断，不自行补写语义内容或修改草稿。 |
| `workflow_draft.submit` | 检查提交条件，固化当前草稿快照并导出正式配置，将文件引用和版本信息交给主控流程进入编译。 |

`apply` 使用受支持的领域操作，而不是让模型生成任意修改脚本。例如，先新增一个执行节点及输出，再根据返回的稳定标识配置标准、评审节点和依赖；补充节点工具范围时只更新该配置，不重新生成整张图。每次调用可提交一组相关变更，工具负责序列化、标识与引用检查，目标、工作要求及标准内容仍由设计师填写。

草稿尚未完整时，可以保存待配置项，但不能把缺项静默填成默认员工、空验收条件或自动通过规则。每次写入检查操作是否合法、已提供字段是否符合类型与权限要求；完整性及跨对象关系在校验时继续检查。删除或改变被引用对象时，必须同步处理相关引用，或者明确保留为待修订诊断，不自动删除关联 Gate 来使图通过检查。

每次修改携带草稿修订号和操作标识，构建组件原子应用相关变更，返回新修订号、变更摘要及受影响项。过期修订不得覆盖当前草稿，同一操作重复提交应返回已登记结果，避免工具响应重传导致重复节点。草稿修订号用于编写过程，不等同于 `workflow_version`，也不代表发生了运行期 replan。

权威草稿和正式配置只允许由构建组件写入，不能同时允许设计师通过通用文件或 Shell 工具绕过编辑接口修改。需要查看文件时可以提供只读视图；说明文档不是配置事实源。这样，模型负责设计决策，工具负责可靠落盘，不依赖模型自行维护多份文件的一致性。

## 6.4 局部校验、整图检查与反馈修订

编写期检查与正式 Compiler **复用同一套配置契约和校验规则**。局部校验用于及时发现字段类型、员工引用、能力配置和输入输出绑定等问题；整图检查进一步覆盖前向依赖合法性、必要评审、返工关系、要求覆盖、完成条件及已形式化的规范约束。工具只是调用入口，不在自身内部另建一套宽松的“快速规则”。具体检查和编译流程在第 7 章定义。

未完成草稿允许存在缺项，因此“已成功写入”不等于“已通过校验”，“某节点局部合法”也不等于“整图可提交”。校验报告应绑定草稿标识、修订号和所用 Schema 版本，列出问题代码、严重程度、配置位置、关联对象或规范条款，以及可理解的原因。草稿更新后，旧报告不得直接作为新修订已经通过的依据。

设计 Skill 指导设计师先定位问题及关联配置，再进行最小范围修订。例如，诊断指出某项受控输出绕过评审被下游使用时，应一起核对输出绑定、Gate 对象与下游准入条件，而不是只改一个字段来消除提示。修改节点输出或评审标准引用后，也应复查相应依赖、要求覆盖及完成条件；相关内容修订完毕后重新执行整图检查。

Compiler 正式检查未通过时，主控流程将诊断返回原设计师 Session，继续修订草稿，不重新创建一个设计师读取摘要接手。设计阶段的配置修订与执行阶段的产物返工分别记录，不混为同一类重试。资产确实不可用、要求冲突或既有节点语义无法表达必要流程时，应报告具体限制，由主控流程登记阻塞；不能删除强制要求、降低标准或伪造资产来消除错误。存储或工具连接失败则按运行时故障处理，不误报成设计不合法。

**校验通过不替代设计质量责任。** 设计师仍需核对工作拆分是否覆盖原始要求、员工是否真正适合其职责、标准是否能够检验交付物，以及并行成果是否有明确整合责任。结构检查能够发现缺少引用或必要关系，不能仅凭字段齐全就证明自然语言目标和标准充分；首版不为此另设一个自由裁决的总控 Agent。

## 6.5 完整配置文件的生成与正式提交

设计师完成修订和整体核对后，调用提交工具。构建组件针对指定草稿修订完成提交前检查，生成不可变快照，并按正式 Schema 序列化为 JSON。文件只包含 WorkflowDefinition 的定义内容，不混入草稿编辑记录、校验日志、Session 状态或实际执行结果；这些信息关联到本轮运行记录中保存。

提交回执应包含当前 Run、草稿标识与修订号、`workflow_id`、`workflow_version`、配置文件引用及内容摘要，并关联本次检查报告。文件中的任务输入、规范及资产引用保持确定版本。候选配置提交后不得原地改写，主控流程与 Compiler 读取的必须是回执对应的同一份内容，而不是一个随后可能变化的“当前草稿”。

**提交成功只表示配置已交付，不表示工作流已经获准执行。** 主控流程登记提交并调用独立 Compiler，Compiler 再对这份确切配置执行完整校验、资产解析和编译；通过后才由主控流程冻结执行基线并交给 Runtime。设计师不自行标记编译通过，也不通过工具串联承担状态更新和启动执行事务。[^3]

若正式编译返回诊断，设计师在原 Session 中基于已提交内容继续编辑，形成新的草稿修订并重新提交；旧文件和诊断保留，新提交重新接受检查。提交、诊断和修订均归入同一个 Run 的设计阶段，外部状态由主控流程根据这些记录派生，不以设计师自述“设计完成”作为推进依据。

执行基线冻结后，当前配置不再通过普通草稿编辑入口修改。后续结构调整必须进入第 7 章定义的显式 replan 与版本变更流程，不能以重新调用构建工具绕过冻结边界，单次 Run 的验收标准保持不变。正常执行中的交付物修订则留在既定执行—评审闭环内，不返回设计师重新编写工作流。

# 第 7 章　工作流校验、编译与执行基线

## 7.1 配置结构、资产引用及节点契约校验

Compiler 是图引擎架构中的独立确定性组件，接收第 6 章正式提交的 WorkflowDefinition，输出校验诊断或编译产物。它不承担任务规划，不自行修正专业内容，不启动节点 Session，也不直接改变 Run 的执行状态。编写期的 `workflow_draft.validate` 与正式编译复用同一套规则，但局部检查不能代替正式提交后的完整检查。将流程定义转化为可检查的执行约束，而不是依靠角色提示词自行推进，是本项目对既有材料的工程化落实。[^1]

正式编译以提交回执指向的不可变配置为输入，同时读取该 Run 已保存的 TaskInput、ProcessSelection、所选规范及确定版本的依赖资产。首先核对配置内容摘要、任务与规范引用及提交归属，确保检查的是设计师实际提交的那份内容，不能转而读取仍在变化的草稿。配置不得通过替换输入引用、规范版本或加入覆盖项，绕过此前确定的任务依据与完整规范。

**结构与契约检查。** 校验 `schema_version`、工作流标识与版本、节点类型、必填内容、唯一标识及跨对象引用。每个执行节点和评审节点只允许一个 `agent_ref`；执行节点具备完整的工作与提交契约，评审节点明确评审对象、标准引用和返工目标。输入绑定、输出标识、`criterion_id`、要求覆盖及完成条件必须能够相互解析。对于已声明的结构化格式，检查支持范围内的格式兼容性；未知字段、未支持的条件类型和任意脚本路由不得被静默忽略。

**资产与能力检查。** 核对直接引用及其依赖的标识、版本、内容摘要和可读取性，检查员工职责声明、模型配置、Skill、工具及知识库是否能够解析。工具和数据权限必须能映射到当前适配层支持的实际限制，不能仅因提示词中写了禁止事项就视为已实施。资产未登记、版本不存在与合法资源暂时读取失败分别处理；Compiler 不自动改用 `latest`、其他员工或权限更宽的替代工具。

这些检查覆盖结构化声明，不把自然语言职责与提示词的全部语义兼容性视为可机械证明，也不保证外部服务在后续执行时始终可用。专业判断由设计师与相应评审者承担，实际调用和权限检查仍由 Runtime 执施。

## 7.2 IPD 规范符合性与整图合法性检查

节点局部合法之后，还必须检查整张图是否满足规范、交接和完成要求。Compiler 根据规范中具有稳定标识的结构化规则，核对其在工作流中的落实位置；自然语言作业要求保留为节点与评审依据，不冒充已经自动验证的事实。首版手写规范与后续接入规范使用同一套检查入口，不为启动模板设置跳过校验的特例。

| 检查范围 | 必须满足的条件 |
|---|---|
| 规范要求与职责分离 | 必要作业、交付和评审均有对应配置；执行者与评审者分属不同节点，并按独立 Session 实例化。是否允许复用同一员工资产，依据规范的职责限制判断，不以角色名称不同代替独立性。 |
| 前向依赖与准入 | 前向关系保持 DAG，必需节点和完成条件可达；输入来源与准入条件一致，不存在自我等待或无法满足的引用。Gate 可以消费待评审提交，不应依赖自己尚未给出的批准。 |
| 受控产物与 Gate | 评审对象、标准适用对象及下游消费对象一致；受控产物的使用条件包含相应准出要求，不能通过直接依赖、汇聚或最终交付引用绕过必要 Gate。 |
| 并行与汇聚 | 各分支具有独立的工作、输入和提交契约；Fan-in 明确全部必需输入及其准出条件。已声明的共享写入范围存在冲突时，必须具有可落实的隔离、整合或先后约束。 |
| 正常返工关系 | 返工目标是明确的执行节点，与被评审成果或其上游来源有关；关系与前向依赖分开表达，不允许评审者临时指定任意节点。 |
| 要求覆盖与完成条件 | 用户要求和规范强制项存在相应责任、交付或约束及验证安排；最终交付引用有效，成功条件包含所需评审和必要作业的闭合。 |

返工边不参与前向 DAG 的判环，但必须通过目标与关联关系检查。编译结果应保留前向、反向依赖及评审索引，供 Runtime 处理回退后的输入失效与复审；不能为了得到一张无环图而删除正常返工关系，也不能把所有控制回退混入前向拓扑后判为非法。

对规范要求的必需机器检查，缺少对应规则实现时，应明确报告不支持，不能降为普通提示后放行。对于规范中的自然语言要求，Compiler 可以检查是否已配置执行或评审责任，却不能据此证明标准充分、工作拆解合理或未来产物正确。**编译通过表示配置在已支持规则内合法且可执行，不表示业务质量已经过审。**

## 7.3 资产解析、配置合并与可执行图生成

资产解析将已绑定定义展开为每个节点唯一的有效配置，并保留字段来源及资产版本，便于诊断和追溯。解析与整图检查可以按依赖交叉进行，但必须全部完成后才能产出可执行结果。Compiler 不重新选员工，也不补出设计师未定义的专业节点、验收标准或流程路线。

**普通配置采用明确的覆盖顺序，强制要求不参与覆盖。** 对模型配置等允许覆盖的同名字段，按“节点模板默认值 → AgentCard 默认值 → 节点显式配置”依次取值。节点模板提供通用基础，员工资产提供该员工的默认配置，节点填写本次明确选择。资产与 Schema 必须区分默认项、必需项和授权上限；缺失的语义必填内容不得被空值或宽松默认值补齐。

Skill、工具和知识库清单不采用无条件并集。显式配置可以替换可选默认项，但规范或资产要求的必需项仍需满足，传递依赖也必须解析到确定版本。最终能力不得超出系统授权、员工资产及规范规定的边界；越权请求、必需能力缺失或无法实施的访问限制直接报错，不通过静默删去请求或扩大权限使编译通过。按需检索范围同样进入有效配置，不能留到执行时任意扩展。

提示词按系统与规范规则、员工基础职责、节点工作契约和允许的补充内容分块组合；节点补充不构成对强制规则的覆盖权。Compiler 固定其内容来源和组合方式，Runtime 再按节点状态注入输入及交接包。提示词中的限制与实际工具、数据权限分别落实，不能依靠文本排列顺序实现授权。静态职责与按需作业内容的区分沿用前述资产设计。[^2]

编译产物包含**可执行图、节点有效配置、资产锁定清单及校验报告引用**。可执行图将第 5 章的依赖、输入绑定、Gate、返工目标和完成条件转换为 Runtime 可直接使用的结构与索引；Fan-out／Fan-in 等控制语义可以展开为内部调度结构，但不额外生成 Agent 管理节点。资产锁定清单记录直接与传递依赖的版本、内容摘要及不可变内容或引用，同时记录 Schema、Compiler／规则集版本和所需适配能力。

编译产物是对 WorkflowDefinition 的确定性解释，不是另一份可独立编辑的业务计划。在同一适配能力环境下，相同定义、依赖内容和编译规则应得到语义一致的结果；修改配置必须回到受控设计入口。节点就绪判定、提交版本选择、状态迁移和 Session 生命周期由 Runtime 负责，具体执行机制在第 8、9 章展开。

## 7.4 编译诊断及返回设计师修订的协议

每份正式报告应绑定 Run、提交回执、配置内容摘要、来源草稿修订及所用规则版本，记录检查是否完整结束。单项诊断包含问题代码、严重程度、配置位置、关联节点或资产、规范条款引用，以及可理解的原因和修订提示。修订提示用于定位问题，不直接代写专业要求，也不授权设计师删除强制项。

**错误阻止编译通过，警告只用于不违反强制约束的提醒。** 未完成检查、尚未解析的必需资产或不支持的强制规则，不能因为当前错误列表为空就视为成功。例如，发现某个下游消费了未经必要 Gate 准出的产物，应同时指出输出、输入绑定和缺失的准出关系，而不只返回“工作流不合法”。

配置不合法时，主控流程登记诊断并返回原工作流架构设计师 Session。设计师通过 `workflow_draft.read` 定位问题、通过 `workflow_draft.apply` 修订，再重新校验和提交不可变配置；旧报告保留，但不作为新修订的通过依据。即使改动范围很小，正式提交仍需接受完整检查，不能仅凭修改过的节点局部通过就启动执行。

资产确实缺失、规范要求无法由现有节点语义表达或任务要求存在冲突时，应登记相应设计阻塞，不能无限重复提交相同配置，也不能用换规范、放宽标准或虚构资产消除诊断。存储不可用、读取中断和 Compiler 内部执行故障属于技术故障，不能误报成设计内容不合法；其处理归第 11 章。编译未完成或失败时，不生成可激活的执行基线，也不启动部分任务节点。

## 7.5 工作流冻结、版本管理与显式 replan 边界

Compiler 成功返回后，由主控流程将确切的配置快照、编译产物、资产锁定清单和报告登记为**执行基线**，绑定当前 Run 并完成冻结。基线记录具有独立标识和内容摘要，不再依赖可变草稿或浮动资产索引。只有完整基线登记成功、Run 完成相应阶段迁移后，Runtime 才能接收启动指令；重复回执或重复启动请求不得生成另一套节点实例。[^3]

Runtime 按基线读取有效配置，并核对兼容性及所需内容的完整性，不在启动时用新的资产重新解析一遍来改变执行定义。主控流程和运行数据层负责基线登记、启动衔接及状态一致性，Compiler 本身不承担这些状态事务。正式任务启动前的配置修订、编译失败和重新提交仍属于设计阶段，不称为运行期 replan。

版本应保持三个层次的区分：草稿修订记录编写过程；`workflow_version` 标识工作流定义；提交版本与评审记录表达正常作业中的产物变化。已经提交的快照和冻结基线均不得原地覆盖。正常打回、修订和复审只改变提交及评审记录，不重新编译工作流，也不改变节点身份、员工绑定或验收标准。

**显式 replan 是受控的定义变更，不是执行者获得自由改图的权限。** 既定流程无法继续时，节点只能报告原因和受影响工作，由主控流程登记变更请求，在安全边界暂停受影响调度，并授权原设计师在新版本设计上下文中修订。新定义保留旧版本引用和变更说明，使用新的 `workflow_version`，重新接受完整校验与编译；普通草稿编辑入口不能绕过这一过程修改当前基线。

同一 Run 的任务依据、所选规范及已冻结验收标准保持不变，不能通过重命名标准、修改证据要求或削弱完成条件变相降低要求。新版本还需与当前执行状态核对：已有节点、输入、提交和评审的对应关系必须明确，仍承担交付或返工责任的原 Session 必须保留，不能以新建实例加载快照代替。Compiler 检查新旧定义的差异和静态约束，主控流程与 Runtime 负责实际的切换条件、状态接续和有效性判定；新图编译通过不等于可以立即切换。

无法确定合法接续方式时保持阻塞，不覆盖旧基线、不复用已失效的批准，也不强行迁移运行状态。若问题需要修改任务依据、适用规范或验收标准，应留待后续 Run 重新设计，当前 Run 不因此获得豁免。旧定义、编译报告、变更依据及运行记录均保留，为后续分析提供证据，不自动回写公共资产。

# 第 8 章　图执行、质量评审与正常返工机制

## 8.1 Run、节点及作业轮次的状态模型

Runtime 接收第 7 章已经登记并冻结的执行基线，按其中的节点有效配置、依赖与输入绑定、评审及返工关系、完成条件推进工作。运行中只产生状态、提交和评审记录，不重新解释任务来补图，也不改变员工绑定或准出标准。Agent 负责专业工作，Runtime 负责判断结果是否可以被登记，以及登记后允许发生什么流转。[^1]

运行状态分为以下三个层次，不能用一个笼统的“进行中／完成”同时表达。

| 对象 | 核心记录 | 状态含义 |
|---|---|---|
| Run | `run_id`、当前执行基线、所在阶段及总体状态 | 区分规范选择、设计、编译与执行阶段，以及运行中、阻塞和最终成功或失败；正常返工仍属于执行过程。 |
| 节点运行实例 | `run_id + node_id`、节点类型、绑定员工、原 Session 及当前轮次 | 执行节点区分等待准入、就绪、执行中、提交待审与待返工；评审节点区分等待评审对象、就绪、评审中和结果已登记。阻塞或故障另记原因。 |
| 作业轮次 | Runtime 分配的 `round_id`、输入快照或评审对象集合、提交及结果引用 | 区分同一节点的初次工作、返工后的再次执行和复审；旧轮次保留，不被新结果覆盖。 |

每个节点同一时间只能有一个正在执行的轮次。执行轮次绑定确切的输入版本，评审轮次绑定确切的提交集合与标准引用；同一轮可以包含多次模型响应和工具调用，技术请求重发不自动产生新作业轮次。返工或复审沿用原节点和原 Session，不把新轮次实现为新的 Agent 实例。

**节点工作状态与产物准出资格分别记录。** 执行者提交了一份产物，不表示产物已经批准；某个 Gate 已通过，也不表示所有下游都可以使用。准出记录关联具体 Gate、提交版本及评审依据，Runtime 按各下游输入声明的条件计算使用资格，不用节点上的一个“已完成”标志代替所有批准关系。局部准出也不代表后续综合评审责任已经解除。

## 8.2 节点准入、调度与并行 Fan-out／Fan-in

Runtime 根据编译后的依赖索引维护可调度节点。基线激活、输入就绪、提交登记、评审结果登记和版本失效等事件发生后，重新检查受影响节点的准入条件。首次工作通过 Pi 适配层创建该节点的 Session；已有 Session 的后续工作继续使用原实例。重复事件或启动指令不得重复创建节点实例、重复派发同一轮工作。

**准入不仅检查材料存在，还检查材料是否获准用于本次工作。** 执行节点的必需输入必须可读取，并满足相应的版本有效性、前置作业和 Gate 条件；评审节点则读取正式登记的待评审提交，不能被要求先取得自己的批准。综合 Gate 需要哪些前序评审，由基线明确，不由 Runtime 临时追加。

调度前，Runtime 将本轮输入解析为确定版本的快照，记录所消费的提交及准出依据，再向 Session 交付节点契约和结构化交接信息。一次工作期间不自动追随上游的“最新文件”。启动检查与轮次占用需要在同一受控状态变更中完成；输入随后发生失效时，按第 8.5 节处理，不能因为节点已经启动就继续把旧输入视为有效。

多个节点各自满足条件后可以并行执行，形成 Fan-out。Fan-in 按基线等待**全部必需输入及其声明的准出条件**满足，不以分支 Agent 停止输出、已提交文件或部分成果通过代替汇聚。控制关系由引擎处理，不额外创建负责分派或汇总状态的管理 Agent；需要整合内容时，由工作流中已有的专业执行节点承担。

某一分支返工时，只暂停依赖受影响成果的工作，其他独立分支继续推进。并行节点按编译后的工作区与权限安排执行，不默认共享可变输出。等待一个仍在正常生产或评审的上游属于依赖等待；必要条件确实无法满足时才记录具体阻塞。部分节点阻塞而其他节点仍可推进时，不把整个 Run 误报为已经停止；不存在合法推进路径时，再向主控流程报告，处理边界见第 11 章。

## 8.3 正式提交、提交检查与 Gate 启动

执行者通过受控提交入口交付产物清单和证据，而不是直接写入“节点完成”状态。Runtime 将提交关联到当前 Run、执行基线、节点、Session、轮次及输入快照，并检查调用归属和轮次是否仍然有效。一次响应结束、工作区内出现文件或 Agent 自述完成，均不触发下游准出。

提交检查确认必需输出是否齐全、文件或内容是否可读取、格式是否符合已声明 Schema、引用与写入范围是否合法，以及证据是否关联到相应产物或标准。**这些检查证明提交符合接收契约，不证明专业内容正确。** 内容真实性、充分性和复杂质量要求仍由相应 Gate 判断；可定位的证据引用不能被当作证据已经有效的结论。[^2]

结构不合法或必需项缺失时，检查结果返回原执行 Session 补齐，不启动 Gate，也不将其计为一次独立评审打回。检查通过后，登记不可变的 `submission_id`、产物版本及证据清单，返回提交回执。相同提交操作重复到达时返回已登记结果，不重复生成版本；已登记内容不得原地覆盖，后续修订形成新提交。具体存储与版本机制在第 10 章定义。

正式提交使相关 Gate 获得候选评审对象。Runtime 根据基线核对其全部输入条件，组成包含明确提交版本、固定标准和证据引用的评审包，登记新的评审轮次后启动或继续原评审 Session。单个 Gate 可以检查多个节点的成果，但其本轮对象是一组固定提交，不是在评审过程中不断变化的文件集合。

执行者进入等待评审，不持续产生未经调度的新提交，也不继续修改已经登记的内容。评审者只形成结构化结论，不直接修复被评审产物；评审结果同样通过受控入口接受检查和登记。

## 8.4 评审准出、打回原执行者、修订与复审

评审结果应明确本轮对象、逐项标准结论、对应证据和问题位置。需要返工时，还应说明涉及的执行节点及修订要求；修订要求必须用于满足既定标准，不能以新偏好、新阈值或临时增加的交付要求改变验收。评审不预设必须找出若干问题，也不因返工次数增加而强制通过。[^3]

Runtime 接收结果时，核对评审身份、轮次、提交集合及其当前有效性，检查必需标准是否有对应结论、返工目标是否属于预先允许的执行节点，以及决定与逐项结果是否存在结构性冲突。无效交付返回原评审 Session 修订，不直接触发放行或返工。上述校验不代替评审者对专业质量的判断。

**准出。** Runtime 为本轮确切提交集合登记该 Gate 的有效批准，并重新计算依赖它的节点是否就绪。下游消费的仍是执行节点的获准产物，Gate 结果提供批准依据。同一产物被不同下游使用时，分别满足各自配置的必需 Gate，不能要求其先通过尚依赖这些下游工作的后续综合评审，也不能凭一个局部批准绕过其他已声明条件。

**返工。** Runtime 登记问题、标准与证据引用，并按既定关系建立返工任务，先处理受影响提交的使用资格，再把反馈交给原执行 Session。原执行者在新轮次中修订，重新提交后，由关联 Gate 对新版本复审。节点、员工和标准不变，正常返工不触发重新编译，不计为技术失败，也不调用设计师临时改图。

多个反馈涉及同一执行节点时，由 Runtime 统一登记并按轮次组织处理，不并发唤起同一个 Session。执行者收到必要的问题与证据、当前有效输入和原节点契约，而不是评审者的完整会话。能够通过既定工作补交的证据缺项属于返工；必要事实无法取得、问题不属于合法返工范围或既定流程无法继续时，报告具体阻塞或显式 replan 请求，不擅自扩大回退范围。

首版采用保守的会话保留策略：已创建的任务节点 Session 保留到 Run 收口，不因一次局部评审通过而提前销毁；等待期间不持续调用模型。后续 Gate 再次退回时，仍由原实例继续承担工作。Session 真正丢失属于运行时故障，不能用新实例读取快照冒充连续返工，具体生命周期与故障处理分别见第 9、11 章。

## 8.5 跨节点返工对依赖和已批准产物的影响

后续 Gate 退回较早节点时，不能只把该节点重新标为“执行中”，同时让下游继续使用原批准。Runtime 必须同时处理**原提交、实际消费它的成果以及依赖这些成果的评审结论**。失效表示这些记录不再具备本轮继续使用或收口的资格，不表示删除历史，也不等于已经证明每项下游内容都错误。

Runtime 先核对返工目标与被评审成果的来源关系，再依据编译后的反向依赖索引及运行中记录的实际输入版本，确定受影响范围。原提交和依赖它形成的下游提交失去当前使用资格，相应 Gate 批准不再满足准入或完成条件；综合评审依赖的提交组合变化后，其结论同样需要重新取得。未消费失效版本、也不依赖相关准出条件的独立分支不重跑。

**先阻止旧成果继续流转，再安排返工。** 对尚未启动的受影响节点，撤回就绪资格并等待新输入；对正在执行的节点，标记当前轮次失效，通过适配层在安全边界停止继续推进。同一 Session 尚未结束旧轮次的活动时，不启动新轮次；停止请求尚未完成期间到达的工具回执、产物或评审结果可以留作记录，但不得推进当前流程。输入有效性不仅在调度时检查，也在提交和评审结果登记时再次检查，避免迟到的旧结果重新放行下游。

对已经提交或局部准出的下游工作，保留原记录并标明失效原因。待替代输入重新满足准入条件后，将版本变化和必要反馈送回其原 Session，由它重新确认或修订成果并形成新提交。即使最终内容未变，也要记录基于新输入的提交关系并重新通过所需 Gate，不能把旧批准直接迁移到新版本。评审节点同样复用原 Session，对新的确切对象集合开展复审。

例如，A、B 分别通过局部 Gate 后供 C 整合，C 的 Gate 允许退回 A。打回 A 后，A 由原 Session 修订并重新通过局部评审；C 基于新版 A 与仍然有效的 B 再次提交，随后重新评审 C。B 及其独立批准不受影响。该过程改变的是提交版本和有效性，而不是工作流拓扑，也不需要新建执行员工。

首版不自动判断“上游只改了一点，所以旧批准可以复用”，以明确的版本依赖完成失效与复审。业务产物失效也不等于已经撤销外部操作的副作用；已发生的对外操作不能靠回退节点状态假装消失，相关防重与故障处置在第 11 章规定。

## 8.6 最终准出与任务收口

Runtime 在提交、评审及状态变化后重新检查工作流的完成条件。成功收口要求最终交付均有确切且仍有效的提交版本，所需 Gate 批准对应同一组有效对象，必要作业与依赖已经闭合，且不存在会影响最终交付有效性的未处理返工、阻塞或在途工作。最终 Gate 本身通过，也不能替代对这些整体条件的检查。

**收口由 Runtime 完成，不由任何节点直接宣布。** Runtime 在同一一致性边界内核对当前基线和相关版本，登记最终产物清单、Run 成功终态及结果事件，并停止继续派发。重复触发完成检查不重复执行节点或生成另一份独立结果；对外通知未送达时重试结果交付，不重新运行已经完成的工作。状态持久化和对外接口分别在第 10、12 章展开。

确认运行终态并完成必要记录后，释放不再承担工作的节点 Session。外部 Agent 调用结束、页面关闭或状态订阅断开，不触发收口，也不提前释放仍承担返工责任的实例。对外结果包含最终产物引用和必要的完成依据，完整的中间提交、评审及返工记录保留用于追溯，不回灌到外部会话中。

必要条件无法满足时，如实保留阻塞或按第 11 章进入相应失败处理，不把已有的部分成果包装为全部完成。正常返工持续发生并不自动构成技术故障，更不能据此删除 Gate、降低标准或强制通过。本章确定正常执行的推进与收口语义；运行状态、等待原因和返工进度均由实际登记的事件派生，供后续统一对外展示。

# 第 9 章　Pi Agent 适配与 Session、上下文管理

## 9.1 Pi 接入边界与实现代码基线

Pi 适配层负责把第 7 章的节点有效配置转化为实际 Session，向其交付任务，并将执行事件返回 Runtime。它不选择员工、不解释流程规范，也不决定节点准出或下游调度。图引擎通过适配层使用 Pi，避免业务控制逻辑直接依赖 Pi 的内部对象与会话文件布局。

以接入时 Pi 主分支的确定提交作为开发基线，记录 Pi 与适配层版本；升级后重新验证创建、续接、停止、上下文管理和工具权限，不让运行中的实例自动跟随最新版。本章定义项目侧的适配要求，具体 Pi 接口及支持范围需在接入该提交时核验，不将尚未核验的能力视为已经实现。

## 9.2 从节点有效配置创建 Pi Agent Session

Runtime 首次调度节点时，将冻结基线中的模型、角色提示词、节点契约、能力授权、工作区配置及本轮输入交给适配层。适配层据此创建 Session，登记 `run_id + node_id → session_id` 的绑定；后续 `round_id` 均沿用该实例，不重新解析资产或选择员工。同一员工资产被多个节点使用时，各节点仍具有独立 Session。

适配层提供以下四类能力，具体接口名称在工程附录中确定。

| 能力 | 适配责任 |
|---|---|
| 创建与绑定 | 按有效配置创建实例并登记存活对象；重复请求不得重复创建，原实例丢失不得静默重建。 |
| 派发与停止 | 向原 Session 交付首次任务、返工或复审输入；停止当前轮次时保留 Session，并确认其活动已结束。 |
| 事件回传 | 为模型响应、工具调用结果及故障关联节点和轮次；提交与评审结果经受控入口交给 Runtime 校验登记。 |
| 释放 | 仅按 Runtime 或主控流程指令释放实例，不以一次响应结束或局部过审作为销毁条件。 |

ST 与工作流架构设计师使用主控流程预置的员工及能力配置，经同一适配边界运行，不依赖尚未生成的任务工作流；本章不另行固定 ST 的内部组织形式。

## 9.3 Session 生命周期与返工连续性

**首版已创建的任务节点 Session 保留到 Run 收口。** 执行、提交待审、局部准出、等待上游和返工是同一实例的不同工作阶段；等待期间不持续调用模型。编译修订和显式 replan 同样返回原工作流架构设计师 Session，因此设计师实例也需保留到本轮不再可能需要修订为止。

同一 Session 同时只执行一个作业轮次。输入失效或需要中止当前工作时，Runtime 先撤销旧轮次的有效性，适配层停止继续执行，并等待模型与工具活动结束或得到明确处置，再交付新轮次。停止当前工作不等于销毁 Session；期间到达的旧回执仍关联旧轮次，不能推动新轮次准出。具体状态迁移沿用第 8 章，不在 Pi 内维护第二套工作流状态。

Run 终态及必要记录登记完成、在途工作处理完毕后，统一解除绑定并释放实例。会话文件和检查点用于追溯与状态管理，不能以新实例加载记录代替原 Session 返工；原实例确实丢失时报告运行时故障，处理归第 11 章。

## 9.4 节点上下文构造与结构化交接

上下文区分稳定职责、本轮工作输入和按需材料，避免把全部资产及上游对话堆入提示词。[^1] 稳定部分采用 Compiler 固定的系统规则、员工职责和节点契约；本轮输入由 Runtime 解析，包含必要的用户要求、输入版本、待确认事实，以及当前提交或返工信息。Skill、知识内容和详细产物通过授权引用按需读取。

**执行节点取得满足准入条件的输入，评审节点取得确定版本的待审提交。** 返工包包含标准引用、问题与证据位置、需要处理的提交及输入变化，不传递评审者的完整聊天。复审时明确新的提交集合，旧意见只能作为参考，不能代替对新版本的检查。节点之间的交接采用结构化包和产物引用，而不是合并 Session 历史。[^2]

长程执行需要整理历史时，只在原 Session 内使用经接入验证的压缩方式，不以重建或切换会话替代。当前节点契约、固定标准、有效输入和未解决问题必须能够重新取得；原始产物与证据仍可按引用读取。压缩摘要不覆盖正式记录，也不能把待确认事实写成已确认结论。

## 9.5 工具、数据访问与工作区约束

**能力按冻结配置加载，权限在实际调用时检查。** 适配层只暴露已授权的工具及受控提交入口；Skill 或工具检索不得扩大授权范围。未纳入基线的个人配置、提示词、插件或自动发现资源不得混入节点环境，凭据由运行环境提供，不进入任务提示词。

工具调用的 Run、节点和轮次归属来自可信绑定，不依赖 Agent 自填身份。执行者只能操作授权工作区并提交成果；评审者只读被评审的产物与证据，在自己的范围内生成评审结果。公共资产、冻结配置和运行状态不向节点开放直接修改权限，状态迁移仍由 Runtime 完成。[^3]

并行节点使用隔离的可写工作区，跨节点消费通过确定版本的产物引用完成，不能直接覆盖其他节点的工作文件。隔离必须落实到工具或执行环境；仅设置工作目录或在提示词中限制路径，不能约束具备任意代码执行能力的工具。无法满足绑定权限的工具接入不得启用，不能把未实施的限制当作已生效。产物存储及正式提交区的管理在第 10 章展开。

# 第 10 章　运行数据、产物与证据管理

## 10.1 运行状态与事件记录的唯一事实源

运行数据从 `create_run` 开始登记，覆盖 TaskInput、ProcessSelection、配置与执行基线、节点轮次、提交、评审和最终结果。**元数据由统一的事务存储管理，原始材料、产物和证据内容由受控文件存储保存。** 主控流程与 Runtime 经受控入口更新记录；Agent 工作区、Pi 会话文件和对外展示不另行维护流程状态。[^1]

状态变更与对应事件在同一元数据事务内提交。事件记录 Run 内的顺序、变更原因、相关对象及版本；节点事件还关联 `node_id` 和 `round_id`。并行更新检查当前轮次与记录版本，不能以迟到结果覆盖新状态。事件只追加，不回改历史；查询视图与检查点从已提交记录生成，不形成第二份独立真相。事件回放可以重建展示，不能直接重发已经执行过的模型或工具操作。

## 10.2 产物清单、提交版本与正式登记

**工作区文件是可修改的草稿，正式提交是确定版本的交付记录。** `submission_id` 标识一次提交，其中可以包含多项产物和证据；各产物通过节点输出标识对应第 5 章的交付契约。正式记录保留以下关联，完整字段放入工程附录。

| 记录内容 | 必需关联 |
|---|---|
| 提交归属 | Run、执行基线、`node_id`、`round_id`、可信 Session 绑定及 `submission_id`。 |
| 产物清单 | 输出标识、媒体类型或 Schema、不可变内容引用和内容摘要（哈希）。 |
| 生产依据 | 本轮输入快照、实际消费的提交版本及相应准出依据。 |
| 证据清单 | 支持的产物或 `criterion_id`、来源与具体位置、可读取的证据对象引用。 |

接收提交时，先冻结待提交内容或取得一致的副本，在该副本上完成接收检查、计算摘要并封存，再通过元数据事务登记提交、清单和事件，返回回执。文件尚未就绪不得登记成功；文件已保存但登记失败时，不将其视为正式提交，也不启动 Gate。不得用指向可变工作文件的引用代替封存内容。

相同提交操作重复到达时返回原回执，不重复生成版本。修订形成新提交，旧内容不覆盖。**内容相同不代表提交相同：** 基于新输入重新确认的成果仍需新提交及新的生产依据，不能凭哈希相同继承旧批准。提交内容保持不变，其当前使用资格由独立的准出、失效记录表达。

## 10.3 要求、证据与评审结果的追溯

TaskInput 中的原始消息和可保存附件保留原文或不可变副本，并记录来源位置。动态检索材料记录实际取得的内容、来源、取得时间及必要查询条件，不能只保存一个可能变化的网页地址或知识库名称。无法留存完整原文时，明确已保存范围与可验证边界，不宣称已经冻结全部来源。待确认事实的调查结果另行关联证据，不覆盖原始任务输入。

追溯关系沿用工作流定义中的要求引用、输出标识和 `criterion_id`，再连接实际输入、提交、证据及评审记录。证据需要定位到具体文件段落、结构化字段或工具回执；验证结果应关联被检查的提交及必要执行条件，不能用针对旧版本的报告证明新版本合格。摘要用于检索和交接，不替代原始材料；证据可定位也不等于其内容足以支持结论。[^2]

每次评审保存评审节点与轮次、固定的提交集合、标准引用、逐项结论、证据和返工要求。批准与后续失效分别登记：上游返工导致旧批准失去当前效力时，保留原评审结论，追加失效原因及关联对象，不把历史的“当时通过”改写成“当时失败”。第 8 章据这些版本关联计算影响范围，本章不另设一套失效规则。

## 10.4 并行工作区隔离与产物整合

每个节点使用独立的可写工作区，正式产物区、原始材料和冻结配置不向节点开放修改权限。Runtime 按本轮输入快照提供只读引用或副本；跨节点读取不通过共享的“最新文件”路径完成。评审者需要运行检查或生成报告时，在自己的工作区处理，结果仍关联原待审版本，不修改被评审提交。

多个分支需要形成共同产物时，由配置中承担整合职责的执行节点读取各分支满足准入条件的确定版本，在自身工作区整合并正式提交。存储层不替代专业判断自动解决内容冲突，也不将多个分支的最后写入结果拼成一份交付。工作区位置与文件引用不能代替访问授权，实际权限沿用第 9 章的适配约束。

## 10.5 持久化、检查点与存活 Session 的关系

检查点保存某个一致性位置上的执行基线、状态版本、事件位置、节点轮次、有效输入、提交与评审引用、Session 绑定及未完成操作记录。大文件继续引用已封存对象，不必在每个检查点重复复制。保存或导出时应覆盖完整的元数据状态与被引用内容，不能用彼此不同步的状态文件和产物目录拼出检查点。

**检查点保存运行事实，不保存仍然存活的 Agent 实例。** `session_id`、会话文件或状态快照不能证明原 Session 仍存在；重新接续调度前必须通过适配层核对实例及在途工作。原实例丢失时报告运行时故障，不以新实例读取记录代替原实例返工，也不根据状态回退假定外部操作已经撤销。具体故障处理归第 11 章。[^3]

Run 收口时，最终产物清单、终态与结果事件按第 8 章的一致性边界登记；对外只提供仍有效的确切提交及完成依据。中间提交、失效原因、评审与返工记录保留供追溯和后续优化，不自动改写本轮标准或公共资产。运行中的引用对象不得被清理；临时文件清理不能影响正式记录及其证据链。

# 第 11 章　业务阻塞与运行时故障处理

## 11.1 正常返工、业务阻塞、设计问题与技术故障的责任划分

**评审打回属于正常作业，不是异常重试。** 系统按问题性质决定处理方式，不把所有未完成情况统一转成“再次调用 Agent”。以下划分覆盖规范选择、工作流设计、编译和任务执行。[^1]

| 类型 | 典型情况 | 处理责任 |
|---|---|---|
| 正常作业修订 | 质量未过审、可补齐的证据缺项、提交格式不合法。 | Runtime 返回原执行或评审 Session，按第 8 章补交、返工或复审。 |
| 设计校验问题 | ST 交付无效、配置结构或引用不合法。 | 主控流程返回原 ST 或设计师修订，不作为技术故障重试，不启动部分任务图。 |
| 业务或设计阻塞 | 无适用规范、必要事实无法取得、要求冲突、缺少必需资产或流程能力。 | 登记缺失条件和影响范围；在既定工作、合法 replan 或后续 Run 的边界内处理。 |
| 运行时技术故障 | 模型或工具连接失败、存储不可用、Session 丢失。 | 由主控流程、Runtime 与 Pi 适配层负责检测、安全重试或失败收口。 |

分类依据是实际原因，不是工具退出码。例如，测试正常执行但发现产物不合格，应作为质量证据；测试工具本身无法启动才是技术问题。正常依赖等待也不是阻塞：上游仍在执行或评审时，下游等待即可，不因此重复派发。

## 11.2 输入无法满足与流程无法继续的处理

节点报告阻塞时，应指明所在阶段、节点与轮次、涉及的要求或输入、已取得的证据，以及缺少什么条件才能继续。Agent 只提交事实和处理请求，由主控流程或 Runtime 登记状态。能够在原职责与权限内调查、补交或返工的事项，继续走既定工作，不额外创建“异常处理 Agent”。

**阻塞范围按依赖传播，不默认暂停整个 Run。** 无关分支仍可推进；全部可推进工作结束后仍缺少必要条件，Run 才体现为整体阻塞。阻塞解除必须依据新取得的有效输入或已确认恢复的条件，重新检查准入、输入版本和原 Session，不因 Agent 宣布“已解决”直接放行。

既定流程无法处理的问题，按第 7.5 节登记显式 replan 请求，交回原设计师；当前基线不原地修改。涉及任务依据、所选规范或冻结验收标准的变更，留待后续 Run。首版不引入 HITL、不补造前提，也不靠切换默认规范或降低标准解除阻塞；没有合法继续条件时，如实保留原因和已有成果。

## 11.3 运行故障检测与技术重试

技术故障由适配层和工具回执报告，关联 Run、节点、轮次及具体操作。没有进度文字不等于执行失效，连接中断也不等于 Session 已销毁；Runtime 应核对实例存活状态、当前请求与在途工具活动，不能仅凭会话年龄重新派发。

**仅对已确认可以安全重复的失败操作进行有限退避重试。** 模型请求或读取操作发生瞬时故障时，先检查是否已经取得有效结果、是否触发工具，以及旧请求是否仍在活动，再决定是否重发。技术重试沿用原 Session 和当前轮次，不重跑整个节点，不重复已完成的工具步骤；无法判定执行结果时先核对，不盲目重试。

请求超时与技术重试上限由引擎运行配置管理，不写入每份工作流，也不作为任务时间预算或质量返工次数限制。认证、权限或配置错误不能靠无限重试解决，更不能通过扩大授权、替换员工或变更冻结模型配置绕过。安全重试仍无法完成时，登记运行故障及影响范围；可恢复但条件未满足时保持阻塞，已确认无法完成必需工作时进入失败收口。[^1]

## 11.4 重复操作防护与状态一致性

可能重发的操作使用稳定操作标识，并按所在阶段关联 Run、基线、节点、轮次和请求内容。重复的提交、评审登记或启动请求返回已登记结果，不再生成版本或创建实例；同一标识携带不同内容时拒绝处理。返工形成的新轮次和新提交使用新的操作标识，不能被误判为旧请求重发。

状态与事件按第 10 章在同一事务内登记。元数据存储不可写时，暂停依赖状态提交的派发与准出，不以工作区文件或会话自述代替登记；恢复后先查询操作是否已提交，再决定补做。接收结果时重新核对基线、轮次及输入有效性，迟到回执只留记录，不推进已失效的工作。存储中的防重记录不能单独保证外部操作只发生一次。

**对外写入超时，可能意味着结果未知，而非操作未发生。** 工具接入应声明是否可安全重复、是否支持外部幂等标识或结果查询；能够核对时先核对，不能确认时阻塞相关工作并记录未决副作用，不自动重发。既有外部操作不会因产物失效、节点回退或 Run 失败而被撤销；首版不引入通用自动补偿机制，也不能凭修改本地状态声称已回滚。[^2]

## 11.5 Session 丢失与故障收口边界

控制连接暂时断开，但能够核验原 Session 仍存活、绑定一致且在途操作可核对时，允许重新连接并接续调度；这不等于重新创建实例。无法确认实例或操作状态时，先暂停该节点推进，不并行建立替代 Session。控制进程重启后的接续同样遵守这些条件，不能仅凭检查点中的 `session_id` 判定可恢复。

**仍承担交付、评审或设计修订责任的原 Session 确认丢失后，不以新实例加载会话文件或快照续跑。** 按第 9、10 章记录不可恢复的连续性故障；因此无法完成必需工作的 Run 进入失败收口。是否能够重新连接原存活实例，取决于接入时核验的 Pi 与部署能力，不预设首版具备跨进程恢复保证。

失败收口由主控流程与 Runtime 完成：停止新派发、撤销在途轮次的推进资格，登记故障、影响范围、已有成果及未决操作，在安全处理在途活动后释放存活 Session。无法确认完成或撤销的外部操作仍标为未决，不写成已取消。已有提交与评审历史保留，但部分成果不能包装为整体成功；成功收口后的通知失败只重试结果交付，不重新执行任务。

# 第 12 章　对外接口、执行进度与可观测性

## 12.1 创建、查询、订阅与结果获取接口

对外接口由图引擎提供，IPD Tool 只封装任务创建入口。外部 Agent 与用户界面通过同一组接口了解执行情况，不读取 Pi 会话文件来推断进度，也不承担内部调度。首版接口围绕以下四类能力组织，名称为项目侧约定，完整参数与传输协议放入工程附录。

| 接口 | 输入与返回 | 行为边界 |
|---|---|---|
| `create_run` | 接收 TaskInput 与请求标识，返回 `run_id` 和受理状态。 | 完成输入检查与登记后启动主控流程，不等待最终交付。 |
| `get_run` | 按 `run_id` 返回阶段、总体状态、当前基线、节点概况、等待原因及事件位置。 | 返回一致的已登记状态，不触发继续执行或重新派发。 |
| `read_events`／`subscribe_events` | 按 Run 和事件游标读取或订阅后续事件。 | 用于增量观察；断开订阅不取消 Run。 |
| `get_result` | 返回当前状态；成功时提供最终交付清单与完成依据，失败时提供原因及可访问的部分成果。 | 未收口时不返回成功结果，部分成果明确标注，不等同于完整交付。 |

创建请求按调用方和请求标识防重：相同内容重发返回原 Run，标识相同而内容不同则拒绝。网络超时后应核对原请求，不能直接用新标识重复创建任务。查询、订阅和结果读取不提供任意改状态、跳过 Gate 或修改标准的入口；首版不在这些接口中夹带人工审批和流程干预功能。

## 12.2 主控阶段与任务执行状态的统一暴露

**从任务受理开始即可查询，不必等待工作流生成。** 状态沿用第 8 章的分层：Run 表达规范选择、设计、编译、执行及总体状态；节点表达当前工作与轮次；提交和评审记录表达产物使用资格。设计阶段尚未生成节点时，不虚构节点进度；显式 replan 期间区分当前有效基线和候选版本，不提前将候选图显示为已执行图。

状态快照与事件位置从同一一致性视图取得。客户端先读取快照，再从其事件位置之后订阅；重连时按游标补读，重复事件按标识去重，并依据 Run 内事件顺序更新视图，不以本地接收时间排序。事件读取与投递可以重复，但不能因此重复执行节点。底层状态与事件仍遵循第 10 章的事务记录，不为展示另建一套事实源。

读取失败或连接断开只表示暂时无法取得最新状态，不能推断 Run 已失败或停止。界面保留旧信息时，应标明最后更新时间和同步状态；恢复后重新核对快照与事件位置。

## 12.3 节点活动、评审进度与等待原因

进度由正式提交、评审登记、轮次变化和失效事件派生，Agent 的工作说明仅作为补充。[^1] 展示应回答：哪些节点正在工作或评审，哪些交付等待准出，哪些节点正在返工，以及等待的是哪个输入、提交版本或 Gate。正常依赖等待、正常返工、业务阻塞和技术故障分别呈现；部分分支阻塞而其他分支仍可推进时，不将整个 Run 显示为停滞。

**当前有效进度与历史完成记录分开。** 上游返工导致旧提交或批准失效时，当前视图随之撤回相应准出资格，历史评审仍保留。产物是否可供某个下游使用，按该输入要求的 Gate 和版本判断，不能将一次局部通过显示为全部验收完成。

首版以阶段、节点状态和已准出交付清单为主要进度，不强行计算总百分比或预计完成时间。展示计数时说明对象及当前基线，例如“满足全部所需批准的最终交付项数”；节点数量不代表工作量，返工后的有效计数也不保证单调增长。

## 12.4 面向用户与外部 Agent 的结果视图

两类视图共用运行事实，只调整信息粒度。用户视图优先呈现当前阶段、主要活动、明确阻塞和可取得的成果；外部 Agent 取得结构化的状态、对象标识、原因及产物引用，需要时再读取节点和评审详情。首版提供最小状态展示，不要求建设复杂看板，也不将内部完整会话回灌给外部 Agent。

成功结果读取第 8、10 章已经登记的最终清单，绑定确切提交及有效完成依据；摘要只能解释这些记录，不能自行增加“已完成”的判断。最终通知未送达时，仅重试通知或读取原结果，不重新执行任务；通知状态与 Run 成功状态分开记录。

创建、查询、订阅及产物读取均检查调用方权限，`run_id` 和文件引用不是访问授权。外部可读取哪些材料、产物与诊断，由接入权限决定；结果引用通过受控读取入口解析，不默认暴露服务器路径、凭据或其他节点的私有工作内容。

## 12.5 决策依据、故障记录与运行指标

可观测记录保存规范选择依据、编译诊断、评审结论、返工原因和故障处置，并关联相应任务要求、标准、提交与证据位置。节点相关记录携带 Run、执行基线、`node_id`、`round_id` 及必要操作标识，便于从外部状态定位真实记录。保存可核对的决策摘要与依据，不以模型内部思考文本或全量聊天替代审计信息。[^1]

首版采集各阶段耗时、模型与工具调用量、可取得的 Token 用量、配置修订、提交补正、评审返工及技术重试次数。后三类修订与重试分别统计，不混成一个失败率；统计覆盖 ST、设计师和执行、评审节点，不能遗漏组织流程本身的开销。指标采集不构成 Token／时间预算控制；缺失的用量标为未取得，不能按零计算。

日志对凭据、敏感参数及无关内容做过滤，详细产物和证据继续按受控引用保存。运行指标用于第 13 章的验证与定位，不直接回写员工资产、流程规范或本轮验收标准。[^2]

# 第 13 章　首版实施路径与验证方案

## 13.1 实现顺序与集成里程碑

首版按“契约与资产 → Pi 接入 → 受控执行 → 自动设计 → 端到端验证”推进，先验证确定性的控制机制，再让设计师生成真实工作流。以下是实现顺序，不是功能删减；并行、Fan-out／Fan-in、独立 Gate 和原 Session 返工均属于首版验收范围。

| 里程碑 | 主要交付与通过条件 |
|---|---|
| M1：契约与启动资产 | 固定核心 Schema、标识和交接协议；登记项目手写规范、必要 AgentCard、节点模板及设计 Skill 骨架，准备合法与非法配置样例。 |
| M2：Pi 适配验证 | 绑定确定提交，验证创建、续接、停止当前轮次、释放、工具权限和上下文管理；确认等待评审后能够回到原存活实例。 |
| M3：编译与受控执行 | 用人工编写的测试配置打通 Compiler、Runtime、提交存储及状态事件，验证独立评审、局部返工和并行汇聚。 |
| M4：自动设计与任务入口 | 接入 ST、Project Shepherd 设计师、增量构建工具及共享校验规则，打通 `create_run` 到冻结基线的自动链路。 |
| M5：完整集成与评测 | 完成对外查询、订阅、结果读取、跨节点返工和故障测试，以真实 Pi Session 运行完整任务并开展单 Agent 对照。 |

M3 的人工配置用于隔离调度问题，不代替 M4 的自动设计验收。实现中可以使用可控执行桩验证状态机，但最终必须以真实 Session 验证生命周期和实际权限。首版手写规范仍是项目自定义启动资产，不能将联调成功解释为已经符合华为内部正式规范。

## 13.2 规范选择、增量配置构建与编译验证

**选择与设计验证。** 使用适用任务、无适用规范、输入缺失和要求冲突等样例，检查 ST 是否忠实保留任务依据、绑定完整规范版本，并正确交付或报告阻塞。仅有一份规范时也要验证不匹配路径。设计师必须通过构建工具完成节点配置、员工绑定、关系闭合及正式提交，不能由测试人员在导出后手工补齐配置再计为自动设计成功。

**编辑与校验验证。** 覆盖草稿分步保存、旧修订写入、重复操作、引用缺失、局部通过但整图不合法，以及正式编译返回诊断后的原 Session 修订。构造缺少必要 Gate、绕过准出、非法前向环、越权工具、无效资产版本和不支持的强制规则，确认均不能形成可激活基线。合法样例应完成资产解析和编译；未完成检查不得误报通过。

检查依据为保存的任务与规范引用、草稿操作记录、确切配置文件、编译报告和基线内容，不使用设计师自述代替。结构通过与语义设计质量分别记录：要求覆盖和标准是否充分，仍需对照原始任务核查，不能仅检查 JSON 合法。

## 13.3 并行、返工、会话连续性与故障测试

运行机制先用可复现用例验证，再通过真实任务联调。核心验收覆盖如下。

| 测试范围 | 必须观察到的结果 |
|---|---|
| 并行与汇聚 | 独立节点实际并行，工作区互不覆盖；Fan-in 等待全部必需输入及批准，未准出的分支不能放行汇聚工作。 |
| 正常返工与复审 | 打回后回到原执行 Session，新提交由原评审 Session 复审；节点、员工和标准不变，不因多轮返工强制通过。 |
| 跨节点失效 | 上游返工使实际依赖它的提交及批准失效；无关分支保留，迟到结果不能恢复旧批准，同一 Session 不并发执行新旧轮次。 |
| 技术重试与副作用 | 可安全重复的失败操作按规则重试，重复登记不重复创建实例或提交；对外操作结果未知时先核对，无法确认则阻塞，不能盲目重发。 |
| Session 连续性 | 等待和局部准出后实例仍存活；原实例确认丢失时按第 11 章处理，不加载快照创建替代者并冒充恢复成功。 |
| 冻结与显式 replan | 普通编辑不能修改冻结基线；合法新版本重新校验，切换保留原责任实例；改变任务依据或验收标准的请求不能在本 Run 生效。 |
| 状态与收口 | 查询快照与事件对应，重连不漏事实，重复投递不重复执行；失效成果不能进入最终清单，成功后的通知失败不触发任务重跑。 |

故障注入覆盖模型或工具中断、登记回执丢失、存储不可写和原 Session 丢失。断连后能否重接原实例，只按第 9 章实际核验的能力测试，不宣称具备未实现的跨进程恢复。每项结果关联事件、提交和实例核验记录；受控的缺陷注入用于验证闭环，不作为真实质量提升的证据。

## 13.4 产物质量与协作机制的评价

首版评价仍分两个维度。**产物质量**检查原始要求满足程度、事实或功能正确性、完整性及交付可用性。任务评价方法在实验前确定，并独立于本轮 Gate 的自评结论；“所有 Gate 通过”只能证明流程获得了批准，不能单独证明最终产物正确。[^1]

**机制有效性**检查规则是否真正执行，统计自动设计可执行率、完整任务成功率、Gate 发现的有效问题与误报、返工范围、上下文交接缺项，以及各阶段耗时、调用和 Token 用量。缺少独立缺陷核对时，不报告无依据的缺陷发现率。故障用例按“可安全恢复、应阻塞、应失败”分别核对，不追求所有故障都恢复成功。

绕过 Gate、重复副作用、失效成果准出、隐式改标准和原 Session 被替换，属于机制验收的不允许行为，不能用最终产物较好抵消。质量和效率不预设必然提升；报告各指标的样本数、判定口径和未完成情况，失败与阻塞样本不得从成功率分母中删除。

## 13.5 单 Pi Agent 对照与优化证据沉淀

首版至少比较“单 Pi Agent”与“本方案 IPD 协作”两组。两组使用相同任务输入、材料版本、可完成任务的工具与 Skill、模型设置及评价方法，分别运行于干净工作区。单 Agent 不人为缺配能力；若多角色实验采用不同模型，应单列配置差异，不能把全部质量变化归因于流程治理。任务按相同条件重复运行并逐项比较，少量样例只能支持穿刺结论，不能证明普遍收益。[^1]

计时从各组接收完整任务开始，到正式结果可读取为止。IPD 组计入 ST、设计、编译、执行、评审、返工及可能的 replan 开销，分别报告最终质量、整体成功率、墙钟时间和调用用量。运行中不追加预算控制；测试观察结束时尚未完成的任务如实标注，不当作成功，也不因测试需要改变本轮标准。

每次实验保存任务与材料引用、Pi 及适配层提交、资产与工作流版本、编译基线、运行记录、产物证据和独立评价结果。代表性故障、关键修复、已验证能力及后续问题整理到项目根目录的 `Checkpoint/`，详细轨迹继续留在运行数据中，不在检查点重复堆放全部日志。

**优化依据回到下一轮设计，不反向改写本轮事实。** 根据证据区分规范不适用、工作拆分不足、角色或 Skill 不匹配、评审标准问题、上下文丢失和运行时缺陷；人工修改相应资产或实现后，使用新版本重新验证。首版不自动更新规范或员工，也不凭一次成功扩展尚未验证的流程能力。[^2]
