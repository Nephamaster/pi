查阅你给出的论文、华为公开文档以及 IBM 的 IPD 资料后，我认为关键结论可以明确为：

**IPD 在你们架构中应当体现为一层“流程治理规范”：它既约束节点内部如何工作，也约束节点之间如何组织、交接和评审。节点结构与 IR 是承载这套规范的重要载体，但不能等同于规范本身。**

下面先明确原始 IPD 的含义，再给出它在你们系统中的具体位置。文中的 `ProcessSpec`、节点契约等名称，是面向你们架构提出的工程抽象，并非华为原有的术语。

## 一、华为的 IPD 究竟是什么

### 1. 它是产品开发与管理体系，不是一套节点定义

先校准一个来源事实：IPD 并非华为最早提出。华为在其官方白皮书中说明，公司于 1999 年引入 IPD，其实践结合了 PRTM 的 PACE 方法、IBM 的咨询建议，以及华为自身长期积累的经验。我们现在要借鉴的是**华为实践中的 IPD 体系**。

你提供的论文《New product development paradigm from the perspective of consumer innovation: A case study of Huawei’s integrated product development》区分了两个层次：广义的 IPD 管理体系包括市场管理 MM、需求管理 RM 和产品开发流程 IPD；狭义的 IPD 流程则包括概念、计划、开发、验证、发布和生命周期管理。论文第 5 页的图 1 展示的正是这两个层次的关系，而不只是开发活动的先后顺序。

这意味着，不能把完整 IPD 理解成“先设计、再实现、再测试”的工作流程。它同时回答：为什么做这个产品、谁对整体结果负责、各专业如何协作、不同阶段应达到什么成熟度，以及谁有权批准继续推进。

你们不需要把整套企业经营管理搬进 Agent 系统，但需要先辨认出其中哪些机制与长程协作真正相关，再进行转译。

### 2. 与你们最相关的是“组织责任、结构化流程、阶段评审”的结合

**组织责任解决的是谁对结果负责，而不仅是谁执行一个步骤。** IBM 的原始资料区分了负责产品组合管理的 IPMT，以及负责具体产品规划与执行的跨职能 PDT。这里的关键不是团队名称，而是管理决策与具体执行有不同的责任主体，执行团队又由不同专业共同参与。

**结构化流程解决的是如何让工作不再只依赖个人经验。** 关于华为 IPD 转型的研究指出，标准流程和模板不仅规定阶段，还明确各角色的责任、评审需要准备的材料、工作结果的评价方式，以及需要其他专业支持时如何协作。它们共同构成工作方法，而不是一张流程图单独起作用。

**阶段评审解决的是工作能否被接受、项目能否继续。** 这里必须区分两类概念：华为公开文档中的 TR 是技术成熟度评审，关注阶段成果、遗留问题和产品风险；DCP 则是决策评审点。IBM 资料进一步说明，DCP 涉及是否批准继续、终止或调整方向，也涉及相应的资源承诺。两者并不是同一种“检查结果对不对”。

这组区别对你们很重要：**你目前定义的 Gate——检查执行节点的交付物和证据是否过审——更接近对技术／质量评审机制的通用化，而不是完整复刻投资决策意义上的 DCP。** 首版完全可以保留这种范围，不必为了使用 IPD 的名字，再加入你已经排除的预算管理或投资管理。

### 3. IPD 不要求把所有专业串成一条固定流水线

华为官方对 IPD 的定义明确包含并行工程与跨功能团队；其测试流程图也显示，测试需求分析、测试策略和测试设计在前期就介入，而不是等开发结束以后才开始。

因此，“存在阶段和评审点”并不意味着“所有角色按阶段串行出现”。更合适的理解是：多个专业可以提前介入、并行工作，但它们需要在明确的交付和评审边界上同步。

公开的华为云资料也分别提供系统设备类与独立软件类的 IPD 需求模型，面向不同的研发特点。这些产品文档不是完整的企业 IPD 规范，却足以说明不能把同一套具体流程不加区分地套到所有任务上。

还需要限定资料的证明范围：你提供的论文是一项案例与机制研究，不是华为内部流程规范全集。作者自己也说明，其概念模型未必完全对应真实实践。因此，资料能够支持上述组织与流程原则，**但不能直接推导出唯一正确的 Agent 节点类型、IR Schema 或 Session 生命周期**；这些需要我们根据运行时目标设计。

## 二、为什么“IPD 规范对应节点设计”只成立一部分

你的思路抓住了一个关键点：规范必须进入节点结构，而不能只是工作流设计者读过的一段说明。

例如，一个执行节点明确了目标、输入、职责、允许使用的能力、交付物和证据要求，那么这些约束就可以用于构造 Agent 的任务上下文、工具边界和提交要求。一个评审节点明确了评审对象、评审者与准出标准，就可以用于控制下游是否被放行。**这是 IPD 在节点层面的落地。**

但仍然存在另一类规则，无法通过单个节点的字段是否齐全来判断。

假设所有执行节点和评审节点都符合 Schema，工作流设计者仍然可能构造出这样的工作流：某个关键交付物没有经过评审就被下游采用；评审者实际也是该交付物的唯一生产者；两个分支各自过审，但汇聚时没有检查它们是否采用相同的需求和接口约定；最终交付覆盖不了最初的任务目标。此时**节点局部合法，整体流程仍然不合格**。

这就是必须补充的全局层：哪些活动必须出现，哪些成果必须经过何种评审，生产与批准的职责如何分开，哪些节点可以并行，在哪里汇聚，以及最终交付如何追溯到任务要求。

建议把几个容易混淆的概念分开：

| 概念 | 在你们架构中的含义 | 不应混同于 |
|---|---|---|
| IPD 方法论 | 需求驱动、跨专业协作、结构化交付、阶段评审等设计依据 | 某一张具体工作流 |
| 流程规范 `ProcessSpec` | 对一类任务的组织方式、必要活动、交付与评审关系作出规定 | 一套节点字段定义 |
| 节点类型与节点 IR | 引擎能够表达、校验和执行的节点结构，例如执行、评审及相应契约 | 完整的业务流程规范 |
| 节点模板 | 在通用节点结构上沉淀的可复用作业要求、输入输出与评审要求 | 某次任务的具体节点 |
| 工作流定义 | 设计者结合任务和规范，确定的具体节点、员工绑定、依赖及验收标准 | 执行中的状态与会话 |
| 工作流 Run | 对冻结工作流的一次执行，包含 Session、产物版本、评审记录和进度 | 可被执行者随意改写的计划 |

这里最重要的区别是：

**节点类型定义“系统能够表达什么”；流程规范定义“这类任务应当如何组织”；具体工作流定义“这次任务究竟怎样做”。**

所以，不必为每套 IPD 规范开发一套不同的引擎节点类。不同规范完全可以复用相同的执行节点、评审节点和并行／汇聚机制，只是在节点契约、组织关系和必须满足的流程条件上不同。确实出现了无法用现有节点表达的新执行语义时，再扩展引擎能力。

## 三、建议如何定义你们的“IPD 流程规范”

我建议采用下面这个工作定义：

> **IPD 流程规范，是面向某类长程任务预置并版本化的组织执行规则。它规定必须完成哪些活动、由哪些职责承担、形成什么交付物与证据、经过何种评审，以及满足什么条件后才能向下游交接；工作流设计者在这些规则之内，为当前任务构造具体执行图。**

一份规范约束的应当是**一族合法工作流**，不必只对应唯一一张固定图，也不能宽泛到只剩“请合理规划、认真评审”。

从内容上看，它至少应当覆盖下面三个相互关联的层面。

**第一层是流程骨架与组织责任。** 规范需要说明适用任务、必须保留的活动或里程碑、所需专业职责、重要的先后关系与汇聚关系，以及哪些职责不能由同一个执行主体兼任。这里的“骨架”不一定是六个固定阶段，也不一定要求独立建模成阶段节点；它可以表现为必须存在的工作单元和必须经过的评审边界。

**第二层是节点作业契约。** 这是你第 6 点重点考虑的部分，包括目标、输入、执行指引、约束、交付物、证据要求和参与角色。规范可以规定某类工作必须形成哪些内容，而具体工作流再把这些要求落实到本次任务。例如，规范要求“形成可验证的验收依据”，设计者则必须进一步明确本次任务具体检查什么、依据什么材料、采用什么标准，而不能只原样复制一句抽象要求。

**第三层是跨节点的交接与准出规则。** 哪份交付物由哪个 Gate 评审，评审通过后允许被哪些下游使用，多个分支需要提交哪些成果才能汇聚，最终交付如何覆盖原始要求，都属于这一层。它们不是 Agent 内部的工作提示，而是整张图必须遵守的关系。

这也明确了 ST 与工作流设计者之间的分工：**ST 选择的是一套组织执行规范，不是一套节点 SDK；设计者在选定规范内完成具体任务分解、节点配置和数字员工选择。** 首版 ST 只选已有规范，不承担修改规范的职责，与你已经确定的边界一致。

这里还需要避免两个极端。规范过于具体，设计者就退化成给固定流程填参数；规范过于抽象，设计者又会回到自由规划。比较合适的边界是：**固定必须遵守的责任、交付与评审关系，开放具体工作拆分、专业配置和合法范围内的并行组织方式。**

例如，“交付型任务”与“探索型任务”可以使用相同的节点类型，但前者更强调已明确要求的覆盖与最终交付验证，后者更强调假设、实验和证据是否足以支持结论。这只是说明规范的区分维度，不是为你们预先确定分类，更不是照搬某套华为官方分类。

在存储表达上，也不必强求所有规范都立刻变成机器可判定的表达式。可以在同一份版本化资产中同时保留自然语言作业要求和结构化约束：前者供设计者、执行者与评审者理解，后者供 Compiler 和 Runtime 检查。**但必须明确哪些条件由代码强制，哪些内容仍然需要专业判断；自然语言写了“必须”，并不等于系统已经能够强制执行。**

## 四、它在图引擎与 Pi 之间的具体位置

按你已经明确的边界，我建议将整体关系组织为：

```text
外部 Pi Agent
  → IPD Tool.create_run（任务与必要上下文）
  → 图引擎的主控流程
      ST 选择流程规范
        → 工作流设计者构造任务工作流、绑定数字员工
        → 独立 Compiler 校验并编译
        → Runtime 执行任务工作流
            → 节点内的一个或多个 Pi Agent Session
            → 交付、评审、返工、并行与汇聚
```

这里存在两个逻辑层次：**负责“选择规范—设计—编译—启动执行”的主控流程，以及为当前任务生成的具体工作流。** 前者必须能够在任务图尚未生成时推动整个过程，后者才是工作流设计者的输出。这不意味着需要两个图引擎，而是一个完整架构内的两个控制层次。

在这条链路中，IPD 规范不是只被 ST 和设计者读取一次，而应当在三个位置实际生效。

**在设计时，它限定工作流的合法设计空间。** 工作流设计者使用节点模板和数字员工资产，将任务具体化；员工选择在这里完成，而不是交给 Runtime 临时重新匹配。设计者不仅输出一张能连接起来的图，还需要说明这张图如何满足选定规范，例如必要活动落在哪些节点、每类受控交付物由哪个 Gate 负责。

**在编译时，它成为合规校验的依据。** Compiler 不仅检查图结构和字段是否有效，还检查有没有漏掉规范要求的活动与 Gate、员工绑定是否满足职责要求、交接关系是否完整、受控产物是否存在绕过评审的下游路径。这里可以同时存在节点级校验与整图校验。Compiler 独立于入口 Tool，并且需要同时理解工作流定义和它所声明遵循的规范版本。

不过，Compiler 能够验证的是已经形式化的结构和规则，不能仅凭 Schema 完整就证明“任务分解合理”“验收标准充分”或“最终结果一定正确”。这些仍然是语义质量问题，不能被静态校验冒充解决。

**在运行时，它被落实为实际的执行约束。** Runtime 按契约为节点准备输入和能力，接收产物与证据，启动对应评审，并控制下游放行。Agent 的文字声明不直接等于节点准出；准出需要经过工作流已经规定的评审关系。运行时不必每次重新解释整份 IPD 文档，而应执行编译后明确绑定的契约。

因此，IPD 在这个架构中的位置可以概括为：

**规范资产是规则来源，工作流是规则的任务化实例，Compiler 检查实例是否合规，Runtime 执行已经固化的规则，Pi Agent 在这些规则之内完成专业工作。**

IPD Tool 则只负责引入这套执行体系，不负责承载其中的复杂性。

## 五、由这一定位，可以进一步明确节点、Gate 和 Session 的关系

### 1. 节点应当代表“有交付责任的工作单元”，而不是一次 Agent 调用

你提出执行节点可以有多个执行者、评审节点也可以有多个评审者，这与上述定位并不冲突。因为节点的边界应由**目标、交付和准出责任**确定，而不是由调用了几个模型决定。

一个执行节点可以由多个数字员工协作，但需要对外形成明确的交付包；一个评审节点可以由多个评审者检查不同方面，但需要对外形成明确的评审结果。具体如何分工与汇总可以继续设计，目前不需要展开表决规则。

需要保留的区分是：**节点是工作责任单元，Session 是参与该工作的执行实体。** 不宜因为有多个 Session，就自动把一个节点拆成多个节点；也不宜因为同一个员工参与了多个工作，就把这些工作合并成一个节点。

### 2. 独立 Gate 更适合表达明确的交付与放行关系，但不必强制一对一

从你们希望显式控制评审对象、评审者以及并行成果汇聚的目标看，独立评审节点是一个合理方向。

但建议不要在底层模型中写死“一个执行节点只能对应一个 Gate”。局部工作可以有自己的评审，多项成果汇聚以后也可以有综合评审。前者判断某项成果本身是否合格，后者判断多项成果放在一起是否一致、完整、能够支撑下一步。这两类责任不同。

Gate 的核心关联对象应当是**确定版本的交付物及其证据清单**。否则，评审通过的是版本 A，生产者又把文件覆盖成版本 B，下游却仍然沿用原来的批准状态，就会使评审失去意义。这里不需要立即设计复杂状态枚举，但应当从概念上明确“评审批准哪一次提交”。

并行场景下，某个 Gate 没通过，阻塞的是依赖该受控交付物的下游，而不是所有无关分支。这样才能同时成立“严格准出”和“并行执行”，而不把整个流程重新串行化。

### 3. 持续 Session 与冻结工作流可以同时成立

按照你已经明确的要求，执行 Agent 在首次提交后应当等待评审，而不是结束并销毁；需要返工时，将评审反馈送回原 Session，由它继续修改，直到对应交付达到标准。因此，**一次模型响应结束、一次产物提交完成、一个工作单元通过评审，是三个不同的事件**。

这个生命周期来自你们对执行连续性的要求，并不是从 IPD 文献中直接得出的技术规定。IPD 提供的是持续承担交付责任的组织启发，Pi Session 如何保持这份责任连续性，则是你们的运行时设计。

同样，冻结工作流也不意味着执行只能走一遍。工作流结构、员工绑定和评审标准可以保持不变，同时允许交付物形成多个修订版本、评审发生多轮、原 Session 继续返工。**修改交付物不等于修改工作流，既定返工机制的再次执行也不等于 replan。**

这里需要特别处理一个图模型问题：如果显式画出“执行 → 评审 → 返工回执行”的边，完整控制图就已经包含环，不能再把全部运行语义理解成一个纯 DAG。比较适合你们当前要求的表达是：**前向任务依赖保持 DAG，评审返工由固定的执行—评审闭环或节点组状态机承载。** 这是一种建模建议；无论最终选择哪种实现，图引擎都不能只具备“一次拓扑排序、每个节点执行一次”的语义。

---

综合起来，你当前的想法可以修正为下面这段架构表述：

> **我们借鉴华为 IPD 的组织协作与结构化流程思想，将其沉淀为可选择、可版本化的流程规范资产。流程规范同时约束节点的作业契约和工作流的组织、依赖、交接及评审关系。工作流设计者依据选定规范，使用通用节点与节点模板，从数字员工池中选择参与者，构造当前任务的具体工作流；独立 Compiler 完成合规校验与编译，图引擎在运行时强制执行交付和评审规则，节点中的 Pi Agent Session 则持续承担执行责任，直至其交付通过评审。**

**所以，当前最值得先定义的不是“IPD 一共对应几种节点”，而是“哪些规则属于流程规范，以及这些规则分别由节点契约、整图约束和运行时机制中的哪一层负责落实”。** 这一层划分清楚之后，节点结构与 IR 才有明确的设计依据，而不会把全部组织规则挤进一个越来越大的节点配置表。
