**IPD 需要一套可靠的执行环境，但不需要把 IPD 做成一个庞大的云沙箱平台，更不需要把 Agent 限制成只能按规定路径填文件、遇到缺依赖就停下来的程序**。

## 为了让 Agent 顺畅工作，真正需要的是五项完整能力

### 1. 提供能工作的基础环境，同时允许正常的项目内调整

合理的环境不是“什么都没有，让 Agent 从零装系统”，也不是“预装清单之外一律禁止”。

应该分成两层。

**基础环境由系统负责。** Python、Node、Git、常用构建工具、证书，以及 Office 场景需要的 LibreOffice、字体等，应当通过少量维护良好的镜像提供。这样不必每个节点反复安装，也不应让 Agent 花几十分钟排查系统级依赖。

**项目依赖由正常工作流程负责。** 某个项目需要额外 npm 包、Python 库，Agent 应能在自己的项目目录或虚拟环境内安装和使用。npm 支持项目内 `node_modules`，Python 的虚拟环境支持独立安装项目包；这与修改宿主全局环境是两回事。([npm 文档][3])

例如：

> 基础环境保证有 Python；任务需要某个额外的数据处理库，在授权的软件源和自己的虚拟环境中安装，属于正常开发工作，不应该自动变成整个 Run 的阻塞。

**“冻结基础镜像”也不意味着“整个工作环境不能发生变化”。** 基础镜像确定起点，项目目录、依赖文件、虚拟环境和中间产物仍然可以变化；需要复现时，记录实际依赖版本与安装结果。

这也是现有成熟产品使用的方式之一。Codex 云环境提供预装常见语言和工具的镜像，同时支持项目 setup script、自动依赖安装，并单独配置 Agent 阶段的网络权限，而不是要求一个镜像预先知道所有项目的依赖。([OpenAI Developers][4])

这里也要纠正一个过于绝对的表述：**不是所有缺依赖都应该在启动前硬阻塞。**

启动前必须确认的是环境本身可用，例如目录能写、解释器能执行、所需网络通道可达。基础镜像承诺提供的软件缺失，应当作为平台配置问题处理；项目可以在授权范围内补齐的依赖，则应允许安装。只有既缺少必要能力、又没有合法补齐路径时，才需要暂停。

真正需要系统级软件变更时，更新镜像或受控初始化配置即可，**不应该因此修改 IPD 调度器，更不应该让 Agent 去修改宿主机。**

### 2. 让所有文件工具看到同一个工作区，并给足工作空间

对 Agent 来说，最基本的体验应该是：

> `write` 写入的文件，`bash` 能读取；Python 生成的图片，`read` 能打开；下一轮和返工时，这些文件还在。

这要求 `read/write/edit/bash/grep/find` 的实际操作都指向同一份环境文件系统。Pi 文档特别提醒：把内置工具转发到沙箱，并不会自动让其他扩展工具也进入沙箱；扩展仍在 Pi 主进程所在位置运行，除非它们主动委派操作。

因此，统一工具后端是必要的。**但统一以后，不应该再为普通中间文件增加层层路径例外。**

当前采用的基本目录含义是合理的：原始输入和冻结规范只读；节点自己的 `/workspace` 可写；临时目录、缓存和 Home 可写；正式输出单独导出。当前 README 也已经明确允许执行节点在工作区根目录放源码、依赖和中间文件，不必把每个临时目录声明为 Artifact。这部分应该保留。

所谓“挂载”，就是将指定存储目录呈现在容器中的某个路径上。Docker 可以把输入挂载为只读，把工作区挂载为可写；后者的修改可以持久保存在宿主指定目录中，而无需开放整个宿主文件系统。([Docker Documentation][5])

**还有一个需要正式改进的边界：评审者不能修改被评成果，不代表评审者不能写任何文件。**

评审代码时，可能需要安装测试依赖、产生构建目录、运行测试并保存日志；评审演示材料时，可能需要生成渲染图。合理做法是：

```text
被评提交：只读，保持原版不变
评审者自己的检查目录：可写
需要构建时：从确定版本创建检查副本
评审结论：仍针对原提交，并说明实际检查方式
```

当前 Compiler 会直接禁止 Review 节点获得 `write/edit/bash/powershell`。这是现阶段采取的保守实现，**不是独立评审的本质要求**。后续应显式演进成“保护被评对象、允许检查活动”，而不是简单删除校验、让评审者直接修改生产者文件。

### 3. 把联网分清楚：访问资料、下载依赖和修改外部系统不是同一种权限

你说的“该联网的能联网”，至少包括三类不同操作：

| 实际需求             | 应提供的能力              | 不应顺便放开的权限           |
| ---------------- | ------------------- | ------------------- |
| 查询资料、阅读公开网页      | 搜索／网页获取工具，或授权的出站网络  | 任意读取和上传宿主文件         |
| 安装依赖、下载模型或资源     | 访问所需软件源、文件服务和相关下载地址 | 任意访问宿主管理接口或无关内网服务   |
| 推送代码、发布内容、修改业务数据 | 有明确目标和权限范围的认证工具     | 将全部账号凭据交给任意 Bash 使用 |

这里还有一个容易误解的点：**Agent 会话能调用模型 API，不代表容器中的命令也能联网。** 在“Pi 留在宿主、工具进入容器”的架构下，两者本来就是不同网络路径。反过来，一个在控制侧执行的搜索工具，也可以代替容器访问网页，而不必让所有容器获得相同的网络能力。

我的建议是：**预先授权正常工作所需的网络范围，让范围内的操作自动执行，而不是每条命令都让用户批准。** 这不要求加入你此前排除的 HITL；允许什么，可以由可信的运行配置事先确定，工作流设计者只能在已有授权内选择。

对于受限联网，要采用实际执行网络限制的机制，例如统一出站代理配合无法绕过它的网络规则。代理可以理解为“网络出口”：请求必须经由它转发，它负责判断目标是否允许。**仅设置一个代理环境变量，或者在提示词里写“只访问这些域名”，不能等同于强制限制。** Claude Code 的沙箱设计同样将文件与网络边界分开，并通过沙箱外代理控制网络访问，目的就是在边界内允许命令自主运行。([Claude][6])

这里不该走两个极端。

一端是“一律断网”，于是调研和依赖安装都被堵住；另一端是“普通 Docker bridge 就等于安全联网”。Docker bridge 提供连接能力，但它本身不是按业务目的配置的域名白名单。([Docker Documentation][7])

另外，**没有宿主密钥，也不等于没有数据泄露风险**：Agent 可能处理敏感输入，网络请求本身就可能携带这些内容。公开资料任务与内部机密材料任务应使用不同授权；访问外网的风险也包括恶意网页指令和不可信依赖。([OpenAI Developers][8])

因此，该补的是“可用且明确授权的联网”，不是简单把 `none` 改成一个更宽松的网络名字。

### 4. 让程序正常运行、可观察、可停止，而不是每次出错都重置工作台

为什么要管“多进程”？因为 Agent 做实际任务时，本来就会启动不同程序。

生成一张图的 Python 脚本通常很快结束；开发服务器却需要一直运行，供后续测试访问。不能让工具一直等待开发服务器退出，否则后面的工作永远不会开始。因此，执行层至少需要区分：

**短任务：**执行命令，返回退出码、输出和错误。

**长任务：**启动后返回一个句柄——可以理解为编号，后续用这个编号查询状态、读取日志和停止程序。

这不是为了多 Agent 预建复杂调度平台，而是为了支持“启动服务，然后测试它”这种最普通的开发行为。

关键还在于**失败影响到哪里**。测试失败，应该把失败结果交给 Agent 修改代码；一条命令超时，应优先停止这一条命令及其子进程；环境本身失效，才需要暂停相关工作。不能把这些都理解成“整个 Run 失败”。

我上一轮指出的单命令超时杀掉整个容器、业务 round 与模型派发停止边界混用，仍然需要修。它们对应的用户体验非常直接：

> Agent 正在做正常工作，一条检查命令出错，不应该导致开发服务器消失、其他工作被打断、整个节点又进入无法解释的暂停。

同样，**文件保存、会话保存和进程保持运行，是三种不同的持续性。** 返工应该保留原会话和工作文件；暂停后服务是否仍运行，必须有明确规则。不要承诺“容器还在，所以所有内存状态和进程都自动恢复”。

这部分需要一套小而完整的生命周期实现，但不需要分别建立好几个相互重叠的“重试管理器、恢复管理器、停止管理器”。

### 5. IPD 只管理工作责任和交接，不介入每一条普通命令

IPD 真正应该关心的是：

> 当前谁负责什么、使用哪一版输入、交付什么、由谁评审、评审失败影响哪些后续工作。

它不应该关心某段 Python 使用了哪个临时文件，也不应该为了 Agent 新安装了一个项目库，就重新设计工作流。

工作区中的代码和中间文件，允许持续修改；在需要交接和评审时，再形成确定版本的提交。**修改自己的工作内容属于执行自治，修改验收标准或批准记录才属于越权。** 这也与我们此前明确的“冻结工作流不等于只能执行一遍”一致。

因此，基础能力的职责应该固定：

| 负责方         | 应负责什么                           |
| ----------- | ------------------------------- |
| **Pi**      | 模型调用、会话历史、工具循环、原生重试和上下文压缩       |
| **执行环境适配层** | 文件与命令实际在哪里执行，网络和依赖是否可用，程序如何启动停止 |
| **IPD**     | 任务组织、输入版本、提交、评审、返工、下游放行和最终完成判断  |

这些可以都在同一个项目、同一个主程序中实现。**逻辑分层不等于微服务化，更不等于每层都要一个独立服务器。**

## 四、哪些复杂度值得保留，哪些现在没有必要

**值得保留的，是能够直接解释其价值的机制。**

独立工作区避免并行任务互相覆盖；只读输入保护原始材料；统一工具后端避免“写了却读不到”；持续环境避免反复安装与丢失工作；提交版本避免评审对象变化；取消与清理避免程序失控和资源遗留。这些都直接服务于“顺畅干活”。

**现在没有必要的，是为了尚未出现的规模和风险提前建设完整平台。** 例如跨机器调度、多租户计费、多种沙箱后端同时维护、微虚拟机集群、任意环境的透明迁移、所有外部操作的自动补偿。这些不是让你当前 IPD 正常完成代码或内容任务的前提。

还有一些要求虽然听起来“严格”，但并不合理：每个中间文件都要预先声明；所有依赖必须事先穷举；每次 Bash 都重新初始化环境；所有错误都转成节点阻塞；评审者完全不能运行程序。它们会限制正常工作，却未必有效保护真正需要保护的对象。

**我的取舍不是撤掉安全边界，而是：边界外严格，边界内给足工作自由。** 例如不允许修改宿主 Python，但允许维护项目虚拟环境；不允许修改被评提交，但允许在检查副本中构建；不允许访问任意内网管理接口，但允许访问任务所需的软件源。

## 五、落到你当前代码，接下来到底要做什么

你现在不是缺一套全新的架构。已经有 Docker、持续 Session、统一文件工具、成果封存和运行状态，不应重写。当前需要完成的是：

| 工作             | 具体完成标准                                         |
| -------------- | ---------------------------------------------- |
| **补齐授权联网**     | Bash、包管理器和需要联网的工具能够通过实际授权通道工作；断网是可选择策略，而不是唯一能力 |
| **明确依赖处理方式**   | 基础软件由镜像保证，项目依赖允许在自己的工作环境中安装；不把可修复缺依赖一律当成阻塞     |
| **完成文件与检查权限**  | 所有工具看到同一工作区；执行者能正常开发；评审者不能改原提交，但能在私有检查空间验证     |
| **修完整个工作生命周期** | 单命令错误不破坏其他程序；正常返工保留会话和文件；停止、暂停、失败清理都有确定结果      |
| **保留并修正治理正确性** | 仍按确定版本评审；批准撤销时正确影响实际依赖它的下游，不能用“环境顺畅”替代质量正确     |

这里每一项都应优先完善现有模块，而不是添加一个名字更宏大的新框架。

**最重要的验收方式，也应该从“机制测试通过”补到“正常工作确实可完成”。** 先让同一个模型、同一套工具在同一个受控环境中，用普通 Pi 完成实际任务；再让 IPD 节点完成相同工作。这样才容易区分：问题来自环境、工具、模型，还是 IPD 编排。

至少应覆盖三条真实路径：联网获取资料并生成交付物；准备代码依赖、实现、构建和运行测试；启动后台服务、执行后续检查，再经历一次失败修复。然后再叠加评审和返工，而不是直接用一个庞大工作流同时检验所有基础设施。

---

**所以，回答你最核心的问题：实现“IPD 下的 Agent 能顺畅干活”，需要的是一台为它准备好的、权限明确的工作计算机，以及一套不妨碍它使用这台计算机的工具接口。IPD 只在任务责任、交接和质量上施加约束。**

环境故障不可能被彻底消灭，但合理目标是：**常见操作开箱可用，项目内问题允许自修，真正的权限缺口明确说明，局部失败不摧毁已完成工作。**

容器应该帮助实现这个目标，而不是成为新的障碍；治理应该保证交付可信，而不是把员工的正常工作变成层层审批。现在最需要补齐的，正是这两者之间的界限。
