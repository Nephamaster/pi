## 第 01 章　IPD 的借鉴范围与控制机制

<a id="s01-01"></a>

### 1.1 要控制的不只是单次回答错误，而是错误如何进入后续工作

《基于组织流程控制的多智能体长程任务范式》将问题指向长链路中的偏差积累：早期局部错误被后续步骤接受，直到终态才暴露，返工代价随之增大；原始设想因此强调角色专精、流程可选和阶段准出。[01-S02](appendices.md#ref-01-s02) 本指导将其作为需要实现和验证的目标，而不把“完全消除失配或漂移”等愿景表述当作已经取得的效果。

例如，一个研究者把未经确认的推断写成事实，设计者据此形成方案，实施者再忠实执行。后两名成员即使严格完成了自己的局部任务，整体成果仍然可能错误。再增加一名只读最终摘要的 Reviewer，也未必能发现最初的证据问题。

本方法需要同时处理四类失控：**任务依据被逐步改写、局部错误被当作可靠输入、多个正确局部不能组合成正确整体、执行者的文字声明越过了正式控制条件。** 它们不一定通过“再思考一次”解决，而需要保留依据、显式交接、独立核验和真实的状态控制。

因此，治理的对象不应是模型的每一步推理，而应是工作中的关键责任与承诺：一次交付究竟承诺了什么，承诺由什么证据支持，后续工作凭什么依赖它。节点内部保留必要的探索和工具使用自由，跨责任边界则使用明确协议。

与此对应，**可控不等于结果必然正确**。这里的可控首先指：工作范围和授权明确，运行状态可解释，关键成果可核验，失败可定位，变更可追溯，停止与恢复有依据。质量改善还取决于模型、专业方法、资料和验证能力，需要另行评测。

### 1.2 借鉴的是 IPD 的治理机制，不是企业组织外形

#### IPD 的公开资料提供了什么

华为 2013 年官方白皮书说明，其于 1999 年引入 IPD，结合了 PRTM 的 PACE、IBM 建议和自身实践。该文图 4 区分市场管理与产品开发，并展示概念、计划、开发、验证、发布和生命周期的高层结构；图 5 展示安全活动嵌入开发阶段，而非仅在最后检查；§7.5.1 则说明配置管理、追溯和职责分离。[01-W01](appendices.md#ref-01-w01)

华为云 CodeArts TestPlan 的公开说明强调，IPD 包含并行工程、跨职能团队和对产品生命周期的早期考虑；其术语表将 TR 定义为技术成熟度评估，关注阶段成果、遗留问题和产品风险。[01-W02](appendices.md#ref-01-w02) 因而，“集成”不能仅理解为把不同专业串成一条流水线：需要提前介入的专业应提前介入，存在真实独立性的工作可以并行，在必要的成熟度和交接边界再汇聚。

IBM 的公开培训材料区分跨职能管理团队 IPMT 与执行团队 PDT。它说明的 DCP 不仅判断材料质量，也涉及继续投入、终止或调整方向，以及相应资源承诺。[01-W05](appendices.md#ref-01-w05) **TR、DCP 和本项目的质量 Gate 不能混称。** 本方法主要转译交付成熟度、专业核验和准出关系，不因使用 IPD 名称就给 Agent 增加投资、采购、产品上市或现实组织审批权。

这一借鉴也不是将原企业流程原封不动软件化。IBM Research 对其高层 IPD 定义的研究指出，相关定义强调业务目标、治理、高层结构、参与角色和明确交付，对低层活动结构并不逐项穷尽。[01-W03](appendices.md#ref-01-w03) 这支持我们区分“规范约束什么”和“当前任务具体怎样做”；至于如何编译、维持会话、隔离工具和恢复副作用，仍需独立设计。

#### 公开实践如何转译为本范式

下表右侧是本方法的设计约定，不是公开资料声称已经实现的 Agent 机制。

| 借鉴维度 | 在本范式中的转译 | 必须避免的等同 |
|---|---|---|
| 需求驱动与整体价值 | 保留用户原始目标，让局部交付能够回到整体用途和最终验收 | 部门完成自己的清单，就等于用户目标完成 |
| 跨职能协作 | 按所需专业职责组织成员，明确其输入、贡献和整合关系 | 多几个角色名，就获得了真实能力或独立判断 |
| 结构化流程与阶段成熟度 | 对一类任务定义必要活动、受控成果和关键质量边界 | 每个阶段必须对应一个节点，或必须使用固定六阶段 |
| 技术评审与问题处置 | 对确定版本及证据作专业判断，形成可定位问题和修复责任 | Reviewer 的身份、口头同意或投票多数自动构成质量证明 |
| 决策与执行分离 | 专业意见和正式状态迁移分开，Runtime 执行已经授权的规则 | Agent 自行宣布全流程通过，或者获得企业 DCP 权限 |
| 配置与变更管理 | 固定当前依据和版本，显式处理修订及其影响 | “冻结”意味着不许返工，或“灵活”意味着随时改标准 |
| 持续改进 | 用运行证据修订后续资产和方法，再验证、发布 | 为使当前 Run 通过而悄悄修改生效规范 |

华为云关于已基线需求变更的实践，将专家评审、审批人决策和通过后修改字段分为不同步骤。[01-W06](appendices.md#ref-01-w06) 我们从中借鉴的是**对既有承诺的修改需要明确程序**，而不是照搬每次操作都必须召开同样的审批流程。

公开材料也有边界。2024 年的华为 IPD 案例论文使用案例研究讨论机制，并指出既有 IPD 在用户洞察和敏捷迭代方面存在局限；作者承认数据来源及概念模型与实际实践的吻合程度有限。[01-W04](appendices.md#ref-01-w04) 因此，企业案例可支持借鉴动机，不能直接证明本方法比单 Agent 更快、更省或更准确，也不能替代华为内部规范。

### 1.3 IPD 在本方法中的位置：规则来源、任务设计与执行机制分层

本方法对 **ProcessSpec（流程规范）** 的工作定义是：

> 面向一类任务、可选择并版本化的组织执行规则，说明需要保留哪些专业责任、活动、交付和证据，哪些成果应经过何种判断，以及何种条件下可以交接或完成。它约束一族合法工作流，而不是直接给出当前任务唯一的执行图。

这一定位沿用既有 `what_is_ipd.md` 的核心结论。[01-S04](appendices.md#ref-01-s04) 为避免后续实现混淆，先区分以下层次：

| 层次 | 回答的问题 | 不负责什么 |
|---|---|---|
| IPD 方法原则 | 为什么采用这种组织、交付和质量控制方式 | 不直接规定某个 SDK 或状态存储产品 |
| ProcessSpec | 这一类任务有哪些不能丢失的组织与质量责任 | 不穷举当前任务的工具调用和每项业务内容 |
| 工作流模板 | 对一组适用条件，已有怎样的可复用具体组织方式 | 不保证换一个任务后仍然适用，也不携带旧执行状态 |
| 当前工作流定义 | 这次任务由谁完成哪些工作，输入输出和评审如何关联 | 不代表工作已经执行或成果已被批准 |
| 执行基线 | 本次获准执行的工作流、资产、标准和资源依据是什么 | 不容许执行中通过静默改写改变承诺 |
| Run 与运行时状态 | 实际执行到了哪里，使用了哪些版本，哪些结论仍有效 | 不以角色自述替代事实，也不重新发明任务目标 |

这里最重要的关系是：**引擎定义可以表达什么，规范定义这类任务应如何组织，工作流定义本次如何落实，运行记录说明实际发生了什么。** 一份新流程规范通常不需要对应一套新节点类；只有出现现有执行语义无法表达的真实需求，才扩展内核。

IPD Tool 是进入这一体系的入口。它接收任务和必要信息、创建或关联执行过程、返回状态与结果入口；不应把规范选择、团队组织、状态维护和故障恢复全部塞进 Tool Prompt。

从逻辑上，治理与编排层位于 Agent Harness 之上：前者管理任务责任和成果准出，后者提供成员会话、模型请求、工具循环和宿主能力。**这是职责分层，不要求两套独立服务，也不要求复制第二套对话历史系统。** 若宿主已有满足契约的工作流或持久化能力，可通过适配复用；同一项正式业务状态仍只能有一个权威维护者。[01-S01](appendices.md#ref-01-s01)[01-F00](appendices.md#ref-01-f00)

### 1.4 作用原理：把局部能力组织成有证据的承诺链

本范式将下述机制连接起来。缺少其中的关键环节，仅增加角色或阶段名称，不能形成相同的控制效果。

#### 事前明确依据，防止任务和标准在交接中漂移

原始请求、正式规范、经批准的设计决定和一般实现建议具有不同地位。设计者可以把“关键数字准确”具体化为可复算的检查，可以选择页面或接口组织方式，但不能把个人偏好冒充用户原始要求。执行者也不能为了绕过困难，把必需交付改成可选或把待确认事实写成已知。

这里要求固定的是**当前工作的责任与验收依据**，不是假装已经知道所有执行结果。研究任务可以把实验、证据和诚实的不确定结论作为交付；尚无法确定的后续实施，可以通过有边界的发现工作和正式变更处理。冻结与探索并不矛盾，静默改写与可追溯才矛盾。[01-F00](appendices.md#ref-01-f00)

#### 事中按专业配置能力，而不是只分配身份

专业分工的价值，需要体现为不同成员实际采用的资料、工具、方法和检查视角。一个能够编写代码的角色不因此具有安全审计结论的充分依据；一个擅长引用的角色也不自动具备所有领域的核验能力。

Agency-Agents 的历史分析提供了一个重要区分：角色与作业手册是可移植资产，但文本本身不是调度、权限和持久化实现。[01-S07](appendices.md#ref-01-s07) 在本方法中，专业资产用于选人与指导，实际可执行能力还必须经过资源装配和授权。能力缺失时应报告缺口，而不是通过改角色名称声称补齐。

#### 交接以确定成果为中心，减少对会话默契的依赖

下游接收的是与自身责任相关的交付视图：成果的用途、版本、必要结论、限制、证据定位和实际读取入口，而不是生产者的全量聊天记录。完整原始材料可以保留供核验，紧凑视图用于降低理解成本，两者不能互相冒充。

“文件存在”“候选提交已接收”“必要检查通过”“获得特定准出”“用户要求已经满足”是不同事实。一次通过仅适用于被检查的对象、版本、标准和范围，不能自动推广到后来修改的同名文件。

#### 评审把专业判断接到正式放行条件，而非增加一次表态

有效的评审至少需要明确对象、依据、证据、结论和问题责任。若评审者只能看到生产者自我评价，或者评审失败不影响该受控出口，设置了 Reviewer 也没有形成实质质量控制。

机械检查验证其实际实现的条件，专业评审判断需要领域理解的条件，Runtime 检查提交身份、对象有效性、必需判断是否齐备以及允许的状态迁移。**确定性的控制协议不意味着专业判断本身确定无误。** 因此，不能从“Compiler 通过”推出“方案合理”，也不能从“评审报告结构合法”推出“成果事实正确”。

#### 问题返回实际责任，修复影响沿真实依赖传播

正常质量返工改变的是成果版本，并不自动改变工作流或验收标准。修复要求应说明违反哪项标准、何处有问题、证据是什么、由谁修正以及如何复验。只有“失败了，请重做”通常不足以形成有效反馈。

持续承担责任还意味着，正常返工回到原有成员的持续 Session，而不是一次提交后就销毁实例、再让新成员从摘要猜测前情。宿主崩溃后允许恢复同一逻辑会话，但应先核对历史、输入与未确定动作。这是本项目已确认的连续性要求，不是由 IPD 文献直接推出的技术规定。[01-F00](appendices.md#ref-01-f00)

当上游成果改变时，曾依赖旧版本的下游成果和批准需要重新判定有效性；未受影响的工作不应被无差别重做。尤其要区分：**批准需要重新取得，不等于每个被评成果都必须重新生产。** 阶段评审可以重新核对一组成果，而其中没有变化、仍然有效的分支继续复用。

整个机制可概括为一条可追溯的承诺链：

```text
原始要求与选定规范
        ↓ 明确责任及验收依据
工作包与实际参与者
        ↓ 使用确定输入，在授权范围内执行
候选成果及证据
        ↓ 针对确切版本检查、评审
具有明确适用范围的批准
        ↓ 受控交接、组合验证
满足整体用途的最终交付

发现问题 → 定位责任 → 修订成果 → 核对影响 → 重新验证
```

这是治理关系说明，不要求图中的每一行都创建一个 Agent 节点。候选接收、版本核对、状态迁移等可以由代码直接完成。

### 1.5 由谁做判断，由谁维护控制

本方法保留“规范选择—任务设计—编译—执行”的职责区分。采用模板或用户明确指定规范时，可以省去不需要的生成工作，但不能省去相应的适用性与合法性检查。

| 责任主体 | 正式职责 | 不能据此取得的权限 |
|---|---|---|
| 流程选择者 ST | 根据任务性质和治理需要选择适用的规范版本，说明依据和决定性未知 | 擅自改规范、补造业务事实，或替设计者完成全部任务拆分 |
| 工作流设计者或设计团队 | 将任务与规范落实为工作包、员工与资源、交接、评审和完成条件 | 通过形式 coverage 掩盖责任缺失，或为了可编译降低要求 |
| Compiler 与资产解析 | 检查已形式化规则，解析真实能力并形成确定的执行基线 | 替代专业判断，或默默改写任务和规范以消除错误 |
| 执行成员 | 在契约与授权内决定具体做法，提交成果、证据或真实阻塞 | 修改全局状态、未授权地调用其他执行主体、自行准出 |
| 评审成员或评审团 | 对分配对象和标准提供专业结论及可定位问题 | 修改被评成果、临时增设门槛，或用多数意见抹除必需标准的真实失败 |
| Runtime 与宿主能力后端 | 根据受控命令和有效结果维护正式状态、实际权限、派发与收口 | 用模型自述推测已完成，或把内部 Gate 等同现实外部授权 |

这里的“唯一正式状态写入口”并不要求全系统只有一个进程，而是要求同一项控制事实具有唯一、可验证的提交协议。实现可以不同，不能出现 IPD 和底层自由 Leader 各自宣布下一步、批准或完成。

数字员工不必知道全图所有细节才能履职，但必须知道当前工作的目的、边界、有效输入和验收依据。治理角色需要更完整的任务与能力视图；执行角色按责任读取；评审角色获得足以独立判断的对象和证据。**视图可以不同，事实来源不能分叉。**

<a id="s01-06"></a>

### 1.6 这套机制的效果边界

第一，流程不能创造缺失的事实和现实验证条件。没有可用来源、测试环境或专业判断渠道时，再增加一轮讨论不会把未知变成已知。系统应交付真实限制、请求补充条件或停止相应工作，不能用程序化的 PASS 掩盖缺口。

第二，角色分离不等于统计独立。相同模型、相似上下文和相同错误来源可能造成共同盲点。应优先提供独立可核验的依据、确定性检查和适当的专业配置；是否需要不同模型或外部复核，再依据风险和证据决定，不能仅以角色名称不同证明独立性。[01-S08](appendices.md#ref-01-s08)

第三，早期发现错误和缩小返工范围是机制目标，不是所有错误都能被限制在一个节点。需求、共享设计和共同数据错误可能影响多个分支；不能为了追求“局部闭环”的表面指标，把应当上溯的问题压给最后一个生产者。

第四，完整流程不保证低成本。规则理解、上下文交接、独立判断和状态维护都有开销。近期 Run 审查中，几乎串行的关键路径、过大的中间文档和节点内部反复修改构成明显负担；请求体错误还阻止了最终交付。它说明“有工作流”不等于“节点工作已收敛”，但不能由一次样本断言全部 IPD 组织方式无效。[01-S11](appendices.md#ref-01-s11)

因此，本方法追求的是**在明确的质量与安全约束下取得可验证的净收益**，不是最大化节点数、评审数或流程覆盖的表面完整程度。

## 第 02 章　何时使用受控协作，怎样确定治理强度

<a id="s02-01"></a>

### 2.1 按任务的依赖、风险和验证需要判断，而不是按任务名称判断

“做 PPT”“写代码”“生成报告”描述的是成果形态，不足以决定治理方式。同样是修改演示材料，替换一页图片和形成重大方案决策材料的组织需求不同；同样是代码修改，一个小而可测的函数修复与跨模块数据迁移也不同。

本指导不以固定时长、页数或调用次数定义长程。更重要的是：任务是否需要跨较多工作步骤保持同一目标，是否有多个相互依赖的成果，错误是否会积累，以及能否在中间形成有效反馈。以下判断维度用于选择组织方式，不要求建立一套伪精确评分模型。

| 判断维度 | 需要确认的问题 | 对组织方式的影响 |
|---|---|---|
| 目标与交付可辨认 | 能否说清预期成果、用途、关键要求和不在范围内的内容？ | 未明确到可以工作时先补齐决定性信息，不能直接冻结虚构计划 |
| 依赖与放大效应 | 哪些局部决定会被多个后续工作采用？错到后面才发现有何代价？ | 对高影响共享依据设置更早的检查，对真实独立工作保留并行 |
| 专业与授权差异 | 是否需要不同知识、工具、数据权限或独立核验责任？ | 有真实差异再分工，不为同一能力复制多个头衔 |
| 风险与可逆性 | 错误是否易发现、易撤回，是否涉及不可逆操作或正式外部承诺？ | 越难撤回越需要在动作前检查；内部评审不替代真实授权 |
| 验证可行性 | 能拿到什么证据，由什么方法判定，缺少哪些现实条件？ | 无证据不能靠增加 Reviewer 解决；应补能力或保留阻塞 |
| 复用与整合成本 | 已有流程是否适用，拆分后如何合并，交接成本是否值得？ | 优先复用足够好的组织方式，不默认每次从头规划 |

**高风险不一定意味着大团队；耗时长也不一定意味着需要完整 IPD。** 一个短小但不可逆的操作，可能只需要明确授权和针对性验证；一个耗时很长的确定性批处理，可能更需要可靠作业执行与恢复，而不是多轮专业协商。

反过来，预研并不天然排斥流程。它可以围绕假设、实验方案、数据和结论边界组织工作，验收的是研究是否诚实、可复核、足以支持当前决策，而不是强制得到正面结果。

<a id="s02-02"></a>

### 2.2 先决定是否需要治理，再分别决定规划来源与局部组织形式

不要把“单 Agent—模板—设计师—团队—子 IPD”当成必须依次升级的一条等级链。它们回答不同问题。

#### 第一层：当前任务是否需要正式的交付治理

对目标集中、职责单一、结果可以直接核验且错误易修复的任务，优先让一个 Agent 使用合适工具和 Skill 完成。多步工具操作本身，不是增加工作流节点的理由。必要时可增加有明确对象的独立检查，而不必建立完整专家组织。

当关键成果需要跨责任主体复用，必须持续保持来源与版本，或者需要阶段性专业判断控制后续工作时，再进入受控流程。这与 Anthropic 关于优先使用足够简单的方案、只有收益明确时增加 Agent 系统复杂度的工程建议一致；该建议不是本项目性能已经获得验证的证据。[01-W07](appendices.md#ref-01-w07)

#### 第二层：进入流程后，采用已有模板还是任务化设计

**有合适的具体工作流模板时，先复用。** 复用前必须确认任务边界、必要输入、资源、质量责任和最终交付匹配，再重新绑定当前任务并编译。相同文件格式或相近名称不足以证明可复用；旧 Run 的状态、输入路径和批准记录不能成为新任务的有效依据。

**只有流程规范适用、具体执行方式尚不合适时，再由设计者实例化。** ST 选规范，设计者决定当前工作包和资源。选型要先排除明显不适用条件，再比较必需责任是否充分、是否引入大量无关工作；规范更长或更“专业”不自动优于通用规范。

当用户已经明确指定规范，可以跳过自动选择；当用户选择了合法模板，也可以跳过自由设计，但仍需验证。这不是目标构想中的唯一启动方式：Pi 原型的固定基线 README 已明确提供这些路径。[01-G01](appendices.md#ref-01-g01) 评估效果时应保留启动方式，不能用一次人工模板 Run 证明 ST 和 Designer 的自动能力。

#### 第三层：某个工作包由单人、团队还是子流程完成

| 局部组织方式 | 合理条件 | 不应采用的理由 |
|---|---|---|
| 单成员持续工作 | 专业责任集中，输入和交付明确，方法可以在一个会话中实施 | 不是因为“系统只允许一个字段”才被迫使用 |
| 局部团队 | 有可区分的专业贡献，需要明确分工和整合，但整体责任已经清楚 | 仅为了让多智能体看起来更完整 |
| 完整子 IPD | 子任务确实需要独立的流程选择、规划、交付和质量闭环 | 当前成员觉得难、历史太长，或想把相同根任务再交给下一层 |

团队和子流程是目标能力，启用必须以引擎实际支持为前提。局部团队可以复用已确定的组织计划，不必每次重走 ST—设计—编译全链。子 IPD 则必须保持父责任边界、受限授权和明确返回结果；其内部完成不自动等于父级验收完成。

最大深度只限制链长，不能同时限制分支总量、保留实例和活动资源。复杂度控制是启用条件之一，不是等树展开后再靠提醒模型节制。具体协议在第 15 章展开。

<a id="s02-03"></a>

### 2.3 将 ProcessSpec 实例化：保留责任语义，不照抄阶段标签

工作流设计的顺序应从任务用途和规范义务出发，而不是从员工库里有哪些人出发。

**先解释治理意图。** 对每项必要活动、成果和评审，说明它试图防止什么问题。例如“形成需求基线”旨在避免各专业使用不同目标；“独立核验”旨在防止未证实结论成为正式依据；“交付准备”旨在避免正确内容因版本、格式或说明缺失而无法使用。

**再落到当前业务对象。** 同一项责任在不同任务下应有不同具体形式：

| 通用责任 | 软件接口变更 | 数据分析 | 正式内容交付 |
|---|---|---|---|
| 明确工作依据 | 行为、兼容性与接口约定 | 分析问题、样本与统计口径 | 受众、用途、主要问题与材料边界 |
| 建立可信输入 | 代码、依赖和既有行为依据 | 数据版本、来源和处理记录 | 原始资料、事实与引用 |
| 验证满足要求 | 行为测试、兼容性和授权检查 | 复算、诊断与结论适用范围 | 事实、论证、跨部分一致性和媒介可用性 |
| 正式交付 | 代码与必要说明、验证记录 | 结果、方法与限制 | 正式文件及必要附件、限制说明 |

该表是方法示例，不是三份现成的 ProcessSpec。真正采用哪项强制要求，仍以所选规范和当前任务为准。

**随后确定成果、标准和证据。** 先说明需要交出什么、怎样判断足够，再选择专业成员和组织方式。要求映射应能够回答“谁落实、体现在哪里、凭什么判断”，而不是只让每个 ID 在配置中出现一次。

**最后检验资源、依赖和完成条件。** 规范适用于这类任务，不意味着当前资产库和环境足以执行。资源缺口应明确报告，不应让设计者把强制责任删除到“剩下的部分可以跑”。同样，一个活动在配置中有合法归属，还必须真正参与应有的准出与完成关系，不能成为对成功无影响的装饰节点。

现阶段 ST 只选择已有规范，不在 Run 中裁剪、组合或修改规范。需要轻量版本时，应选择已经发布的适用版本，或者通过受控的资产修改与验证形成新版本。**在规范许可内合并具体工作包，与删掉规范要求的责任，是两种不同操作。**

<a id="s02-04"></a>

### 2.4 工作包粒度：既不要拆成工具调用，也不要把复杂性藏进超大节点

节点应代表有明确交付责任的工作包，而不是一次模型响应、一次读文件或一个阶段名称。一个节点可以经历多轮工具调用、自检、补正和返工；未来也可以由多个成员协作，其对外责任不因成员数量变化而模糊。

决定是否拆分时，重点看：是否需要不同专业或权限，是否形成可独立消费的成果，是否存在真实并行收益，是否需要独立判断或局部返工边界。**若合并后不会失去这些价值，就没有必要保留一次独立交接。**

但节点少也不等于轻量。一个节点如果同时建立工具链、开展研究、设计表达、制作产物和编写检查器，复杂性只是从图上转移到了不可见的会话内部。应判断问题来自缺少成熟 Skill、工具接口难用，还是工作责任确实需要拆开，而不是一律增加或减少 Agent。

粒度还应考虑信息增量。每个中间成果应有明确消费者和用途；若它只是把已有材料再解释一遍，没有形成新决定、证据或可复用结构，应优先合并或改为已有成果的索引。紧凑交接不能省掉重要限制，完整证据保留也不要求下游反复阅读所有探索过程。

并行必须同时满足工作与接口条件。共享输入已经稳定、职责独立、输出可以对齐时，才能期待减少关键路径；若两个分支需要不断猜测对方的编号、口径或格式，图上的并行可能转化为更多集成返工。共享业务标识、版本和整合约定，应在并行开始前明确。

<a id="s02-05"></a>

### 2.5 评审粒度：在有意义的承诺边界设置 Gate

评审不是给每个执行节点配置一个镜像节点。选择边界时，需要同时考虑错误影响、证据形成时机和检查成本。

**对高影响的共同依据，优先考虑前置检查。** 需求、接口、指标口径等若被多个分支使用，早期确认通常比等全部实施后再统一发现分歧更合适。但前置检查只能判断当时已有证据，不能预先证明实现成功。

**对阶段成果，采用整体成熟度评审。** 阶段内多个工作包可以在明确规则下使用已封存、有效但尚未阶段准出的成果；到阶段出口，再对结果组合和整体属性作出判断。内部候选交接必须显式授权、记录实际版本和未完成的验证，不能被偷换为任意消费未审产物；对外发布或其他不可逆行为也不能借此绕过保护。

**对重大原子成果，保留局部评审。** 一个独立结论、关键变更或高风险操作即使不构成完整阶段，也可能值得单独核验。反之，同一对象、同一标准和相同证据不应被多名 Reviewer 无差别重读，只为增加“安全感”。

**对最终交付，检查整体用途。** 局部全部通过，仍可能遗漏用户问题，使用不一致版本，或者各部分无法组合。最终判断要核对必要交付和质量责任是否齐备，而不是机械重复所有已有效完成的检查。

具体设置时，一项评审至少应能回答四个问题：它依赖什么确定成果、要证明什么条件、为什么在这个时点检查、失败会阻止哪个受控出口。无法回答这些问题的评审，通常只是仪式。

还必须区分**规范允许的优化**和**违反规范的省略**。例如，已有 `project-reviewed-content-delivery@2.0.0` 明确列出了需求、计划、设计、内容、成品、验证和交付评审。[01-S09](appendices.md#ref-01-s09) 不能因为目标引擎支持阶段 Gate，就把该版本的全部要求默默改成一次终审。合并是否允许、是否保留必要时点和独立责任，必须由规范与经过校验的工作流明确表达。

### 2.6 一个贯穿示例：软件接口变更中的组织与返工

以下为**说明方法而构造的例子**，不是实际 Run，也不对应一份已发布规范。假设任务是：为已有服务增加批量导出能力，保持原客户端兼容，交付代码与验证记录；生产部署不在授权范围内。选定的治理规则要求明确行为依据、独立验证和最终交付确认，并允许阶段内受控候选交接。

先形成接口与兼容性依据，确认后进入实现阶段。编码工作与测试用例设计都可以基于同一份接口依据开展；两者之间不应靠最终代码反向决定全部预期。代码候选与测试材料就绪后，再进行集成验证，阶段评审读取实现、测试设计和执行证据。

```text
接口与兼容性依据 → 必要的基线检查
                         │
                  ┌──────┴──────┐
                  ↓             ↓
                编码实现       测试设计
                  └──────┬──────┘
                         ↓
                      集成验证
                         ↓
                      阶段评审
                         ↓
                  代码与记录正式交付
```

这里有五个容易做错的地方。

**一是并行的依据。** 编码和测试设计共享批准的行为约定，可以并行；集成验证需要真实代码和用例，不能为缩短图而提前宣称完成。采用这种阶段内候选交接的前提，是运行时已支持对应权限与版本语义，不能仅修改提示词。

**二是验证结果的含义。** 集成验证可能正确发现旧客户端被破坏。此时一份忠实记录失败、覆盖和证据的验证报告，可以是合格报告；产品候选却不能因此通过阶段评审。要求测试人员“必须交出全绿报告”，会诱导其修改断言或隐藏真实失败。

**三是问题归属。** 若问题来自实现，返工编码责任，并让受影响的集成验证和评审重新进行；仍然有效的接口依据和测试设计可以保留。若根因是原接口约定遗漏关键兼容要求，就必须上溯相应责任和依据，不能永远让编码者局部打补丁。

**四是独立性。** 编码者可以自检，但最终专业判断必须满足规范要求的独立责任。测试或评审成员可在自己的受限环境中运行验证、产生日志，不能直接覆盖被评代码，让“修好后我看过了”代替生产与评审分离。

**五是最终授权。** 工作流确认交付条件后，可以交付代码和记录，不得据此自动部署生产。内部质量准出和真实外部行动授权始终是两条不同边界。

如果任务只是修改一个有充分测试覆盖的孤立格式错误，上述结构就可能过重。合并实现和常规自检，保留必要的独立检查即可。例子的价值在于展示如何选择边界，而不是提供所有软件任务必须照搬的节点数量。

<a id="s02-07"></a>

### 2.7 治理强度必须有收益依据，也必须允许诚实停止

本方法采用“最小充分”而非“最少节点”：保留达成交付、质量和授权条件所必需的责任，同时删除没有实质价值的协调和重复检查。《极简 Agent 设计方案》将极简的重点放在模块边界，而不是省略所有控制功能。[01-S01](appendices.md#ref-01-s01)

可用下面的关系检查一项新增组织机制是否值得：

```text
净收益的判断依据
  = 降低的错误损失与返工成本 + 有效并行和复用的收益
    − 新增的规划、交接、评审、运行与维护成本
```

这是决策框架，不是要求模型凭空填写概率和金额的评分公式。初次设计时可以给出定性理由；有实际数据后，用对照任务验证它。不能用减少必要安全检查换取更快的表面结果，也不能只统计流程自己的 PASS 比例来证明质量改善。

“继续工作”本身也需要理由。关键标准已经满足、证据齐备时，应提交，而不是无限补充；决定性材料或能力缺失时，应记录阻塞，而不是反复生成相似方案；多轮没有实际进展时，应检查任务依据、方法和资源是否仍然成立，而不是简单增加重试次数。保护阈值由任务、宿主能力和运行策略确定，不把某个历史示例的时间或次数写成全局规范，更不能用次数耗尽强制通过。

还要区分两个改进循环。**Run 内的质量循环**在当前合法依据下修订成果、补充证据并复验；**Run 间的方法循环**分析失败和低效，修改规范、角色、Skill 或模板，经过验证后发布。已经冻结的工作流或责任依据确需改变时，走明确变更程序，并重新检查影响；不通过后台更新资产让旧 Run 悄悄采用新规则。

在尚未完成对应实现时，团队、阶段交接或子流程只能是设计目标，不能由治理 Prompt 提前宣称可用。每次增加组织复杂度，都应同时增加可验证的控制范围，而不是只增加 Agent 能发起的动作。

<a id="s02-08"></a>

### 2.8 交给开发实现前，至少回答这些问题

第一部分不冻结具体 Schema，但实现设计应已经能明确以下答案。

| 问题 | 至少应形成的设计结论 | 不接受的替代说法 |
|---|---|---|
| 为什么这次需要受控协作？ | 指出真实依赖、专业差异、质量风险或可复用组织收益 | “这是长任务，所以多配几个人” |
| 遵循哪份规范，哪些义务不能丢？ | 明确规范版本、适用依据及必要责任 | “看起来像某张流程图” |
| 哪些判断由模型做，哪些由代码保证？ | 专业结论与正式状态、授权、版本和完成规则分开 | “Prompt 已经写了必须” |
| 工作包与评审边界为什么这样划分？ | 说明独立交付、真实并行、检查时机和返工价值 | “一个活动对应一个 Agent，再跟一个 Reviewer” |
| 问题出现后怎样处理？ | 能定位成果、标准、责任和受影响依赖；缺能力如实阻塞 | “再执行一次，直到通过” |
| 怎样知道整体完成且确实有效？ | 必需交付与有效质量结论齐备；另有终态和成本评估依据 | “所有人都说做完了”“看板全绿” |

这些问题的答案构成后续资产和 Runtime 实现的需求，而不是要求额外创建六份长文档。能写进已有契约、目录或检查项的内容，不再另造一套平行记录。

## 本部分结论

**IPD 在本范式中提供的是组织与质量治理依据：对一类工作明确必要责任、交付成熟度和评审关系，再由当前任务决定具体工作包、参与者和执行结构。** 它既不是固定节点模板，也不是要求每次调用模型都经过审批。

真正值得迁移的，是“依据不漂移、能力有实物、交接有版本、判断有证据、放行有条件、问题有责任、变化有影响范围”这组性质。至于使用几个 Agent、怎样分阶段、是否调用子 IPD，以及采用什么 Harness 和存储实现，应围绕这些性质和实际收益作选择。

第二部分将据此定义数字员工、流程规范、工作流模板、Skill 和执行资源等资产；第三部分再把这些约定落实为节点执行、质量闭环和可靠生命周期协议。
