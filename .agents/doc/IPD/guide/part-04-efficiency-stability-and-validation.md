## 第 17 章　可观测性、容量与性能优化

<a id="s17-01"></a>

### 17.1 先确定优化对象：缩短无价值工作，不削弱责任与证明

“轻量”不是没有持久化、权限检查和错误反馈，而是同一事实只有一个负责方，同一机制不重复实现，不为一次偶发问题建立一套新平台。《极简 Agent 设计方案》把极简首先解释为模块划分明确、不额外增加功能；本章据此约束观测和优化系统本身。[04-S01](appendices.md#ref-04-s01)

效率优化同时看四件事：最终交付质量、完成任务的时间、真实资源消耗、实现与维护负担。不能靠删除必要评审、隐藏未执行检查、降低标准、减少日志到无法追责，获得表面上的加速。也不能因为质量有所改善，就忽略调用量失控、取消不及时或大量人工救援。

建议用约束下的比较，而不是先拼一个任意加权总分：先确认安全、权限、确切版本和必需质量义务没有退化，再比较完成比例、延迟分布、调用与环境成本；必要时展示几种可选配置的质量—成本曲线，由部署目标决定采用哪一种。一次配置在所有指标上都不占优，就不应仅因“多智能体更先进”而保留。

治理工作并非天然浪费。研究者形成的证据索引、设计者明确的接口和 Reviewer 发现的缺陷都可能减少后续错误。所谓无价值工作，需要由重复内容、无关返工、错误补正、无进展循环、无用等待等具体证据支撑，不能把所有非生产模型调用一律减掉。Anthropic 的工程建议同样强调选择最简单且足够的模式，并实测复杂性带来的收益与代价；这不是对本方法收益的外部认证。[04-W42](appendices.md#ref-04-w42)

<a id="s17-02"></a>

### 17.2 三类数据各司其职：权威审计、性能遥测、受控调试

| 数据层 | 典型内容 | 可靠性与保留要求 | 禁止的混用 |
|---|---|---|---|
| **权威运行记录** | 身份、派发、结果采用、批准、Finding、委派、停止与变更 | 正式控制所需记录必须持久；不能因采样丢失 | 用遥测事件反推或覆盖正式 Run 状态 |
| **性能遥测** | 持续时间、队列、请求量、usage、字节、资源和错误类别 | 有界缓冲、可采样、明确缺失；失败不改变业务结果 | 在状态事务内同步发送远端监控，或让异常日志触发盲目重跑 |
| **受控调试材料** | 原生会话、必要工具载荷、原始结果、请求视图信息 | 按授权保存，控制访问、脱敏和期限 | 默认把全部原始任务、秘密、图片或模型内部文字广播到看板 |

关键命令的唯一身份、结果登记和副作用回执属于第一层，不可用“观测允许丢数据”来豁免。高频时延样本和资源采样属于第二层，可以在背压时降采样，但必须统计丢弃量。第三层用于复现，不能成为日常指标平台的默认输入。

当前 Pi 已把低频指标写到独立 NDJSON，并保护遥测回调不改变执行结果。这是值得保留的方向；但“异步写”仍需考虑缓冲增长和关闭时限，不能认为 Promise 链天然有界。[04-G51](appendices.md#ref-04-g51) 首版可以只有本地文件和离线统计器；只有确有多服务查询、长期趋势或统一运维需求时，才接入完整观测后端。

<a id="s17-03"></a>

### 17.3 用同一套身份解释一项工作，不让指标重新发明业务对象

每次可归属的操作，应关联前文已经定义的 root Run、当前 Run、节点／工作单元、参与者、逻辑 Session、WorkRound、Attempt 和执行资格。工具动作还需要 tool invocation ID；模型请求需要 request ID；涉及交付、评审、返工或变更时，附其对象引用。不是要求每个字段都有值：控制准备阶段可能还没有任务节点，缺失应明确，而非伪造一个节点补齐。

Run 开始记录实际生效配置：引擎与适配器版本、Git SHA、dirty 状态或构建摘要、Harness／SDK 版本、资产摘要、模型请求名称和真实返回名称、协议类型、思考与生成配置、上下文策略、环境镜像身份、网络与资源策略、重试所有者。可变模型别名或中转 API 不保证后端固定；提供不了真实修订信息时记录未知，不能只凭同名就声称可完全复现。

这些信息进入运行清单，不必每轮灌进模型。trace ID 用来连接观测，不代替幂等键、授权标识或产物哈希；Session ID 也不是会话仍然存活的证明。

```yaml
# 观测逻辑示例；标识和配置来自可信执行层，不让模型补填。
operation_observation:
  observation_id: obs-example-01
  root_run_id: run-root
  run_id: run-child
  work_unit_id: calculate
  participant_id: statistician
  logical_session_id: session-calculate
  round_id: calculate-round-2
  attempt_id: attempt-2-1
  operation_id: request-017
  parent_operation_id: attempt-2-1
  kind: model_request
  clock:
    process_epoch: worker-epoch-4
    start_monotonic_ns: 1000000000
    duration_ns: 2300000000
    observed_at_utc: "2026-09-22T02:00:03Z"
  status: response_received
  measurement_source: provider_adapter
  fields:
    request_bytes: 118420
    image_count: 1
    input_total_tokens: 14000
    output_total_tokens: 450
    server_queue_ms: null
  evidence_refs: [request-shape-record-017]
```

`response_received` 只表示请求得到响应，不表示模型输出合法或任务完成。`server_queue_ms: null` 表示没有该测量，不当作零。高基数字段应进入 trace 或运行明细，不把每个 runId、文件路径和完整 URL 都做成常驻时序指标标签。

### 17.4 分清墙钟、活动时间和工作量，避免并行与暂停被错误计费

一个根任务至少需要下列时间口径，且都注明观察起点、截止点和是否终结：

| 口径 | 定义 | 能回答什么 |
|---|---|---|
| 用户可感知历时 | 接入至正式交付／终止；未结束时为接入至统计截止 | 用户等了多久，包括已明确的排队与暂停 |
| 活动区间并集 | 统计范围内至少一个成员实际占用活动执行槽的时间 | 引擎在多少时间内有实际作业 |
| 成员活动时间之和 | 每名成员各 Attempt 的实际活动区间求和 | 付出了多少成员工作量；并行时可大于墙钟 |
| 排队时间 | 语义已就绪，到资源准入并启动的等待 | 是否需要调整并发与资源配置 |
| 条件等待时间 | 等批准、输入、子结果、信息补齐等 | 是否被真实依赖限制，而非机器太慢 |
| 暂停与恢复时间 | 暂停原因、停机区间、恢复处理分别记录 | 人工等待、服务故障与恢复成本分别多大 |
| 环境驻留时间 | 环境或保留 Session 的存在区间 | 等待时即使不调用模型，仍承担什么资源成本 |

同一进程内用单调时钟测持续时间；UTC 用于排序和审计。单调时间不能跨宿主重启相减，跨主机墙钟也不能无条件视为同步。记录 process epoch、来源时钟和必要的同步误差；不能可靠对齐时，只报告本地 duration 和可确认因果，不输出虚假的全局精确并发图。

设实际成员活动区间为 \(I_i=[s_i,e_i)\)：

\[
W=\sum_i(e_i-s_i),\qquad A=\left|\bigcup_i I_i\right|,\qquad \bar c=W/A.
\]

\(W\) 是成员活动量，\(A\) 是活动时间并集，\(\bar c\) 是**有活动期间的平均活动并发**，不是 CPU 利用率，也不是全时段吞吐率。没有活动时比值应为未定义。统计时排除代表父级总范围的包络 span，不能同时把父节点含等待的总时长和每个子活动再加一遍。

局部 A 暂停而 D 继续，不应从整 Run 墙钟中减去 A 的全部暂停。`墙钟减某个暂停时长` 更不能直接叫纯执行时间。若需要可相加的整体时间分解，应预先给根任务定义互斥状态区间；各节点的等待分类可以重叠，只做分布或并集分析。

一次 Attempt 有开始、没有可靠结束时，计作未闭合样本。可以按统计截止计算截至目前的活动量，但必须标明右截尾，不能填一个假成功结束时间，或悄悄从平均值剔除最慢的未完成任务。随附 [`measurement.py`](source-snapshots/step-04-support/measurement.py) 实现的是已给定区间的计量，不替系统推断哪个状态算真实活动。

### 17.5 找瓶颈要看执行关键路径，不能把低并发直接归因于调度器

模型响应跨度、工具执行、环境准备、封存检查、状态事务和 UI 请求是不同层次。对每个操作标明测量位置，区分包含子操作的总时间与扣除子操作后的时间；工具内部模型请求不能被算成额外顶层模型与顶层工具的两份独立工作量。

`message_start → message_end` 若是当前唯一观测，只能称模型响应跨度。没有 Provider 事件，不能拆成排队、网络、prefill、推理和输出。客户端首 chunk 也未必是首个内容 token；代理可能缓冲，chunk 可能只有元数据。命名必须反映实际边界。

对一份静态 DAG，可以分析理论关键路径和可并行区域；有返工、技术重试、恢复和子任务后，应基于**实际展开的执行实例**重建因果链。原图上只画一次 A，不能用来计算执行了三轮 A 的真实时延。某次优化减少了非关键分支时间，未必缩短端到端历时；反过来，减少关键路径上的无效补正，可能比增加并发槽更有效。

建议按“观察—假设—最小变化—同条件复测”推进：先定位等什么，确认是否有足够独立工作，再考虑提高并发。并发升高后应同时检查尾延迟、429／限流、失败、环境压力和最终质量。Google SRE 提出的延迟、流量、错误与饱和度有助于避免只看单一速度指标；这里将其用于运行诊断，而非新增一套庞大监控系统。[04-W40](appendices.md#ref-04-w40)

### 17.6 token、缓存、请求字节和账单是四种不同事实

不要把某个 SDK 的 `usage.input` 直接称为总输入。一些接口把未缓存输入、缓存创建和缓存读取分开报告；另一些接口的 input 已含缓存，缓存字段只是其中的子集。映射必须按实际 Provider／适配协议版本确定。

| 已确认的口径 | 总输入计算 | 不能做的事 |
|---|---|---|
| 各输入桶互斥 | 未缓存＋缓存创建＋缓存读取 | 只统计未缓存；把缓存创建的 TTL 子分类再加一次 |
| input 已含缓存 | 直接使用 input；缓存仅作分解 | 再加缓存读取造成重复计算 |
| 口径未知／部分字段缺失 | 保留原回执，报告已知项与未知总量 | 用零填补缺失后声称完整总输入 |

同理，output 是否包含隐藏推理、不同输出子项是否重叠，也必须按接口解释。流式 usage 有些是累计、有些是增量，先按 request ID 聚合终值或差量；重放同一个观测事件不再计费，真正发出的另一次技术请求则需要另计。一个根任务的总量按底层真实请求去重汇总，不能再叠加父 Run 的递归汇总字段。

当前 Pi 遥测的 `message_end` 投影记录 `usage.input/output`，未一起记录 cacheRead/cacheWrite。这可作为为什么要显式定义口径的代码例子，不能据此判定所有 Provider 都采用相同解释。[04-G51](appendices.md#ref-04-g51) OpenTelemetry 当前 GenAI 指标区分客户端、服务端、Agent 和工具操作，且仍标为 Development；使用时应固定语义版本并映射，不将会演变的指标名嵌进治理内核。[04-W39](appendices.md#ref-04-w39)

**token 上下文合法，不代表请求体合法。** 在最终适配器序列化之后测量 UTF-8 字节，以及图片数、单图／总图字节、工具 Schema 和其他载荷。记录测量发生在压缩前还是压缩后、实际网关限制哪一层。不要用磁盘图片大小、字符数或 token 估计冒充真实请求字节。

成本报告分别保存用量、计价配置和账单。计价快照应带日期、币种、服务、缓存策略和折扣适用范围；没有价目或账单时报告资源数量，不编造美元金额。缓存命中可以降低计价或服务端计算，但不能证明客户端未再次发送完整图片与文本。

```yaml
# 计量示例，不是某个厂商的当前 API Schema。
usage_receipt:
  request_id: req-example
  normalization_profile: exclusive-input-buckets-v1
  input_uncached: 120
  input_cache_read: 1000
  input_cache_write: 200
  input_total: 1320
  output_total: 80
  output_reasoning: null
  usage_complete: true
  provider_receipt_ref: restricted-receipt-example
  pricing_snapshot_ref: null
  billing_status: not_available
```

附带的输入归一化函数只处理这两种**已由适配器确认**的口径，不识别厂商、不预测账单、不进行上下文截断。新 Provider 必须先验证映射，不能凭名称选择一个看起来合适的模式。

### 17.7 用可复核的范围衡量定点返工，而不是只统计“返工几次”

第 12 章已区分：修正责任集合 \(F\)、实际失效或受影响结果集合 \(A\)、需要复验集合 \(V\)。效率评估必须继续保留这三种对象类型；不能把一个 Review 复验算作重新生产，也不能把一个节点正常首次生产算作返工。

在可控夹具中，由独立参考事实给出必要修正工作 \(F^*\)、必要传播 \(A^*\)、必要复验 \(V^*\)。运行系统的集合分别与其比较。真实开放任务未必知道最小集合，应用人工标注或明确标记“未判定”，不能直接拿被测 Runtime 自己生成的影响集合充当真值。

| 指标 | 解释及必要限制 |
|---|---|
| 修复目标命中／遗漏 | 是否定位真实责任；集合为空时写 not_applicable，不强行得到 100% |
| 无关重产量 | \(F\setminus F^*\) 中的额外生产次数、模型调用和活动时间；不要只报节点数 |
| 失效遗漏 | 本应失效的结果或批准仍被采用；属于控制正确性问题，不能被节省成本抵消 |
| 复验有效性 | 受影响标准得到重验，同时避免无理由重复完全独立检查 |
| 问题复发与引入缺陷 | 原问题是否修好，修复是否引入新的可验证问题 |
| 独立成果保留 | D 的产物引用、Session、环境和必要在途工作是否保持；正常继续产生事件不算被扰动 |

贯穿夹具仍是 A 出错、B 消费 A、D 独立、R 联合评审：应由 A 原责任修复，B 根据真正的使用前提处理，R 重新取得必要判断，D 不重新生产。只有原质量批准失效而内容仍可保留的情况，按第 12 章执行重新核验采用，不为提高“局部率”继续使用无效批准。

再加入相反夹具：A、B 都正确，J 抄错或错误集成，此时修 J 而非强制回退 A、B。以及验证脚本错误、产品正确的夹具，此时修验证责任。**只有同时测“该返工谁”和“不该动谁”，指标才不会奖励全图回退。**

生产图设计不同，节点数不可直接比较。跨方案应按外部工作义务、成果和调用成本归一；把一个工作拆成十个节点，不能凭“只返工一个节点”宣称放大范围更小。

<a id="s17-08"></a>

### 17.8 容量保护要覆盖活动与驻留，也要避免把正常工作误判为停滞

第 13—15 章的根级资源限制需要对应观测：活跃模型请求、运行中工具／进程、排队长度与年龄、保留 Session、环境驻留内存、输入副本与导出字节、日志积压、子任务累计创建和并发数。父等待子释放活动槽后，仍保留的内存和环境不能记成零资源。

容量测试分别覆盖宽图、深图、长历史、多模态、频繁返工、多观察者和多 Run。一次一变量的阶梯测试先定位瓶颈，再测组合压力；记录拒绝、排队、取消响应和恢复，不只找到“没有崩溃时最大并发”。测试必须在授权隔离环境进行，保护条件不能为了压测得高分临时关闭。

停滞识别以证据为基础：同一失败重复提交、同一失效输入持续被使用、相同检索和编辑没有新增有效信息，可以触发诊断或有限恢复。长时间阅读、一次耗时较长的合法计算不自动等于停滞。保护机制可以暂停、阻塞或请求合适变更，但不能在次数耗尽时强制 PASS，也不能自行增加新 Agent 掩盖当前上下文故障。

<a id="s17-09"></a>

### 17.9 优先消除可证明的无效工作，再优化基础设施

| 已观测现象 | 优先检查与改变 | 保留的验证边界 |
|---|---|---|
| 长 JSON／代码来回补正 | 结构化对象输入、明确诊断、受限预检、较小可独立修改单元 | 工具 Schema 与产物契约仍一致，不能只删掉出错字段 |
| 相同资料反复全量读取 | 原件外置、紧凑消费索引、按标准定位、适用缓存 | 摘要不代替证据，授权与版本不能跨 Run 错用 |
| 历史和图片不断重发 | 有来源的请求视图、分批检查、合理压缩和最终字节准入 | 不删除最新必要证据，不更换原责任 Session 来逃避容量问题 |
| 同一检查／编译重复且输入未变 | 按完整输入、规则、资源版本缓存验证结果 | 缓存有效不等于产物批准；检查器或权限变化需失效 |
| 多个无依赖分支串行 | 校验输入相容后并行，取消无必要批屏障 | 不能将实际上依赖共同设计的工作伪装为独立 |
| 模型承担固定数据整理 | 将确定性序列化、哈希、筛选、验证交给代码 | 业务判断不偷换为未经验证的规则 |
| 节点越来越多却没有净收益 | 合并无独立责任的步骤，采用较小治理 Profile | 不删必需专业职责或阶段出口 |
| 环境准备重、重复安装 | 预置稳定依赖，按可信内容复用镜像和只读资产 | 用户数据、写工作区和凭据不跨不信任范围共享 |
| 状态写放大、UI 读开销上升 | 静态对象外置、索引、投影缓存、有界更新 | 唯一权威存储与提交原子性不被弱化 |

每项改变单独记录假设、测量、质量回归和失败场景。不要在同一次实验中同时换模型、缩规范、增成员、换环境，再把改进统一归因于“流程优化”。发现根本契约错误时优先修正确性，不要求先做大样本性能研究才能修 bug。

<a id="s17-10"></a>

### 17.10 让观测自身轻量、可关闭、可失效

当前 `FileRunStore` 的外层 span 包含排队到提交的过程，而 `onMutationMetric.durationMs` 从获取写锁后开始计时；两者虽然都叫时长，却不代表相同范围。[04-G52](appendices.md#ref-04-g52) 优化前应拆明队列等待、锁获得、读取／解码、状态转换、序列化、落盘与通知。不能看到 mutation 很快，就排除其外层排队很长；也不能将每个层级 span 求和当总时间。

首版遥测建议采用批量、有界队列和关闭期限。缓冲满时，低价值样本可采样／合并／丢弃并计数；正式审计事实走自己的可靠提交路径。指标写失败只影响可观测性状态，不把已完成任务改成失败；但涉及业务所需审计存储失败时，应按第 14 章处理，不能伪装普通遥测异常。

慢观察者不得占住状态事务。UI 根据 revision／游标拉取或订阅投影；断线、乱序、缓存过期时重新读取权威快照。静态 HTML 快照应声明生成时点，不显示为实时；查看或下载动作不能再次驱动业务执行。

日志采用字段允许列表和按需调试。原始错误可能带 API key、路径、客户内容和 URL 参数，不能默认外传。不得以记录秘密的普通哈希代替脱敏；低熵秘密仍可能被枚举。保留对账所需的安全引用，不把敏感凭据放进产物或共享报告。

<a id="s17-11"></a>

### 17.11 历史 Run 应当成为诊断教材，不成为未经对照的收益宣传

本项目历史样本 `20260917T150740223Z` 的既有审计记录了：事件跨度约 9 小时 52 分，成员活动区间并集约 4 小时 12 分，其中一次暂停到人工恢复约 5 小时 40 分；607 条模型消息、752 次工具调用，最终仍为 paused。它由用户手工选择流程并复用模板，没有 ST／工作流设计师自动治理过程，也没有正式质量 REWORK。[04-S13](appendices.md#ref-04-s13)

这份样本可以支持“要区分暂停与活动”“不要把业务视觉设计误认为控制层设计”“容量不只看 token”“泛化诊断会增加补正成本”等经验。它不能证明阶段评审优于逐点评审、子 IPD 能提高成功率、定点返工已经充分验证，或方法比单 Agent 慢多少；因为没有这些对照和实际路径。

本批复核既有指标文件中的口径，并用附带区间函数重算其七个 Attempt 的活动量，不重新执行原业务。原审计未取得最终产物、完整 Provider 请求抓包和服务端耗时，因此继续保留这些限制。请求内容字节下界足以解释特定故障，却不是历史原始 HTTP 请求的字节级副本。

**经验要落到反例和接口，而不是落成固定魔法数字。** 某模型网关曾报约 6 MiB 上限，不意味着所有 Provider 都设相同上限；某次低并发来自串行责任，不意味着永远不用提高并发；某次重写检查器发生错误，也不意味着禁止所有合法的检查器修复。

## 第 18 章　质量验证与故障验证

<a id="s18-01"></a>

### 18.1 分开四个问题，才能知道测试到底证明了什么

| 要证明的问题 | 最合适的证据 | 不能替代它的证据 |
|---|---|---|
| **控制规则是否正确** | 领域模型测试、负向用例、并发和崩溃故障注入 | 真实模型恰好配合、看板全绿 |
| **Harness 适配是否忠实** | 原生 Session＋受控模型替身、真实工具／环境、协议契约测试 | 只 Mock 掉整个成员执行器 |
| **真实任务是否完成** | 确切最终成果／外部状态、独立判定和真实运行 | Runtime 说 succeeded、Reviewer 自报 PASS |
| **协作组织是否有净收益** | 固定任务集上的公平对照、重复运行、分项成本与质量 | 单次成功演示、更多角色、更长日志 |

本方法的 Runtime 只能保证已经形式化并正确实现的控制关系，不能保证 Reviewer 的专业判断永远正确。因此既要测非法批准是否被系统拒绝，也要测一个结构完全合法、内容却误判的 Review 是否会造成缺陷逃逸。

华为云公开测试评估实践区分产品质量报告与测试执行过程总结，分别用于判断被测对象和改进测试活动。[04-W41](appendices.md#ref-04-w41) 本文借用这一分工：**任务成果质量、控制引擎质量、评测工具质量各有证据**，不把写出一份漂亮评测报告视为三者已经通过。Anthropic 的 Agent eval 实践也区分任务、trial、过程记录与最终环境 outcome；本文的 trial 是完整评测重复，不是前文技术 Attempt。[04-W43](appendices.md#ref-04-w43)

<a id="s18-02"></a>

### 18.2 用分层测试控制成本，真实模型不是每一层的前提

| 层级 | 被测对象 | 基本方法 | 典型失败 |
|---|---|---|---|
| L0 契约与纯规则 | Schema、引用、依赖、批准、完成和影响计算 | 固定夹具、属性测试、变形测试 | 缺必需 Review 仍成功；局部问题扩大成全图 |
| L1 持久化与执行协议 | 命令、认领、代际、回执、等待、对账 | 临时真实存储、受控时钟、重复／乱序／中断 | 回执丢失重复副作用；子完成早到导致父永远等 |
| L2 原生 Harness 与环境 | 会话、工具循环、上下文、进程、权限 | 原生 Session＋模型替身，真实文件／容器／工具 | submit 后模型继续执行；Shell 越界或进程未停 |
| L3 小型真实端到端 | ST／Designer／执行／评审完整链或明确模板路径 | 真模型、真工具、小任务、独立终态校验 | 模型不理解契约、诊断导致反复猜测 |
| L4 能力与收益评测 | 任务集、组织方式、成本与稳定性 | 同条件对照、重复运行、盲评与分层分析 | 简单任务过度治理；复杂任务看似快但缺陷增加 |

模型替身应模拟不配合、漏提交、无效参数、晚回执、容量错误和不完整证据，而非永远按剧本输出正确结果。它能够验证执行协议，却不能证明实际模型会稳定使用工具或理解规范。

本指导前文已运行的 Python 纯函数构造用例，只属于 L0 的有限示例检查；不自动计入 Pi 或 Jiuwen 的 L1—L4 通过记录。先运行便宜且高信息量的测试，再把真实模型投入到无法由确定性测试证明的部分。

<a id="s18-03"></a>

### 18.3 建立独立参考模型，避免“被测代码验证自己”

测试应有简单、透明的参考规则：输入版本是否有效、哪些标准有当前证据、哪个义务尚未完成、某事件是否可采用。不要直接调用同一个 `computeImpact()` 既生成实际结果，又生成期望结果；这种测试只能发现序列化或调用失败，无法发现共同逻辑错误。

属性测试可以生成不同顺序、宽度、共享依赖和多个 Review 的工作流，再运行创建、提交、批准、返工、暂停、恢复和取消序列。Hypothesis 的 stateful testing 支持用规则和状态模型比较系统行为；它提供生成与缩减方法，并不替我们定义正确性。[04-W44](appendices.md#ref-04-w44)

适合本方法的变形关系包括：添加一个真正独立 D 不应改变 A/B 的合法性；重排无依赖事件不应改变最终语义；同一合法回执重复不增加提交；只增加遥测事件不应撤销执行资格；更换显示名不应改变身份；重新物化同一输入不应改变内容证明；将业务失败报告写得更积极不能使被测产品通过。

失败后保留可重放的随机种子、最小反例、版本和时序。验证 reference model 与生产逻辑的分离，不以测试代码行数为目标；能够解释一个五步反例，比一万条无法定位的失败日志更有价值。

<a id="s18-04"></a>

### 18.4 将历史事故转成故障夹具，并同时验证“不应发生什么”

下面不是重复第三部分全部验收表，而是推荐优先落地的贯穿夹具族。每族引用前文对应责任，至少有一个可通过的正向路径和一个真正触发拒绝／恢复的负向路径。

| 夹具族 | 注入点或输入 | 必查结果 | 关联前文 |
|---|---|---|---|
| 任务与标准漂移 | 上游把可调整设计建议标成用户硬要求 | 来源冲突显式出现，不能静默扩张标准 | 07、11、16 |
| 诊断完整性 | JSON 缺逗号、字段非法或环境命令缺失 | 保留具体路径／位置／条件，原 Session 获得可行动反馈 | 09、10、14 |
| 多模态容量 | 最终请求超过代理字节限制而 token 未满 | 新证据仍被合法处理；原样恢复不形成循环 | 09、17 |
| 候选封存 | 导出中工作文件变化或登记前中断 | 不暴露混合版本；未登记文件不是可评审 Submission | 11、14 |
| 联合评审失效 | A 改变、R 依赖 A+B | R 相关批准失效，未解决 Finding 保留 | 12 |
| 定点修复 | A 错、B 依赖 A、D 独立；以及 J 单独抄错 | A/B/R 或 J 被准确处理，D 不重产 | 12—16 |
| 完成条件 | 必需 Review 未执行、文件版本在打包中改变 | 不因 Promise 完成或另一版通过而成功 | 13 |
| 取消竞态 | 撤销后旧模型和工具回执晚到 | 不采用结果；旧写入确实停止或被隔离 | 10、13、14 |
| 未知副作用 | 服务端已接受动作、客户端未收到结果 | 按原业务操作 ID 对账，不盲目重复 | 14 |
| 父子等待 | 子完成先于父登记等待、活动槽仅一个 | 不丢唤醒、不死锁、不重复创建 | 13、15 |
| 局部变更 | J/R 换基线、D 仍在运行 | D 按明确续接条件保留，旧未解问题不清零 | 16 |
| 展示与发布 | 客户端脚本语法错、接口新 Schema、离线快照 | 真实浏览器可见变化；展示故障不改主流程 | 13、20 |

例如定点返工夹具应显式写出观察，不用一个泛化的 `all_pass=true`：

```yaml
# 评测夹具的逻辑表达，不是实际 WorkflowDefinition。
scenario:
  id: locality-A-B-D-R
  baseline_ref: fixture-stage-v1
  fault:
    point: after_candidate_A1_registered
    kind: domain_defect
    object_ref: artifact-A1
  oracle:
    repair_owners: [A]
    refresh_consumers: [B]
    repeat_review: [R]
    keep_valid_production: [D]
    retain_sessions: [session-A, session-B, session-D, session-R]
  observations:
    - assert_no_new_production_attempt_for: D
    - assert_no_dispose_or_environment_reset_for: D
    - assert_old_release_not_used_by: next-stage
    - assert_repair_returns_to: session-A
    - assert_final_result_uses: artifact-A2
```

这只适用于夹具中已明示 B 的结果确实依赖 A 正确的条件。若 B 是记录 A 失败的真实测试报告，其依赖类型不同，另一个正向夹具应证明它可以保留。不能为了方便测量把所有来源边都改成正确性依赖。

<a id="s18-05"></a>

### 18.5 故障注入按实际提交边界设计，不用 sleep 猜测竞态

至少覆盖：命令登记前后、外部启动前后、动作已发生但回执未登记、候选封存后但状态未提交、Review 登记与失效竞态、最终包生成与采用之间、停止请求与停止确认之间、父子事件投递前后、检查点记录前后。

用确定的 barrier／hook 暂停在边界，再注入故障；单靠“睡 100 ms 再 kill”会因机器速度变化漏掉目标竞态。夹具记录准确的注入确认；故障未发生就属于无效测试，不能被算作恢复成功。

异常抛出、进程被杀、容器终止、磁盘写满、文件损坏、主机掉电和远端动作回执丢失是不同故障。只测试抛异常，不能宣称通过断电恢复。真实副作用优先用拥有持久对账记录的隔离测试服务，不对生产支付、删除或发信目标做破坏性试验。

每个恢复测试同时验证 safety 与 liveness：既不能采用非法结果，也应在前置条件恢复且存在合法路径后最终继续。永远拒绝提交可以轻易通过“没有错误批准”，却不能构成可用运行时。计时期限服务于测试终止，并与目标运行配置对应，不反向创造业务质量阈值。

<a id="s18-06"></a>

### 18.6 最终质量判定应独立于被测系统的自评

评测者接收确切最终产物、原始任务与合法来源、必要的环境结果；不把内部 PASS、角色名和长篇完成声明当成正确性的替代。软件检查真实行为和回归，数据报告复核计算与来源，内容成果检查覆盖、证据、限制和实际可用性，外部动作检查目标系统中是否真实发生。

确定性检查优先用于可形式化条件；语义判断使用有明确尺度的领域评审、模型评分或人工校准。研究／内容等任务允许多种正确表达，不能因为没有遵循某一固定工具序列而判错；真正的授权、证据和必经责任属于协议约束，必须检查，两者不能混淆。[04-W43](appendices.md#ref-04-w43)

评分器也会出错。为每类评分器保留合格参考成果、不合格变体、边界样本和证据缺失样本；将评分器版本与任务集一起锁定。模型评分器应检查位置、冗长、自我宣传和注入偏差，随机化或交换 A/B 位置，保留无法判断选项，定期与专业判断核对。不同模型只是减少共同盲点的一个手段，不是独立性的充分条件。

评测环境中的人工审阅只用于开发和判断，不意味着业务 Runtime 必须增加 HITL。测试题可以隐藏答案和独立检查，但不能偷偷增加用户未声明的文件名、技术路线或商业要求，再惩罚合理方案。

<a id="s18-07"></a>

### 18.7 任务集同时包含应协作与不应协作的任务

任务集按责任跨度、依赖长度、专业差异、并行机会、隐蔽缺陷、验证成本和信息不确定性分层。长程不简单等于实际跑了很久；一个反复出错的小任务可以跑两小时，却没有多阶段责任复杂度。

建议至少覆盖：即时小任务、清楚的模板任务、需要任务化设计的多专业任务、强串行任务、真实可并行任务、跨成果一致性任务、资料不足必须诚实阻塞的任务、局部错误应精确返工的任务，以及确有独立子治理价值的任务。故障合成集与自然任务集分别报告，不能把大量容易拒绝的非法输入混进成功率来提高数字。

先从真实失败建立回归集，再扩展未解决能力集；回归集不应不断被改成“刚好让当前版本通过”。开发、选择配置和最终比较的任务分开，锁定持出集；同源模板、相近变体和同一次事故不能随意散到不同集合造成信息泄漏。

公共 benchmark 用于补充任务类型和可比性，但不要求它原生多 Agent 才能使用。选择时核对交互、环境、交付和评分是否覆盖本方法需要证明的性质；例如一个只检查最终文件的基准，不会自动评估原 Session 返工或旧批准失效。这些仍需本地协议夹具。当前章节不推荐一长串未经逐项适配的 benchmark，也不把 PPT 穿刺作为全领域方法的唯一证明。

<a id="s18-08"></a>

### 18.8 对照设计要区分“治理有效”与“多用了资源”

按问题选择少量必要组，不必每次跑满所有组合：

| 对照组 | 目的 | 必须控制的差异 |
|---|---|---|
| 同 Harness 单 Agent | 基础能力与成本基线 | 不故意拿走可用工具、数据和相关 Skill |
| 单成员受控工作流 | 检验显式交接和质量闭环 | 记录新增治理开销，最终判据一致 |
| 阶段门禁与较细门禁 | 检验门禁位置和流程税 | 必需质量义务不能被削弱；适用规范不同须公开 |
| 静态专业团队 | 检验专业分工／真实并行 | 模型配置、总资源额度与整合成本可见 |
| 受限子 IPD | 检验局部独立治理价值 | 深度、宽度、创建数、等待和父级采用都有记录 |

有两种合法但回答不同问题的比较：**同资源约束下的质量比较**，与**按各自默认产品配置的整体方案比较**。后者可以用不同模型、不同上下文或更多调用，但必须承认结果是整体系统差异，不把全部收益归因于组织结构。测质量—成本曲线时应改变一项资源条件并保持其他条件可解释。

手工挑规范和预编译模板，不能当自动 ST／Designer 的成功证据。治理准备的能力与成本应单独分层：固定模板路径、自动规范选择路径、自动任务化设计路径、完整端到端路径。评测集输入模式和预处理也保持一致。

每个 trial 从隔离初态开始；不能让后运行组读取前运行组的产物、Git 历史、共享长期记忆或带答案的缓存。冷／热缓存、共同只读依赖、服务端缓存不可控状态分别记录。对外部实时检索，可用固定语料快照做可重复对照，再补充实时运行；快照不能冒充完全真实的开放网络条件。

<a id="s18-09"></a>

### 18.9 指标必须有分母、观察窗口和未完成状态

| 指标 | 推荐定义 | 主要防误用点 |
|---|---|---|
| 任务交付成功率 | 独立验收通过的有效试验数／进入该能力评测的有效试验数 | 暂停、超时、取消和有效失败保留；评测设施损坏单列并公开 |
| 正确阻塞率 | 应阻塞样本中，原因和所需条件均正确的比例 | 与正常可完成任务的成功率分开，不奖励一律阻塞 |
| 缺陷逃逸 | 发布／交付结果中独立发现的严重缺陷；同时报任务级和缺陷级口径 | 没有独立审计就不能声称零逃逸；缺陷样本分布需说明 |
| Review 检出与误报 | 在有真值的候选集上区分 TP、FP、FN、TN | 不能用 gate 通过率代替准确率；弃判／阻塞另记 |
| 返工收益 | 修复前后同标准的变化、额外成本、引入新问题 | 只统计返工次数无法判断好坏；参照 §17.7 |
| 恢复成功率 | 故障已确认注入且前提满足的样本中，保持不变量并继续的比例 | 注入失败、不可恢复和设施问题分别报告 |
| 成功交付成本 | 全部有效试验消耗／成功交付数，并附成功条件下成本分布 | 失败消耗不能丢；成功数为零时不输出有限均值 |
| 延迟与尾部 | 分别报全部观察状态和成功样本历时分布 | 只取已成功样本会产生幸存者偏差；小样本不伪装稳定 p99 |
| 运维与人工介入 | 人工分钟、暂停救援、配置修复与复测 | 人工代修后仍算“完全自治成功”属于错误归因 |

未完成观察是右截尾，不等于失败发生的精确时刻；若按固定任务期限判失败，要提前声明该期限。结果可以同时报告产品成功／未成功和时间统计中的截尾性质。未经对齐的模型消息、工具调用、成员 Activity 不应混作同一种“步骤”。

重复运行时，以任务为分析单位保留 trial；若多个任务来自同一模板族，还要考虑族内相关性。配对比较优先在相同任务和条件下计算差值，再按任务／任务族分层重采样；不能把几千次工具调用当几千个独立任务样本。SciPy 的 paired bootstrap 能保证成对索引一起重采样，但聚类单位、缺失处理和试验设计仍须自行确定。[04-W45](appendices.md#ref-04-w45)

重复采样不是自动证明稳定。固定模型别名和随机种子也不能保证远端服务绝对确定。先报告样本、差值、区间和实际意义；小样本作为探索，不宣称最终普遍收益。零故障也应报告试验范围；即使在独立同分布的二项假设下，零次故障的概率为 \((1-p)^n\)，有限次观测仍允许非零真实故障率。

`pass@k` 回答有多次尝试时至少一次成功的机会，不能冒充用户只提交一次的成功率。若产品会自行选择多个候选，必须把实际选择策略、所有尝试成本和选错风险纳入评测；使用隐藏真值挑最好结果只是诊断上限，不是部署能力。[04-W43](appendices.md#ref-04-w43)

<a id="s18-10"></a>

### 18.10 用消融实验找收益来源，但不能把违规流程当合法部署

有意义的消融包括：保留／去掉专业角色内容，保留／去掉紧凑交接视图，详细／泛化诊断，单成员／团队，细门禁／阶段门禁，受限子流程／直接局部执行。每次说明其他机制是否保持，避免同时更换模型和任务难度。

研究环境可以使用无独立评审的对照，用于回答评审有什么价值；如果目标 ProcessSpec 明确要求独立评审，该对照不符合正式部署规范，结果不能直接当作上线候选。也不能故意削弱单 Agent 工具或缩小上下文，制造看似有利的多 Agent 结果。

对“专业团队更好”的结论，还应区分专业画像、额外调用、上下文隔离、并行和独立证据各自的作用。样本有限时不必跑全因子设计，但应诚实把结论写成“该配置组合在该任务层有效”，而非已经识别了唯一因果机制。

<a id="s18-11"></a>

### 18.11 发布报告明确建议与未证实，不让指标驱动新的形式主义

```yaml
# 发布评估记录；pending 表示本示例没有填入实测结果。
evaluation_release:
  experiment_id: staged-collaboration-eval-v1
  task_set_ref: heldout-task-set-v1
  candidate_build_ref: candidate-build-id
  baseline_build_ref: baseline-build-id
  environment_profile_ref: eval-environment-v1
  outcome_grader_ref: independent-outcome-grader-v1
  protocol_suite_ref: governed-runtime-conformance-v1
  unit_of_analysis: task
  repeated_trials_policy_ref: repeat-policy-v1
  valid_trial_count: null
  excluded_trials: []
  safety_conformance: pending
  task_quality: pending
  locality_and_recovery: pending
  latency_and_cost: pending
  judge_calibration: pending
  deployment_recommendation: pending_evidence
  limitations:
    - 本例只定义应记录什么，不代表已经执行评测。
```

发布判断至少检查：已启用能力的关键不变量是否通过；最终质量是否达到声明目标；故障路径是否安全且可恢复到声明级别；复杂协作收益是否值得成本；未完成和排除样本是否透明；新版本是否影响已有 Run 和资产。

安全违规不能被高平均质量分冲抵，统计未显著也不等于两个方案等价。无足够收益证据时可以仅保留实验开关，或继续使用较简单配置。发布本身可由工程团队完成，不强制在业务 Runtime 中增加人审步骤。

每次事故按“原始记录—最小复现—修复—回归—任务再测”沉淀。指标指导资产下一版本修改，但不能改变正在执行的 Run 的验收依据。发现评分器问题时版本化修复并重评可比样本，不只修对自己有利的一半结果。能力评测与回归套件分别维护，防止把追求新能力变成破坏旧能力的理由。

### 18.12 本章实施验收

| 编号 | 场景 | 期望结果 |
|---|---|---|
| T18-01 | Runtime 全绿但独立输出检查发现错误 | 任务不算成功，保留结构合法与语义错误的区别 |
| T18-02 | 评测模型替身总是正确配合 | 补充负向替身；不以此宣称真实模型质量 |
| T18-03 | 正确成果未遵循某个非必需工具顺序 | 不因偏好路径误判；真实授权义务仍检查 |
| T18-04 | 固定夹具新增独立 D 或重排独立事件 | 原责任语义不改变，D 不无故返工或取消 |
| T18-05 | 故障注入未到达目标边界 | 标识无效测试，不计恢复成功 |
| T18-06 | 只做异常抛出测试 | 不宣称掉电、跨进程或实际副作用恢复已验证 |
| T18-07 | 应正常完成与应阻塞两类任务 | 同时检查完成和诚实阻塞，不奖励一律拒绝 |
| T18-08 | 后运行组能访问前组答案或缓存 | 隔离并作废污染试验，保留重跑与排除记录 |
| T18-09 | 多次试验只有最好一次成功 | 报真实策略与全部成本，不以隐藏真值 best-of 冒充一次成功 |
| T18-10 | 同任务重复 trial、不同任务数量悬殊 | 以正确任务／族单位统计，不用调用数虚增样本 |
| T18-11 | 未完成与失败样本昂贵 | 保留消耗和观察状态，不只汇报成功样本成本 |
| T18-12 | 评分器偏爱长回答或某个位置 | 校准、交换次序、保留弃判与分歧，不盲信单次总分 |
| T18-13 | 更快方案移除了规范必需 Gate | 可作标明不合规的研究对照，不当合法上线版本 |
| T18-14 | 局部返工次数少但遗漏真实依赖失效 | 控制验收失败，不能以成本更低抵消 |
| T18-15 | 发现任务或评分器错误 | 版本化修正并重评可比样本，不静默改单侧判据 |
| T18-16 | 复杂团队未证明比简单配置有净收益 | 继续实验或回到简单配置，不把规模当完成标准 |
