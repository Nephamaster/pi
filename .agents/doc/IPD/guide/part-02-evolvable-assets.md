## 第 03 章　资产分类、引用、发现与发布

<a id="s03-01"></a>

### 3.1 先区分可复用定义、任务绑定和实际运行记录

一份资产应有清楚的复用对象。数字员工复用专业责任和方法，流程规范复用组织与质量要求，工作流模板复用一种具体组织方案，Skill 复用作业方法。任务中的输入、授权、实例身份与执行结果，则不能因为也保存在文件中，就一并变成下一次任务的默认资产。

| 对象 | 定义和主要使用者 | 不应承担的内容 |
|---|---|---|
| 数字员工／AgentCard | 描述一个专业角色的职责、边界、方法和能力需求；供设计者选人、成员执行时参考 | 当前节点的全部任务、既有会话记忆、真实执业资格、默认拥有的任意系统权限 |
| 流程规范／ProcessSpec | 定义一类任务必须保留的活动、成果、专业责任、评审与交接规则；供 ST、设计者和校验机制使用 | 当前任务唯一的 DAG、具体文件路径、每次模型调用、某个固定员工名单 |
| 工作流模板／WorkflowTemplate | 在明确适用条件下复用节点责任、依赖、交付与检查关系；供启动器或设计者实例化 | 旧 Run 的数据、Session、状态、批准记录和未经声明的客户特定假设 |
| Skill | 描述如何完成一类专业工作，并可携带脚本、参考资料和模板；供获准成员按需使用 | 独立的调度引擎、权限发放者、事实数据库、自动获得调用资格的所有工具 |
| 工具能力／Tool | 可实际调用的操作接口，包含参数、返回、错误、身份和副作用约定；供宿主注册和成员调用 | 仅凭文字声明的能力、不能定位实现的函数名、未经核验的“安全”标签 |
| 环境配置／Execution Profile | 描述执行所需的基础软件、运行条件和约束；供装配器及环境适配器使用 | 某次容器的可变工作区、用户凭证、当前进程的生命周期状态 |
| 知识资源 | 描述授权范围内的资料集合或查询入口；供成员查证和获取任务信息 | 默认可信的所有返回内容、授权之外的数据、永远不变的线上事实 |
| 检查器／Check | 把特定标准的一部分转化为可执行验证，明确能证明的范围；供 Runtime 或获准验证成员使用 | 仅有名称而没有实现的检查、包办所有语义质量的通用 PASS |
| 角色协议与提示模板 | 承载公共边界及执行、评审、选型、设计等角色的稳定作业协议；供 Harness 组装 | 另一份手工维护的工具参数 Schema、任务状态账本或员工履历 |

**当前工作流定义和执行基线是资产的消费结果，Run 记录是实际执行事实。** 某次成功工作流可以经过整理成为模板，某段有效脚本可以经过检验成为 Skill 资源，但它们不会因为“保存下来”就自动获得通用性、发布资格或下一次任务的授权。

这一分层延续总纲中的流程与角色解耦、Skill 与 Tool 分工，以及 Agency 分析中的单一资产源思想。[02-S01](appendices.md#ref-02-s01)[02-S02](appendices.md#ref-02-s02)[02-S07](appendices.md#ref-02-s07) 它不要求把角色、工具、环境完全拆成互不相干的文件，而要求各字段的责任不能混淆。

### 3.2 每项资产同时具有内容、可信来源和可用性，但三者不是一回事

以一个“API 测试工程师”为例：角色方法写得充分，只能说明资产表达了相应专业责任；附带一个 `api-test` Skill，只能说明存在一份方法资源；实际完成测试还取决于脚本、依赖、被测版本、环境、权限和可观察结果。

建议分别回答四个问题：

| 判断 | 依据 | 不能推导出的结论 |
|---|---|---|
| 内容是否有效 | Schema、引用、内部一致性和必要的专业审查 | 能在当前机器执行 |
| 来源是否获准 | 来源记录、发布者或维护者、项目信任策略 | 内容必然正确，没有恶意或缺陷 |
| 本次是否适用 | 当前任务、规范边界、专业职责和交付要求 | 当前工具与数据已经齐备 |
| 本次是否可执行 | 精确资源绑定、依赖检查、环境和授权 | 最终成果一定满足全部要求 |

因此，目录中应能够区分“未发布”“已发布但当前不可用”“可用于当前环境”“已被本 Run 锁定”。这些状态是不同维度，不必压成一个越来越长的总枚举。例如，某个硬件可靠性测试规范可以是内容完整的已发布规范，但当前环境没有测量设备；不能把它误称为无效规范，也不能用 API Tester 替代真实物理验证。[02-S09](appendices.md#ref-02-s09)

对流程选择尤其要保留这一区分：ST 判断哪份规范适合任务；装配和设计判断当前资源能否满足它。资源缺口应以结构化原因返回，而不是让 ST 为了让流程跑通而篡改任务类型。

### 3.3 资产身份：名称用于理解，版本用于发布，摘要用于确认内容

至少应区分以下身份：

| 身份 | 用途 | 规则 |
|---|---|---|
| 资产类型与稳定 ID | 找到同一类可复用对象 | 不使用展示名称或本地绝对路径充当唯一身份；多来源同名时要有命名空间或明确冲突规则 |
| Schema 版本 | 说明字段和结构如何解析 | 与资产内容版本分开；字段结构没变，不代表作业方法没变 |
| 发布版本 | 表示维护者发布的一份确定定义 | 相同发布身份不能悄悄指向不同内容 |
| 内容摘要／digest | 核对本次实际采用的内容 | 由代码计算，明确算法和覆盖范围，不要求设计模型生成 Hash |
| 来源与转换记录 | 追溯上游、内部编写、翻译或适配过程 | 保留仓库／文档版本、许可和适配说明；来源不是可执行权限 |
| Run 内绑定身份 | 说明哪个任务、节点、成员采用了它 | 不写回原资产，也不与角色 ID 混用 |

推荐的**逻辑引用形态**如下。具体字段名可以适配既有 Schema；`digest` 和 `content_ref` 由解析器填入。

```yaml
kind: agent_card
id: api-contract-reviewer
version: "1.0.0"
digest:
  algorithm: sha256
  value: "<由解析器计算的确定摘要>"
content_ref: "<内容快照引用，而非当前可变源路径>"
```

设计阶段可以根据名称或版本范围搜索，但执行前必须解析到确切对象。`latest`、默认版本或本机搜索路径只可作为选择策略，不应成为活动 Run 每次读取时重新解释的依据。若宿主资源没有发布版本，可用宿主注册身份加内容／构建身份锁定，不必为了形式统一而伪造一个 `1.0.0`。

**相同 ID 和版本被多来源注册时，默认拒绝歧义，不按目录遍历顺序覆盖。** 需要项目级替代时，应有明确的来源选择、派生版本或覆盖策略，并记录最后采用哪一份。当前 Pi 已对重复 AgentCard、ProcessSpec、Skill 身份进行拒绝；Workflow 存储对同版本同内容可复用，对同版本不同内容报告冲突。[02-G12](appendices.md#ref-02-g12)[02-G16](appendices.md#ref-02-g16)

#### 摘要必须说明到底锁住了什么

对 YAML／JSON 定义，可以选用“解析后的规范化内容”作为摘要对象；对 Skill 包，可以选用“规范相对路径及各文件字节摘要组成的 manifest”。但必须把规则写清楚，并在所有适配端一致实现。不能一端按原始 YAML 字节、一端按解析对象计算，却声称二者是同一种身份。

跨语言实现应固定重复键、缺失与空值、默认值、数值和 Unicode 的处理，提供同输入同摘要的测试向量。RFC 8785 的 JCS 可作为确定性 JSON 的一种参考，但使用它需要遵守其输入和序列化约束；不能仅做一次属性排序就声称兼容 JCS，也不要求所有实现必须采用它。[02-W11](appendices.md#ref-02-w11)

摘要的覆盖边界至少包括所有会改变实际方法的包内资源，而不是只计算 `SKILL.md`。跨包引用要锁定对应依赖；忽略的缓存或临时文件必须不参与正常作业。脚本若依赖执行位等元数据，要么纳入包规则，要么统一通过明确解释器执行。符号链接、包外路径和安装时生成的文件也必须有清楚边界。

当前 Pi 的 Skill 摘要包含目录内普通文件的相对路径与内容摘要，排除 `__pycache__`／`.pyc`，拒绝符号链接；快照复制后会再次核对摘要并设为只读。这是一个可借鉴的有界实现，不表示它已经锁定了脚本未来访问的所有外部内容。[02-G13](appendices.md#ref-02-g13)

还需要正视锁定能力的上限：**工具说明与参数 Schema 的摘要，不是工具执行代码的摘要。** 当前 Pi 的工具资产摘要覆盖名称、描述、参数和提示片段等注册信息，没有覆盖 `execute` 实现。[02-G12](appendices.md#ref-02-g12) 若需要更强的执行追溯，应同时记录宿主／插件构建版本；远端服务和模型即使保留同一名称，也可能发生不可由本地锁定的变化。应记录能取得的服务版本、调用时间和回执，不虚称完全可重现。

### 3.4 发现与装配：先检索候选，再读取完整资产，最后验证实际组合

最小资产目录可以用本地目录和派生索引实现。首先需要的是清楚的查询和解析行为，而不是向量数据库、资产市场或新的独立服务。

建议保留三个不同视图：**发布目录**保存规范内容及来源；**可用能力视图**说明当前宿主能执行什么及缺口；**本次锁定视图**记录最终实际绑定的资源。索引是派生结果，不与原文件共同成为内容真相。

一个轻量目录接口只需满足以下职责：

| 操作 | 返回的最小信息 | 关键边界 |
|---|---|---|
| 搜索／列出 | ID、版本、用途、适用边界、必要能力和简短不可用原因 | 仅用于缩小候选，不是最终选择依据；结果要分页或明确截断 |
| 读取确切版本 | 完整定义、来源、摘要、必要依赖 | 找不到就明确返回；不静默换为另一个版本 |
| 解析本次绑定 | 规范化定义、确切资源和依赖闭包 | 只解析已选择内容，不执行其脚本，不自动扩大权限 |
| 检查可执行条件 | 缺失资源、权限冲突、版本不匹配、环境能力缺口 | 区分资产问题与当前环境问题；诊断有路径和原因 |
| 准备锁定快照 | 与已解析摘要一致、受控读取的内容 | 准备后必须核对；不从可变源目录继续读取另一份内容 |

上表是接口责任，不要求五个独立类；已有 Registry、Loader 和 Compiler 能承担的部分直接复用。

对于数字员工，搜索可先按必需能力与真实工具资格过滤，再对职责、适用场景和方法排序；对于 ProcessSpec，先比较适用／排除条件，再精读强制义务。搜索排序不能决定准出。精确读到的版本与搜索时不一致，应重新核对或拒绝，而不是继续沿用旧判断。

当前 Pi 已提供 `search_process_specs/get_process_spec` 和 `search_agent_cards/get_agent_card`；员工搜索还支持 `capabilities_all/tools_all`，完整读取返回选人画像。这一渐进路径已经存在，后续不应退回全量注入全部角色与规范。[02-G15](appendices.md#ref-02-g15) 不过，当前关键词匹配、返回数量和元数据表达只是首版实现：库变大时先补分页、检索诊断和同义词／语言别名，再依据实际召回情况决定是否需要语义检索。

**故障范围也应局部化。** 未被本次选中的可选资产缺少运行依赖，通常可以标为不可用并给出原因；被选中的强依赖缺失，则必须阻止该绑定。身份冲突、内容完整性问题或来源信任问题不能被当作普通无关警告吞掉。当前 Pi 对部分员工资源缺失已有不可用记录，但某个 Skill 声明未知工具仍会使整次装配失败；是否调整为按候选隔离，需要在实现时明确，而不能在文档中当作已有行为。[02-G12](appendices.md#ref-02-g12)

### 3.5 从已选资产形成一次执行的锁定组合

一次任务的实际能力不是“员工卡里写了什么”的简单并集，而是专业责任、方法、工具、数据、环境和授权的组合。装配顺序建议为：

```text
确定任务与流程依据
  → 选择角色、方法和资源
  → 解析确切定义与依赖
  → 核对任务权限、环境和接口兼容
  → 固化绑定及内容身份
  → 为当前成员准备受控视图
```

关键原则是**先检查请求的绑定是否合法，再确认实际集合**。不要仅把所请求权限与允许集合取交集后悄悄继续：必需工具被滤掉时，应明确失败；只有本来就是可选且不影响交付的方法才可以省略。

锁定记录宜包含：流程和工作流来源、所选员工、Skill 包及依赖、工具接口和可取得的实现身份、检查器与参数、环境基础、知识源策略、模型实际配置，以及负责渲染和解释这些定义的协议／适配版本。ST 与 Designer 自己使用的私有 Skill 和角色协议也属于形成本次设计的依据，不能只记录业务员工。

当前 Pi 的 `EffectiveParticipant` 已把员工定义与所选的锁定 Skill、工具及知识资源引用分开表示；这可作为装配边界的参考，不能据此认定上述构建身份、来源和变更协议都已完整实现。[02-G19](appendices.md#ref-02-g19)

这不要求把所有包全文嵌进每个节点或状态文件。可保存内容寻址引用，由多个成员复用同一份只读快照；搜索索引、选择画像、运行画像均可由原资产派生。生成缓存的键应覆盖资产摘要与投影规则版本，不能只按角色名缓存。

有三类条件不适合假装永久冻结：**凭证和即时授权、外部服务可达性、实时数据内容**。它们需要在实际使用前核对。凭证通过受控后端按需注入，不写进资产、模板或可共享快照。某个锁定资源已不可用，应报告条件变化，不回退到宿主高权限工具或偷偷改用新模型。

<a id="s03-06"></a>

### 3.6 可演进：发布新定义，不重写旧任务的依据

建议将生命周期理解为两个相连但分开的循环：

```text
资产循环：草案 → 校验与试验 → 发布 → 使用反馈 → 新草案
运行循环：读取发布资产 → 精确绑定 → 执行和返工 → 归档证据
```

资产“发布”表示它在声明范围内可以被选择，不保证每次任务都适用。可以使用 `draft/released/deprecated` 等简单状态；需要安全撤回时另外记录撤回原因和生效规则，不强制首版建立复杂审批平台。

发布前应验证结构和引用、关键行为、适用边界、权限、依赖，以及受到改动影响的样例。修改选型描述要检验检索与选择，修改专业方法要检验任务行为，修改检查器要检验已知合格和不合格样例。不能只运行 YAML parser 就称为资产质量已验证。

运行反馈应进入**独立的观察记录**，关联资产摘要、任务类别、模型／宿主配置、环境、样本和终态。例如“研究包过长”“工具参数失败”“关键缺陷逃逸”是调查线索，不应直接让一个数字改写员工能力。通过率上升可能来自任务变简单或标准变弱，低返工率也可能意味着没有检查出问题；不能据此直接自动提权或替换发布版。

恢复和发布需要保持一致：活动 Run 继续使用原锁定内容；故障恢复可以重建执行实例，但不能顺便解析当前最新 Skill。旧版本回退适用于新的选择或明确变更，不自动撤销已经发生的外部动作。若资产因安全问题被撤回，可以按策略阻断继续使用，并记录受影响任务及处置；**冻结不意味着忽视安全撤回，但撤回也不授权静默替换内容。**

中英文翻译、角色措辞调整和示例修订也可能改变模型行为。即使字段与 ID 不变，也不应覆盖已经发布的同版本内容。可发布新版本，或采用明确的语言变体与修订身份；共享同一稳定 ID 不等于共享同一内容摘要。

首版用 Git、简单发布元数据、内容快照和测试记录即可承载这些责任。未来是否让 Agent 提出资产修订、运行对照评测或自动发布，属于额外受控能力；无需一开始就实现“资产自演进系统”。

<a id="s03-07"></a>

### 3.7 本章实施验收

最小资产链路至少应验证：同名不同源不能静默覆盖；同版本变更能被发现；脚本或 reference 改变会改变所需包身份；已锁定 Run 不受源目录随后编辑影响；未知／不可用资源返回可定位原因；旧快照损坏时不改读最新源来掩盖；发布观察记录更新不改变资产正文摘要。

**判断资产层是否轻量，不看它有多少文件，而看内容、索引、绑定和运行状态是否各自只有一个职责清楚的真相源。**

<a id="ch04"></a>

## 第 04 章　数字员工与参与者实例

<a id="s04-01"></a>

### 4.1 数字员工是专业责任资产，不是已经工作的实体

本指导继续使用“数字员工”这一表达，但在实现中必须分开三个层次：**AgentCard 描述可复用专业角色，Participant 是当前节点中承担责任的成员，Session 是该成员的持续执行载体。** 一个角色可以用于多个互不相同的成员；某个成员也不会因为进入第二轮返工就自动成为新人。

因此，员工库不保存“当前正在做哪一页”“上次读取了哪个文件”“本次已经通过哪个 Gate”。这些属于任务记录。反过来，当前节点也不需要重新生成一份完整的专业人格：它通过确切 AgentCard 引用取得稳定专业知识，再叠加任务契约和实际资源。

多人节点并不要求一个新的“万能团队员工卡”。当节点需要多种专业责任时，分别绑定成员及其贡献要求；是否分工、整合、评审或委派子流程，由局部执行计划和授权策略决定。团队结构及成员生命周期在第 15 章定义。

<a id="s04-02"></a>

### 4.2 一张可用员工卡，应让设计者判断其能承担什么以及不能承担什么

角色内容应从真实工作出发，而不是仅写“你是一名顶尖专家”。建议至少覆盖以下方面：

| 内容 | 好的表达 | 容易失效的表达 |
|---|---|---|
| 职责 | 分析 API 的兼容性、权限和错误语义，形成可定位的审查结果 | 负责所有质量，确保一切正确 |
| 非职责 | 不代替产品方决定业务优先级，不审批生产部署 | 尽一切努力完成任务 |
| 专业方法 | 对比接口前后版本，枚举旧客户端路径，核对测试证据和未覆盖范围 | 严谨、专业、高效 |
| 适用场景 | 接口演进、调用方迁移、兼容性审查；说明不适用对象 | 软件、法律、医疗、金融等所有任务 |
| 典型交付 | 发现清单、兼容矩阵、证据索引及其必要内容 | 每次固定输出一套与当前任务无关的长报告 |
| 验证参考 | 说明本领域何种证据能支持何种判断 | 无数据支撑的统一成功率、缺陷数量或效益阈值 |
| 能力标签与资源要求 | 便于检索的专业标签；实际需要的工具、资料和环境条件 | 有一个 capability 标签，就认为实际能力已经成立 |

职责允许在专业知识上有交集，但当前任务中每项正式贡献的责任应清楚。测试者和实现者都理解接口，不是角色设计失败；两人都以为对方负责准备测试环境、最终无人承担，才是责任缺口。也不宜为了让卡片看起来职责互斥，把专业背景切割到无法做出完整判断。

当前 Pi AgentCard 已有职责、非职责、能力、适用场景、原则、方法、典型交付、工具和模型配置等字段；这些字段值得保留。是否拆成“专业定义＋部署配置”两个文件可以由项目规模决定，但逻辑上应区分可迁移知识与宿主绑定。[02-G11](appendices.md#ref-02-g11)

<a id="s04-03"></a>

### 4.3 一个专业角色的示例，以及它与当前任务的关系

下面示例采用当前 AgentCard 常见字段名，展示内容粒度。角色、工具名和能力名为说明而设；它不是现有目录中的已注册员工，也不构成可直接编译的完整运行配置。

```yaml
id: api-contract-reviewer
version: "1.0.0"
name: API 契约与兼容性审查员
description: >-
  审查接口变更是否保持已承诺的请求、响应、错误、身份与兼容性语义，
  依据确切版本及调用方、测试证据形成结论，不以接口文档存在代替验证。
responsibilities:
  - 对比变更前后的请求、响应、错误和权限约定，定位破坏性变化。
  - 核对旧客户端、边界输入、重复调用和失败路径的实际证据。
  - 将发现关联到接口位置、受影响调用方、验收依据和复验条件。
nonResponsibilities:
  - 不决定新增业务功能的优先级，不代表业务方接受风险。
  - 不修改被评实现，不批准生产部署，不补造未执行测试。
capabilities:
  - api-contract-review
  - compatibility-analysis
applicableScenarios:
  - 软件接口演进、客户端迁移和跨服务契约核对。
principles:
  - 文档、实现和测试使用同一明确版本；不把旧版本通过记录用于新版本。
  - 区分确定缺陷、缺少证据和环境不可验证，不强制找出预设数量的问题。
  - 通用工作方法不是当前任务的新增验收标准。
deliverables:
  - 兼容性判断与发现清单，包含位置、触发条件、影响、证据和复验要求。
promptProfile:
  approach:
    - 先读原接口承诺和变更目标，再沿关键调用路径对照实现与证据。
    - 逐项检查字段、缺省值、错误码、权限及版本迁移，保留未验证范围。
    - 对有争议的结论说明缺少的证据，不用措辞强弱替代核验。
  communication:
    - 先给出影响和具体位置，再解释依据；建议与阻塞项分别表达。
  verification:
    - 重要判断能回到确定产物和冻结标准，不以审查员身份自证正确。
model:
  selection: run_default
  thinkingLevel: inherit
skills: []
tools: [read, grep, find, ls]
permissions:
  workspace: read
  readScopes: ["."]
  writeScopes: []
  externalActions: false
```

同一张卡用于“批量导出接口变更”任务时，实际绑定还应说明：成员身份、负责哪组标准、读取哪个接口与实现版本、可用哪些检查证据、允许使用哪些资源，以及通过哪种正式工具提交。卡片中的 `readScopes: ["."]` 也不能解释为读取宿主任意文件；实际可见根和授权输入由环境及当前绑定限定。

如果本次需要主动运行测试，而这个配置只有读取工具，不能因其叫“审查员”就假装完成动态验证。可以绑定经过授权的验证能力、安排验证成员生成证据，或如实报告缺口。修改验证工作区并不等于修改被评成果；是否允许以及如何隔离，由具体资源绑定决定。

<a id="s04-04"></a>

### 4.4 一个源定义，分别生成选人画像和运行指导

丰富角色知识应该保留，但不应全部常驻每个成员的模型请求。建议在同一源资产上生成两个视图：

**选人画像**面向工作流设计者，重点是适用与不适用场景、完整职责、非职责、方法、能力、典型交付和资源条件。设计者需要足够信息来比较候选，不能只根据名称或单个 capability 绑定。

**运行指导**面向已分配成员，保留角色定位、不可越过的专业边界和本次相关方法；任务目标、实际输出、证据和准出标准则由节点契约提供。可选专业细节继续按需读取，不把通用交付模板再当成一份额外必交清单。

当前 Pi 已分别实现 `renderAgentSelectionProfile()` 和 `renderAgentRuntimeProfile()`。运行投影保留角色、职责、边界、专业原则和工作方法；选人投影还包含适用场景、能力、通用交付、验证参考和资源权限信息。[02-G14](appendices.md#ref-02-g14) 后续优化应在这个分层上继续，而不是重新维护两套可独立漂移的员工 Prompt。

投影可以是确定性选择与渲染，不必额外调用模型压缩每张卡。对于较长方法，优先把可选专项内容放入 reference 或 Skill；必须保留的专业边界不能因为超长就随机截断。投影规则本身也应有版本和测试：某段“不能把模拟当实测”的约束不能在精简画像时丢失，而带有案例性质的固定数值不应被提升成当前验收门槛。

<a id="s04-05"></a>

### 4.5 从 Agency 等角色库转化：保留专业性，拆掉不实能力和越权承诺

外部角色模板的价值在于具体专业方法，而不是换上一个职称。应尽量保留其核心任务、常见工件、方法选择、边界条件、沟通方式和高级能力的适用前提。历史 Agency 分析同时提醒：角色中的记忆、自动编排和成功指标描述，不等于已经存在相应运行机制。[02-S07](appendices.md#ref-02-s07)

建议采用可审阅的转换表，而不是只保留一段极短摘要：

| 原角色内容 | 转化位置或处理方式 |
|---|---|
| Mission、核心工作 | 职责与适用场景；转为有专业对象的行为 |
| Workflow、Working Method | 稳定专业步骤保留在方法；长专项操作提取为 Skill/reference |
| Deliverables、模板 | 保留典型结构与信息要求，标明由当前契约决定是否需要 |
| Critical Rules | 区分专业原则、宿主安全规则与当前任务约束，分别归位 |
| Identity & Memory | 保留专业定位；不虚构真实资历、经历、私有记忆或已开展活动 |
| Success Metrics、示例阈值 | 保留可测量维度和适用条件；无依据数值不默认参与准出 |
| 工具、平台、框架清单 | 作为经验和依赖线索；实际资源必须另经注册和授权 |
| 自动调度、投资、发布等承诺 | 不从角色文案继承控制权；需要真实授权和运行协议 |

例如，“首次审查必须找到三至五个问题”应改成“未验证之前不预设通过，发现与结论必须有证据”。“熟悉 TensorFlow”可以保留为专业方法背景，但不意味着当前环境安装了 TensorFlow；“曾管理大型客户项目”不能被改写为该 Agent 的真实经历。

来源记录应保留原仓库、提交或文档版本、路径、许可位置、转换方法与重要取舍。当前 Schema 没有适合的 provenance 字段时，可以放在伴随元数据或发布索引中，不能擅自添加额外字段后宣称兼容现有解析器。多个语言版本也应能追溯到同一来源及各自的适配修订。

专业覆盖不需要固定一个角色数量。应围绕目标任务族保留有辨识度的专业角色，依据真实缺口增补；不要为了凑齐所有部门建立无人使用的卡，也不要把所有任务塞给“通用执行者＋通用评审者”。通用角色可作为范围有限的兜底，但不能替代所需的临床、安全、统计等专业判断。

<a id="s04-06"></a>

### 4.6 能力选择、资源授权和实例化必须分别完成

一项工作能否交给某成员，应同时满足：专业职责适合、方法可用、实际工具和数据到位、模型与环境符合任务条件、权限允许。能力标签只参与匹配，不构成这些条件的证明。

模型配置也应区分“角色偏好”和“本次实际选择”。例如卡片使用 `run_default`，执行基线应记录最终解析的 Provider、模型和相关设置；不能在恢复时再读取今天的默认值。相同角色配不同模型可能呈现不同效果，角色表现数据应保留该条件，而不是永久写一个脱离模型的“能力得分”。

对权限，建议用如下关系做校验，而非自动补齐：

```text
本成员请求的动作与读取范围
  必须同时满足：任务授权、可信宿主策略、角色／部署资格、节点需要
  并且当前环境实际能够执行
```

如果组件按集合实现，应验证 `requested ⊆ permitted`；不合法的必需项要返回诊断，而不是悄悄过滤后继续。成员有资格使用某工具，也不意味着每次都应发放它。

当前 Pi 已校验节点工具与员工允许清单、路径范围、Skill 必需工具及工具的伴随依赖。[02-G18](appendices.md#ref-02-g18) 这可以作为最小实现参考，但不会证明名称相同的任意工具都满足隔离和外部动作要求。真正执行能力仍由可信适配层提供。

控制角色还有一个特殊但重要的边界：ST 的选择提交、Designer 的草稿编辑等私有工具，应在获准控制角色 Session 中注册，不需要为了让一般员工卡“看起来资源完整”而加入全局业务工具库。获得这些工具来自正式角色任命，而不是卡片说自己是项目经理。

<a id="s04-07"></a>

### 4.7 角色资产为团队与独立评审提供基础，但不代替协作协议

同一张测试卡可以实例化为两个测试成员，各自负责不同接口；同一张架构卡也可以用于不同方案的专家。卡片复用只说明共享专业定义，不说明共享工作历史、写权限或决定权。

独立评审至少要检查实际贡献关系：谁修改过被评成果，谁提供过关键决策，谁形成独立证据。仅比较角色名或卡片版本，是首版可以使用的粗粒度限制，不是认知独立性的充分条件。同模型、同信息源仍可能共享盲点；不同模型也不天然独立。相关规则应体现在评审计划和贡献记录中，而不是给卡片增加一句“绝对客观”。

将来允许员工调用子 IPD 时，应通过当前任命的委派策略和受控工具发放，而不是给一整类员工永久增加不受限的递归能力。卡片可以表达“具备组织子工作包的专业方法”，不能自行确定最大深度、允许重规划的范围和父任务的完成状态。

本章的最低验收是：选人能看到专业差异；运行时只获得本次需要的任务与资源；角色通用方法不新增冻结标准；同卡不同成员有独立身份与工作记录；资源缺失不会通过换一个名字被掩盖。

## 第 05 章　流程规范与具体工作流资产

<a id="s05-01"></a>

### 5.1 “流程模板”必须拆成两种不同含义

在日常讨论中，IPD 规范和已经排好节点的 Workflow 都可能被叫作“流程模板”。实现时不能继续共用一个模糊概念。

**ProcessSpec 固定一类任务必须保持的责任与质量关系，WorkflowTemplate 保存某组条件下已经设计好的一种执行组织。** 前者需要任务化解释，后者需要适用检查和重新绑定；两者都不等于正在执行的状态。

| 层次 | 固定什么 | 每次任务需要做什么 |
|---|---|---|
| ProcessSpec | 必要活动、成果、专业要求、评审、交接和适用边界 | 选择适用版本，并实例化义务 |
| WorkflowTemplate | 可复用的工作包、参与者槽位或已配置角色、依赖、输出与检查关系 | 验证前提、绑定当前材料与资源、检查仍然符合任务和规范 |
| WorkflowDefinition | 当前任务的具体设计和已明确的绑定 | 校验、解析、形成执行基线 |
| ExecutionBaseline | 获准执行的定义、确切资源和已经形式化的控制规则 | 按该依据执行；必要变更走显式程序 |
| Run 记录 | 实际输入、会话、候选、证据、判断和状态 | 作为审计、恢复与改进依据，不当作新任务模板 |

可以在磁盘上让模板和当前 Workflow 使用同一种结构，但需要保留它们的不同用途。模板不是旧 Run 的“另存为”，Baseline 也不是每次根据当前目录重新解析一次的配置。[02-S04](appendices.md#ref-02-s04)

<a id="s05-02"></a>

### 5.2 ProcessSpec 应充分表达真实作业规范，不写成工具使用手册

一份可用规范要让设计者理解：为什么需要这些活动，通常由哪些专业承担，成果成熟到什么程度后可以交接，什么证据可以支持判断，以及哪些条件下不应使用该规范。

建议保留当前规范中已经形成的核心部分：

| 内容 | 应表达的信息 | 典型错误 |
|---|---|---|
| 身份、来源、适用边界 | 针对什么任务、为什么适用、哪些场景排除、依据从哪里来 | 标成“通用”后自动适用于一切任务；把项目转译标成华为内部模板 |
| 必需活动 | 必须承担的业务责任、目的、必要输入条件和专业能力 | 只写阶段名称，或规定每个活动只能对应一名 Agent |
| 必需交付 | 成果内容、用途、与活动的关系、需要保留的证据 | 只写一个文件扩展名；内部过程文档全部变成用户必收文件 |
| 必需评审 | 对象、成熟度、专业判断、独立要求和标准 | 只有“认真检查”，或者预设所有评审必须通过 |
| 跨活动规则 | 追溯、版本、职责分离、汇聚、准出和变更关系 | 重复所有角色 Prompt，或用一句“遵循 IPD”代替可检查关系 |

规范正文应使用现实场景下的工作语言，例如“测试设计需要覆盖接口边界和失败恢复”“正式发布材料必须对应已验证版本”。不要在每个活动里重复“调用某个 draft 工具”“不要操作 Runtime”“创建一个 execution 节点”；这些属于工作流设计方法或运行协议。

用户提供的 `project-reviewed-content-delivery@2.0.0` 已经将需求、计划、交付件设计、内容、成品、验证和交付写成真实作业内容，并明确声明是项目衍生规范。[02-S09](appendices.md#ref-02-s09) 这适合作为结构和表达方式参考，但其中的具体阶段、评审点和 capability 映射仍需按该版本对待，不是所有任务的默认流程。

#### 来源、适用性、可执行性分别记录

规范可以来自正式组织资料、公开流程转译、项目手写或后续经验总结。记录来源和改编边界即可，不必为了让系统先跑起来就伪装成正式内部规范。公开 PTM 材料映射中的物理可靠性和制造验证，也不能通过改名变成普通软件压力测试。[02-S09](appendices.md#ref-02-s09)

`default_executable` 之类标记只能按实现中定义的用途解释，不能证明规范适用于当前任务，或者所需环境已准备好。资源状态来自本次能力目录和绑定检查，来源权威性来自文档出处，二者都不能代替任务适用判断。

<a id="s05-03"></a>

### 5.3 规范义务必须能够落到责任、成果、证据和判断

规范中自然语言是必要的：复杂质量含义不能全部编码为布尔条件。但每一类规则都应明确**谁解释，谁检查，什么记录能够证明被落实**。

建议将检查分为三层：

**结构与引用检查**：ID 唯一，引用有效，必需交付有活动来源，评审指向明确对象，依赖无矛盾，最终完成条件包含必需责任。它证明配置连得起来，但不能证明任务分解合理。

**有实现的确定性检查**：例如禁止未授权写入、输出版本匹配、某类必需评审存在。声明 `enforced_by: compiler/runtime` 时，必须能解析到已实现的规则。无法实现就明确拒绝或报告能力缺口，不“默认视为已经检查”。

**专业语义检查**：例如方案是否充分覆盖风险、结论是否由证据支撑。它要落实为当前任务的对象、标准、证据和评审责任，而不是只把一句抽象要求原样粘贴到节点说明。

当前 ProcessSpec 已为活动、交付、证据要求、评审标准和规则提供稳定 ID，并区分 `enforced_by`。[02-G17](appendices.md#ref-02-g17) 这提供了映射基础；**字段存在不等于相应规则已执行，coverage 中出现 ID 也不等于责任真实成立。**

以第一部分的“批量导出接口变更”为例，下面是规范义务到本次工作流的**关系示意**，不是固定节点数量要求：

| 规范义务 | 当前任务中的实现 | 可检查的对应关系 |
|---|---|---|
| 保留兼容性要求 | 明确旧客户端、字段和错误语义，形成契约基线 | 变更内容能够追溯到原始需求和接口版本 |
| 形成实现与验证成果 | 实现补丁、测试代码、构建及验证记录 | 哪个工作包对哪个 output 负责，使用了什么输入 |
| 独立判断关键质量 | 核对实现、测试结果与接口承诺 | 兼容性标准指向确切实现和验证版本，而非只读生产者总结 |
| 交付可复用成果 | 提供约定的代码、使用说明和必要证据 | 用户交付清单满足原始需求，不等于已执行生产部署 |

每项覆盖关系至少应能回答“由谁落实、形成什么、怎样判断、证据在哪里”。对于必须影响最终成功的义务，还要保证其实际进入完成条件，不能成为永远不必执行的旁支。

组合标准需要单独注意。例如“实现行为与测试和接口约定一致”，判断对象是一个成果组合。未来 Schema 支持阶段或组合评审时，可以显式表达该集合；若当前引擎只支持某种粒度，应报告表达能力不足或采用经过审查的合法组织方式，不能只在描述中写上“综合评审”就宣称引擎已经支持。

**既有规范的强制项不能因引擎升级自动消失。** 一份老版本规定了七个评审责任，新架构支持阶段门禁，并不意味着设计师可以不加说明地只留下一个终审。可以在新规范中重新明确评审时机和允许合并的责任；只有对象、标准、专业资格与依赖都仍然满足时，具体工作流才有合法合并空间。

<a id="s05-04"></a>

### 5.4 具体化质量标准，不等于任意增加硬约束

规范需要设计者结合任务细化，但必须保留要求来源。建议至少分清三类：

| 类型 | 例子 | 生效与变更方式 |
|---|---|---|
| 用户／组织规范必需项 | 保持旧客户端兼容；关键数据需可复算 | 不能由生产者或设计者自行削弱 |
| 已采用的设计决定 | 本次选择某个接口协议、数据结构或呈现方法 | 依据其承诺和影响范围管理修改，不伪装成用户原话 |
| 方法建议和参数起点 | 推荐某种布局、脚本组织或默认调试方法 | 合法范围内可调整；除非明确纳入验收，不作为新增 Gate 门槛 |

关键标准应说明对象、条件、观察方法、证据和必要单位。能够用正式来源说明阈值时记录来源；没有依据时，不能由模型随手补一个“95%”“最多 20 页”来制造精确感。

此前 Run 审计记录过一个教训：较宽的呈现目标逐渐被细化成图片数量、图形数量、面积比例等硬限制，其中部分又被标注为用户要求。[02-S11](appendices.md#ref-02-s11) 本部分引用的是该审计中的来源混淆现象，不据此断定所有参数都不合理。需要避免的是**设计建议在交接中未经明确决定就升级为不可变约束**。

最小实现可以在标准旁增加来源引用和类型，或者使用单独的要求／决定索引；不必为每项细节发起复杂审批。但检验、返工和后续资产总结都应知道：这究竟是用户未满足、规范被违反，还是某个实现选择需要调整。

<a id="s05-05"></a>

### 5.5 WorkflowTemplate 的复用，必须经过前提核对与重新绑定

模板的价值是省去重复设计，而不是省掉当前任务的判断。至少需要核对以下条件：

| 条件 | 需要判断的内容 |
|---|---|
| 任务性质与交付 | 是否仍然处理相同类型的问题，用户需要的结果是否被覆盖 |
| ProcessSpec 兼容性 | 是否遵循当前选定版本的义务；版本范围必须能被明确解释 |
| 输入条件 | 材料类型、模式、来源、可访问性和必要未知是否符合假设 |
| 能力与环境 | 角色、工具、Skill、模型和运行环境是否真实可用且获准 |
| 组织与质量 | 并行前提、评审对象、独立要求、验证能力和完成条件是否成立 |
| 可变范围 | 哪些参数可替换，哪些变动需要重新设计，而非字符串替换 |

模板中可以固定经过验证的员工组合，也可以定义专业槽位，由设计者选择合格成员。首版不必实现通用参数语言；确有复用需求时，优先定义少量类型明确的输入槽，而不是允许任意 JSONPath 补丁或执行脚本改写流程。

推荐的实例化过程为：

```text
读取确切模板与来源
  → 检查适用条件和资源要求
  → 按声明槽位绑定当前任务、材料和资源
  → 形成新的任务化 WorkflowDefinition
  → 完整编译及必要的语义核对
  → 生成新的执行基线和 Run 身份
```

其中任何一步都不继承旧 Session、旧批准、旧完成标记或旧业务数据。旧任务中的客户名称、文件路径、硬编码页数、私人材料、模型默认和检查阈值也需要检查：只替换 `task_input_ref` 并不能自动删除藏在节点描述里的特定假设。

当前 Pi 的模板路径会复制模板、重新绑定 TaskInput 与 ProcessSelection 引用，再编译；并不会自动理解并重写模板中的所有业务文字。[02-G20](appendices.md#ref-02-g20) 因此，可直接使用的模板应在发布时就消除无关任务残留，明确适用条件。遇到真正不适配的新任务，应转入工作流设计，而不是不断增加条件分支把一份模板变成万能流程。

显式选择规范和模板可以合法跳过 ST 或 Designer。记录应真实表明走了哪条路径；模板执行成功不能作为自动选型或自动设计质量的证据。最近被审计的 Run 就属于显式选型和模板执行路径。[02-S11](appendices.md#ref-02-s11)

<a id="s05-06"></a>

### 5.6 从一个成功 Run 提炼模板，不能只去掉 run_id

建议模板提炼按照“去特定化、补前提、做变体检查”处理。

**去特定化**：移除真实用户和敏感业务数据、环境实例、绝对路径、临时回执、历史状态及批准；保留必要结构，但将可变材料和配置放到明确输入。检查所有自然语言契约，防止只是结构字段换了，正文仍指向旧任务。

**补前提**：说明任务族、输入与环境要求、默认专业分工、不能处理的变体，以及为什么这些评审和依赖有必要。原任务能运行，是证据之一，不是适用性定义。

**做变体检查**：至少覆盖一个符合条件的新任务、一个应被拒绝的任务，以及关键依赖缺失的情况。相关风险较高时，再加入并行、返工、缺证据和取消场景。模板成熟度应能区分“可解析”“可编译”“执行过”“在代表性任务上验证过”；不要把编译通过直接标成生产成熟。

当前 Pi 在成功编译后即可保存 Workflow 资产，并对版本冲突做处理。[02-G16](appendices.md#ref-02-g16)[02-G20](appendices.md#ref-02-g20) 这有利于复用设计，但保存记录本身不证明任务已成功执行。未来模板目录应将结构合法性与实际验证记录分开呈现；不需要因此阻止所有未实跑模板进入试验库。

<a id="s05-07"></a>

### 5.7 发布和修改要按责任层级处理

模板默认参数变化、ProcessSpec 强制义务变化、当前成果修订和运行中 replan，不应共用同一种“更新配置”。

| 变化 | 所属对象 | 不能自动发生的事 |
|---|---|---|
| 改正一份候选成果或补充证据 | 当前工作与 Submission | 不更新模板版本来掩盖本次未达标 |
| 调整当前任务内被允许的实现细节 | 工作决定／产物 | 不把一般建议伪装成冻结标准，也不私自改变强制标准 |
| 改变已冻结工作流的责任、资源或结构 | 明确变更后的新执行基线 | 不覆盖旧基线、丢失原因或静默替换仍承担责任的成员 |
| 改进一类任务的组织方式 | 新 WorkflowTemplate 版本 | 不让既有 Run 自动采用新拓扑 |
| 改变一类任务的必需活动、交付或评审 | 新 ProcessSpec 版本 | 不由 ST 在选择阶段直接剪掉强制项 |

这些关系只定义资产层面的边界；具体 replan、责任延续和失效处理在第 16 章展开。首版可以不实现复杂 replan，但必须清楚拒绝不支持的改变，不能通过改源 YAML 绕过去。

本章的验收重点是：**规范不是形式 ID，模板不是历史状态，重新绑定不是简单改标题，编译通过不是任务质量通过。** 用这四个反例检查资产使用，比要求每份规范都增加更多字段更有效。

## 第 06 章　Skill、工具和验证资源

<a id="s06-01"></a>

### 6.1 Skill 的作用是补齐作业方法，不是重新定义角色、权限或工作流

**角色说明谁具备什么专业责任，Skill 说明一种工作应怎样开展，工具提供可实际执行的操作，检查器提供特定验证能力。** 它们可以组合，但不应互相替代。

一个接口验证 Skill 可以告诉测试成员如何读取契约、选择正反例、准备数据、执行和解释结果；它不能自行把测试对象改成生产环境，不能授予写数据库权限，也不能因测试通过就宣布产品已经发布。一个工作流设计 Skill 可以解释规范、拆分和草稿工具流程，但不能代替 Compiler 或修改 ProcessSpec。

《极简 Agent 设计方案》强调按需检索 Skill、工具自身负责参数描述，并将多步骤工具逻辑与高层工作流区分。[02-S01](appendices.md#ref-02-s01) 本方法保留这一分工：稳定的局部处理可以由脚本完成，不因为脚本内部有多个动作就为每一步建立 Agent 节点。

公开 Agent Skills 格式将 Skill 组织为包含 `SKILL.md` 的目录，可带 `scripts/`、`references/`、`assets/`；必要元数据为名称和用途说明。[02-W08](appendices.md#ref-02-w08) 该格式提供可移植包装，但并不自动实现本方法要求的资产冻结、依赖校验、权限控制和质量准出。

<a id="s06-02"></a>

### 6.2 Skill 要足够具体，也要知道何时结束

建议主 `SKILL.md` 围绕下列顺序组织。它们是内容职责，不要求每个 Skill 强制使用相同标题。

| 内容 | 要解决的问题 |
|---|---|
| 用途与边界 | 什么任务需要它，哪些任务不需要；输出应服务什么目的 |
| 必要输入与前提 | 需要什么材料、工具和环境；缺失时如何辨认而不是猜测 |
| 最小作业路线 | 从当前输入到可交付结果必须做的工作，不先展开所有可选方法 |
| 方法选择条件 | 何时使用某分支、脚本或专业参考；什么情况下不适用 |
| 交付与验证 | 产物怎样组织，怎样检查，证据和限制怎样保留 |
| 补正与常见错误 | 可以直接定位的错误、正确恢复方向，以及不能自行修复的条件 |
| 收敛条件 | 何时内容已足够提交；何时需要补证据；何时应报告阻塞 |

例如研究 Skill 应说明围绕决策问题形成证据链，而不是无限扩展文献范围；设计 Skill 应区分主线、制作说明和可选参考，不要求给每一个页面生成超过实际消费需要的长文；验证 Skill 应说明“检查执行成功”和“被测对象满足要求”的不同。

尤其不能默认治理角色具有本项目历史记忆。`process-selection` 需要解释 ProcessSpec 的含义和选型职责，`workflow-design` 需要解释工作包、输入、交付、评审和返工关系，再介绍工具。共享的方法论 reference 可以复用，但主 Skill 应提供足够的阅读入口和行动路径，而不是一开始抛出大量没有定义的缩写。[02-F00](appendices.md#ref-02-f00)

一个可用的包结构示意如下：

```text
api-contract-verification/
├── SKILL.md                         方法入口、前提、决策分支和提交前检查
├── references/
│   ├── compatibility-cases.md      兼容性专项参考
│   └── evidence-format.md          证据格式与有效／无效示例
├── scripts/
│   └── validate_cases.py           确定性的用例／结果结构检查
├── assets/
│   └── case-template.json          不含客户数据的可复用模板
└── LICENSE.txt                     需要保留的授权或来源说明
```

目录是组织方式，不意味着主 Skill 应在开始前要求读取每个文件。某脚本只需执行即可，不必先将全部源码放进上下文；但来源审查和发布验证仍需理解它实际做什么。

<a id="s06-03"></a>

### 6.3 按需披露不改变授权，读取方法不等于获准执行

建议将 Skill 使用分成五个动作：

```text
发现可能适用的方法
  → 在当前授权范围内选定确切资源
  → 加载方法入口
  → 按需要读取专项参考或执行脚本
  → 将实际产物和检查证据提交给当前节点协议
```

发现阶段可以由宿主的小目录、SkillSearch 或 Tool result 提供摘要；不强制把全库名称和描述都常驻系统提示。正文应说明何时读哪份参考，而不是仅把一个大文件拆成十个文件后仍然要求全部先读。公开 Skills 规范的渐进披露和 Anthropic 的工程说明提供了这一组织思路；本项目采用何种宿主加载入口，则由适配层决定。[02-W08](appendices.md#ref-02-w08)[02-W09](appendices.md#ref-02-w09)

必须分别记录“资产获准且可访问”和“模型实际读过内容”。已绑定但未读取，不等于遵循了专业方法；工具返回出现路径，也不等于模型能够访问或已经理解正文。对治理角色必须先掌握的方法，可以在首次派发时显式加载；不必为此额外生成一个没有业务结果的模型轮次。

**渐进加载不应破坏版本锁定。** 一个已锁定 Skill 的专项 reference 应从同一快照读取，而不是临时跟随源仓库 `main`。两个私有 Skill 共用 `ipd-methodology.md` 时，可以由一个源文件在发布阶段装配到两个包，或引用相同内容对象；不要要求部署者手工复制后又没有一致性检查。包不包含必需 reference 时，应在装配或验证中发现，而不是等模型读到不存在的链接再自行补想象。

如果后续支持节点在执行中动态发现新 Skill／Tool，至少应提前约束可搜索的资源范围、许可动作和依赖，并记录实际选定的确切内容。搜索到的方法没有自动扩大权限的效力。最小实现可以先只支持冻结集合内的按需披露；真正增加资源的受控变更留给扩展协议，不能靠一句“自主使用一切必要工具”实现。

<a id="s06-04"></a>

### 6.4 依赖必须能检查，但不能从 Skill 描述直接生成授权

一份方法真正可执行，需要区分以下依赖：

| 依赖 | 示例 | 检查责任 |
|---|---|---|
| 工具接口 | 读取文件、搜索来源、获取长结果的后续页面 | 注册目录和节点绑定检查 |
| 命令及库 | Python、JSON 解析库、渲染程序 | 环境配置与实际能力探测 |
| 数据和业务对象 | 原接口定义、测试账号、授权测试环境 | 任务输入与运行前提核对 |
| 伴随操作 | 搜索后分页读取；提交后查询未知结果 | 工具依赖契约与调用流程 |
| 网络和身份 | 允许访问的服务、凭证作用域 | 可信宿主策略与执行代理 |

可以使用宿主已有的依赖元数据，也可以提供伴随清单；只有重复出现且可以实际校验的需求，才值得增加机器字段。不应从自由文本中猜测所有可能软件并自动安装。

当前 Pi 会读取 Skill 的 `allowed-tools`、`required-tools`、`required-commands` 和环境需求，并在节点校验中检查必需工具、可读取方法的能力及工具伴随依赖。[02-G12](appendices.md#ref-02-g12)[02-G18](appendices.md#ref-02-g18) 这是该宿主的装配约定，不能原样当作所有 Skills 实现都支持的标准。

尤其是 `allowed-tools`：公开格式将它列为实验性字段，宿主支持方式可能不同。[02-W08](appendices.md#ref-02-w08) 在本方法中，它表达的是待核验的方法声明，不是第三方 Skill 对系统的授权指令。若列出了宿主未允许的 Bash、网络或账户操作，应拒绝相应绑定；不能因为文件叫“allowed”就自动放行。

依赖策略要说明哪些是必需、哪些有合法替代。必需工具缺失时返回具体缺口；替代方法必须真的保持所需结果和证据。把“实测接口”替换为“静态阅读文档”，不是等价实现，不能仅修改 Skill 文案就让任务继续以同样标准通过。

<a id="s06-05"></a>

### 6.5 脚本、原生工具和外部服务按责任组合，不为每项方法造新包装

**脚本适合承载稳定、可复用的局部计算或格式处理。** 例如解析文件、生成格式化输出、检查 Schema、比较版本。它应明确输入输出、依赖、退出状态、日志和异常路径；可预测的处理不要每个任务都让模型重新写一遍。

**工具适合承载具有独立调用契约的能力。** 当需要宿主身份、权限代理、外部副作用、稳定的结构化结果或多处复用接口时，才将相应能力注册为工具。不需要把 Skill 中每个脚本都包装为 Tool，更不需要一对一变成工作流节点。[02-S05](appendices.md#ref-02-s05)

**外部服务适配器负责协议与权限差异。** MCP 或其他接口提供发现与调用方式，但不应成为业务资产必须依赖的执行实现。模型看到工具的名字、用途和 Schema；服务连接、凭证和实际操作边界由宿主管理。MCP 的工具规范也明确要求客户端谨慎对待工具 annotations；来自不可信来源的“只读”等注解不能直接成为安全依据。[02-W10](appendices.md#ref-02-w10)

工具说明应清楚表达何时用、何时不用、需要什么参数、结果如何读取、错误如何处理。参数 Schema 有权威定义时，Skill 只引用并解释作业用法，不再维护一份可能过期的平行参数清单。示例可以保留，但应作为测试的一部分检查其仍然符合接口。

长结果和文件返回也要有明确契约：返回的是可访问的内容引用、受限分页入口还是临时文件？实际执行环境能否读取？读取权限、保留期和来源如何关联？不能只把宿主 `/tmp/...` 路径写进 Tool 文案，期待隔离成员能够使用。已检索的内容是业务证据，不会因为由可信工具返回就自动获得修改角色或权限的指令地位。

<a id="s06-06"></a>

### 6.6 知识资源与环境配置：补齐真实能力，不制造虚假的可移植性

#### 知识资源必须区分固定资料和实时查询

固定知识包可以按内容版本锁定，适合内部标准、参考表和已发布资料。实时检索入口则只能锁定访问策略、接口和可取得的源版本，不能保证未来查询返回相同内容。

用于重要判断的实际检索结果，应保留必要来源、时间、内容定位与获准保存的证据；知识库名称、索引版本或一次查询字符串，都不足以证明答案来自同一资料。原始访问授权和数据保留要求仍然适用，不为了“可复现”就复制全部敏感资料进公共资产库。

当前 Pi 的 AgentCard 和 Baseline 有知识库相关结构，但节点校验明确返回 `knowledge_base_unsupported`，说明当前适配器尚无可执行的知识库投影。[02-G11](appendices.md#ref-02-g11)[02-G18](appendices.md#ref-02-g18) 文档和 UI 不能因为字段存在，就宣称该能力已经可以调用。跨 Harness 移植时应先接通真实读取、身份和证据协议，再开放配置。

#### 环境配置应描述可执行条件，不泄漏到所有专业 Prompt 中

环境 Profile 应提供基础系统、软件能力、平台、适用任务和安全限制；实际实例、临时目录、凭证与进程状态属于运行记录。一个通用“文本处理”环境和一个“办公文件制作”环境可以复用相同治理内核，不需要为每个业务场景新增 Runtime 分支。

固定基础软件与任务依赖也应分开。已验证的镜像或环境包可以作为基础身份；任务需要安装的依赖应有范围、版本和记录，不能静默污染宿主或改写只读 Skill。基础镜像摘要只能说明基础文件，没有锁定后来安装的软件及远端响应。环境是否可用还应有实际探测，不以 Docker 命令存在或包名列在文档中为依据。

专业角色不用理解所有宿主路径与部署细节，只需要一个正确的可见文件布局和可执行能力说明。当前运行目录、输出根与依赖定位通过适配生成；跨平台变化不应要求手工修改每张 AgentCard 或 ProcessSpec。

<a id="s06-07"></a>

### 6.7 验证资产必须说明“证明了什么”，并把执行结果与判断分开

确定性检查器是质量证据来源之一，而不是质量的总解释器。需要明确：它检查哪个对象、接受什么参数、采用什么实现版本、依赖何种环境、能产生什么观察，以及不能支持什么结论。

| 检查 | 可以支持的结论 | 不能直接支持的结论 |
|---|---|---|
| 文件存在与摘要 | 指定文件存在且对应某些字节 | 内容满足业务目标 |
| JSON Schema 检查 | 结构和字段符合已采用 Schema | 字段中的事实正确，方案合理 |
| 接口契约／回归测试 | 指定环境、版本和覆盖场景下的行为符合断言 | 所有未覆盖路径、生产环境和业务效果都正确 |
| 渲染或布局检查 | 在指定渲染条件下观察到某些呈现结果 | 全部视觉质量、叙事和事实已被独立批准 |

当前 Pi 的检查器 Registry 已包含参数 Schema、实际执行函数和结果证据，不是只保存一个检查器名称。[02-G21](appendices.md#ref-02-g21) 但目前其直接结果类型为 `PASS/FAIL`；跨宿主实现还需要在外层区分检查器失败、未执行与有效质量判断，不能因为接口枚举简单就混淆这些状态。

建议以如下**逻辑记录**解释一次检查。字段和枚举为参考，实际实现可复用已有事件与报告，不另建平行账本。

```yaml
check_ref:
  id: api-contract-test
  version: "1.0.0"
  digest: "<检查器及固定测试资源的内容身份>"
subject_ref: "<本次被测产物的确定版本>"
parameters_ref: "<本次参数、用例与采用标准的引用>"
environment_ref: "<实际环境及配置身份>"
execution_status: completed
verdict: fail
evidence_ref: "<原始结果和可定位观察>"
diagnostics:
  - code: incompatible-error-response
    location: "<接口和失败用例位置>"
    observed: "旧客户端无法解释新增错误响应"
    expected: "保持已承诺的错误协议，或按已批准迁移策略处理"
```

如果检查程序没有启动、解析失败或环境缺失，不能使用上述 `completed + fail` 冒充已经判定产品不合格；应表达执行错误或未验证，再由当前流程处理。反过来，测试顺利执行且发现真实缺陷，是检查成功完成而被测对象未通过。

**报告有效与对象合格也必须分开。** 一份准确说明产品 `NOT_READY` 的质量报告可以是合格交付，不应要求分析者把被测产品写成 READY 才能完成自己的节点。

对于模型在当前任务中生成的 `qa.py` 或测试脚本，它最初是候选验证产物，不自动等同于被独立认可的权威检查器。应关联版本、断言依据和实际证据；修改检查器时不能让旧检查结果继续批准新产物，也不能通过放宽断言把同一缺陷“修成通过”。合理纠正检查器误判可以进行，但理由和影响要留存。

此前 Run 审计还记录了工具回执未标错但输出中有 Traceback、以及结构化解析诊断丢失后让 Agent 长时间猜测的问题。[02-S11](appendices.md#ref-02-s11) 应把经验沉淀到检查接口：正确传播实际退出状态，保留错误类型、文件和字段路径及位置，不只返回“校验失败”。这属于稳定工具契约，不需要为每个相似错误再创建一名专家。

<a id="s06-08"></a>

### 6.8 一套可执行资产组合，比孤立精美的 Prompt 更有价值

以“接口契约验证”工作为例，完整组合至少需要下列责任，未必分别对应一个文件：

```text
ProcessSpec：要求保留兼容性验证与独立判断
Workflow：本次对象、责任、依赖、输出和采用标准
AgentCard：具备接口与兼容性审查专业方法
Skill：如何建立用例、执行、解释和组织证据
Tool / 脚本：读取、运行和提取结果的实际能力
Environment：支持这些操作且具有正确边界
Check / Review：对确定对象与证据形成有限、可追溯判断
```

装配完成时应能直接说明“这名成员用什么材料和能力完成哪项责任”，而不是只展示一串角色和工具名称。没有测试环境时，系统应指出所选验证方法不可执行；没有独立核验时，不能因为生产者的测试日志存在就声称完成全部准出。

**本章最低实现不要求新的 Skill 运行引擎。** 原生加载器处理方法披露，工具适配器处理实际操作，环境提供执行边界，Compiler 核对引用和权限，Runtime 登记候选与检查。资产层负责把它们接成明确、可验证的组合，而不是接管每一层。

## 本部分的最小工程落点与验收

第二部分不要求先建一个完整“资产平台”。最小实现只需把以下职责落到已有模块或少量新模块中：资产解析与结构校验、来源与身份索引、候选搜索与确切读取、依赖与权限核对、不可变内容快照、按消费者生成视图、发布与观察记录。只有出现真实共享或独立变化需求时才进一步拆分。

验收应覆盖失败和变化，而不只是“能加载 YAML”：

| 场景 | 必须观察到的结果 |
|---|---|
| 两个来源注册同一角色 ID／版本但内容不同 | 明确冲突或执行显式来源策略，不依赖目录顺序覆盖 |
| 只修改 Skill 的脚本或 reference | 包内容身份发生对应变化，不能沿用旧锁定声明 |
| 源目录在锁定后被编辑 | 活动 Run 使用原快照或报告不一致，不悄悄切换 |
| 发布版只做翻译、文字或示例调整 | 产生可区分的修订身份，并按影响检查；不覆盖旧发布内容 |
| 某个无关可选资产缺少依赖 | 不被误称为可执行；按明确策略隔离其失败，不掩盖全局身份／信任问题 |
| 本次已选方法缺少必需工具、环境或授权 | 编译或准备阶段返回具体缺口，不自动缩减工作或回退高权限后端 |
| 员工卡声明能力，但没有实际操作渠道 | 不宣称已经取得该能力，更不伪造执行和验证证据 |
| 搜索读到了一个 Skill／Tool | 不产生未经批准的调用资格；实际调用仍受宿主边界约束 |
| 从旧任务提炼模板 | 不携带旧输入、会话、批准、敏感数据和隐藏业务假设 |
| 模板引用了合法规范但没有落实义务 | 不能仅因 ID 齐全通过；责任、成果、标准和必要评审有实际关系 |
| 上游设计追加了一个实现建议 | 下游能识别其来源和变更范围，不把它冒充用户必需项 |
| 检查程序报错或根本没执行 | 不登记为有效的产品通过／失败结论；错误可定位 |
| 检查器被修改或被测产物更新 | 检查结果的版本关系可识别，旧结果不能无条件沿用 |
| 知识入口或模型后端动态变化 | 记录实际可取得的版本和证据边界，不宣称仅凭 ID 完全复现 |
| 同一资产在 Pi 与另一 Harness 使用 | 专业语义和锁定规则一致，平台差异由适配层显式处理 |

上述是实现验收要求，并非本轮已经执行的全套测试。正文中的 YAML 片段仅用于说明资产和记录的形态，不包含真实注册工具、产物身份或完整编译输入。

## 本部分结论

**可演进资产体系应把“专业知识与方法可以积累”和“当前任务依据不能漂移”同时成立。** 数字员工提供专业责任，ProcessSpec 定义组织与质量义务，工作流模板提供可复用设计，Skill 提供可执行方法，工具、知识、环境和检查器补齐真实能力；一次任务只采用经过适配和授权的确切组合。

资产层应解决三件事：让设计者选得明白，让执行者拿到合适而不过量的方法，让维护者能够依据真实失败和收益发布改进。它不负责替 Runtime 维护状态，也不能用更多角色、更多规则和更长 Prompt 掩盖能力不足。

第三部分将从任务接入和运行对象开始，定义这些资产如何变成持续会话、精确输入、候选提交、评审返工、调度与恢复。这里已经固定的身份、来源和作用边界不再另行定义一套。
