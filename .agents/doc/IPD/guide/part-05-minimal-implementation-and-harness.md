## 第 19 章　从最小闭环到层级协作

<a id="s19-01"></a>

### 19.1 最小不是只留下 happy path，而是先收窄支持范围

一个可以信赖的第一版，可以只支持一个宿主进程、少量本地资产、单成员执行与评审、一种执行环境和一个手工工作流。但它仍应有明确任务依据、确切输入、真实权限、正式提交、版本评审、局部返工和可解释的失败。不能删去这些机制后，再通过“暂时别碰边界”把示例叫成通用运行时。

对未支持能力应明确拒绝：多人配置不能只执行 `agents[0]` 后假装团队成功；声明不能恢复灾后 Session，就不能把重新创建任务伪装成恢复；无法验证某类输出，应报告能力缺口，不返回通用绿色结果。

对于已经有成熟 Pi 原型的本项目，第一版迁移也不应回到完全没有提交和权限的玩具实现。**可以缩小可执行组织范围，但保留已经确认的关键控制语义。** 例如先不开子 Run，却仍以 Participant 为执行身份；先不开自动 replan，却不允许员工直接改 Baseline。

无新增架构硬约束、正常作业维持原 Session、灾后允许恢复同一逻辑会话，是用户已确认前提。灾后恢复需要单独的检查点与执行接管能力；未完成时只能诚实声明不支持，不能在最小版本中虚报保证。

<a id="s19-02"></a>

### 19.2 先固定支持画像，再让资产和提示词描述能力

每个可发布实现声明一个 `EngineCapabilities` 或等价支持画像，供 Compiler、治理角色、测试与部署共同读取。画像由真实注册的适配器和通过的能力测试产生，不是手工写几个 `true` 就完成上线。

```yaml
# 首版支持画像示例；本例为目标部署配置，不是现有仓库实测值。
engine_profile:
  profile_id: local-governed-v1
  protocol_version: "1"
  ownership: single_controller_per_root
  organization:
    participants_per_node: 1
    stage_candidate_handoff: false
    child_ipd: false
    online_replan: false
  lifecycle:
    same_session_rework: required
    durable_result_adoption: required
    process_restart_recovery: unsupported
  environment:
    provider_ref: isolated-local-profile-v1
    controlled_external_actions: false
  governance:
    modes: [manual_workflow, template_instance]
  conformance_report_ref: report-to-be-produced
```

`unsupported` 表示不能接受需要该能力的任务，不表示可以静默退化。后续启用灾后恢复、团队或子 IPD，必须升级画像、Compiler 可表达范围、Runtime 行为、资产绑定、Prompt／Skill 和验收结果。

支持画像与运行资源参数不同：画像说明引擎是否能够保证语义；并发数、环境配额、超时和 Provider 限制说明本次如何运行。不能把配置了 `max_depth` 当成子流程已经实现，也不能把有一份 JSONL 当成恢复能力已经验证。

<a id="s19-03"></a>

### 19.3 用少量稳定职责组成内核，不提前建成平台

建议将代码分为四个逻辑区域，另设资产和验证目录；实际可先放在同一个包：

```text
contracts/          领域对象、引用、诊断与命令的唯一协议
kernel/             编译关系、合法状态转换、影响与完成判断
application/        准备流程、派发协调、等待、停止、采用和清理
adapters/           Harness、环境、持久化、产物及外部能力接入
assets/             数字员工、ProcessSpec、模板和Skill
conformance/        共享夹具、适配契约、故障与端到端验证
```

目录只是职责示例，不是强制项目布局。纯领域规则不导入 Pi／Jiuwen 的 AgentSession、ToolDefinition、Provider 类型、Docker 客户端或 UI 组件；适配器依赖领域协议，而不是治理内核反向依赖某种工具包装。

应用层组织顺序但不替模型完成业务判断；Compiler 校验已形式化关系，不暗中成为另一位 Designer；Runtime 持有正式控制权；Harness 维护原生会话和工具循环。工具、状态存储与产物后端可以有不同实现，但同一运行中只选择一个权威责任方。

不要求每个名词一个服务、每个接口一个包、每条事件一个消息主题。第一次增加接口，应有当前替换需求、测试隔离价值或明确的边界风险；不是为了“未来可能分布式”预建框架。历史 edict 分析的重要教训之一就是新旧架构并存、状态和部署链路未收口；这里继承教训，不重复搭建两套完整调度体系。[05-S08](appendices.md#ref-05-s08)

<a id="s19-04"></a>

### 19.4 先跑一个有反例的纵向闭环，再扩展自动治理

新 Harness 上最有信息量的首个场景不是大 PPT，也不是几十人的演示，而是一条小型的真实闭环：

```text
接入原任务与两份受控输入
    ↓
人工配置的合法 Workflow → Compiler → 冻结基线
    ↓
A 生产一份可检查产物 ──┐
D 独立完成另一份产物 ──┼→ 必要评审／汇聚 → 正式交付
    A 首次产生明确缺陷 ┘
          ↓
       原 Session 修正 A；D 不重产
```

对象可以是小型代码变更、数据计算和解释文档，不把任何一种媒介写进引擎。用受控模型替身先验证协议，再用真模型验证工具理解和交付行为。首次可以由测试夹具使 A 返回不合格候选，不要求依赖真实模型恰好犯错才验证返工。

这个闭环至少验证：输入真实受限；候选可以被定位检查；正式判断能导致具体责任返工；原 Session 继续；D 不被取消；最终文件与批准版本一致；通知或看板失败不重开业务。随后加入“收到外部动作回执前中断”“提交登记前取消”“恢复旧环境不可用”等关键反例。

ST／Designer 接入之前先有人工合法工作流和非法工作流，能区分规划质量与运行机制错误。自动准备接入后，再单测正确选型、错误引用、决定性信息缺失、增量修订、未调用提交、资源缺口和模板不适用；不能把模板执行成功当成设计师能力已验证。

<a id="s19-05"></a>

### 19.5 版本路线按能力依赖推进，不按功能展示数量推进

下表沿用既有蓝图 M0—M6 的推进意图；对新 Harness，M0 包含能力探针与首条纵向闭环，不能理解为把历史已修复项全部重新开发。

| 里程碑 | 可交付能力与主要工作 | 准出证据 | 有意不做 |
|---|---|---|---|
| **M0 基线收口** | 固定协议与支持画像；宿主能力探针；单成员执行／评审、确切交付和原 Session 返工；对齐重要历史修复 | 人工合法图、非法图、小型原生 Session 闭环；D 保留；生成页面脚本和真实状态显示可验证 | 团队、递归、全自动重规划 |
| **M1 可靠执行基础** | 持久意图／采用、执行资格、错误与诊断、暂停／取消；声明范围内灾后恢复；根级准入；基本遥测；接入单 ST／Designer | 重复／晚回执、中断点、独占执行、容量故障恢复、自动治理分层测试 | 盲目增加多人；无证据的跨主机保证 |
| **M2 阶段质量** | 阶段内受控候选、ReviewBundle、整体标准、Finding、准确影响与复验 | A→B 阶段内合法；出口不绕过 Gate；A 错不重产 D；失败报告可保留 | 投票评审团、自由阶段裁剪 |
| **M3 静态团队** | 独立参与者、贡献、内部依赖、唯一汇总提交；分项评审团队 | 必需贡献缺失不能完成；隔离文件；原成员返工；不同意见有冻结规则 | 自由群聊、自主招人、任意共享目录 |
| **M4 一层受控子 IPD** | 委派契约、幂等创建、持久等待、子结果采用、父子取消与责任保留 | 一个活动槽仍能父等子；通知早到不丢；不重复创建；原子责任可继续返工 | 脱离父级运行、无限嵌套、任意角色直接获得根入口 |
| **M5 治理团队与复杂验证** | 固定 GovernanceProfile；设计提案、唯一整合；评审内部验证 | 旧提案不覆盖新草稿；必需 FAIL 不被票数盖过；验证副本不改被评原件 | 无限元规划、依靠主持人自由改标准 |
| **M6 受控演进** | 义务保留、候选基线校验、局部屏障、原子激活与续接；经实测提高深度 | J/R 变化时 D 原 Attempt 续接；旧问题不清零；回退保留副作用事实 | 自动资产自演进、任意任务中途换规则 |

每个里程碑都要跑第 18 章相应层级测试，而不是最后一起验收。M1 不必立刻实现数据库集群，M4 也不意味着必须跨进程调度；单宿主同样可以具有持久等待和受控子责任。

若某个原生能力迟迟不能保证，不要让整个迁移工程停在口头对齐：将缺口转成最小探针和明确决策。或者补适配支持，或者在支持画像中拒绝依赖它的任务；不能用更强 Prompt 假装等效。

<a id="s19-06"></a>

### 19.6 每个开发任务都交付“协议—实现—反例—说明”

适合开发人员或 Codex 的任务不应只写“支持重试”“增加团队”。它应包含边界、不可改项、真实接口、最小变更和验证命令；如果遇到协议缺口，先形成决策记录，不自行扩展角色权限或降低目标。

```yaml
implementation_ticket:
  id: runtime-diagnostics-preservation
  objective: 将校验器提供的定位诊断完整送回原参与者，不再只返回泛化错误。
  prerequisites:
    - 已有结构化候选捕获和校验器
    - 同一逻辑Session持续存在
  change_scope:
    - 通用诊断DTO
    - 校验到反馈的映射
    - 适配器错误展示
  invariants:
    - 不改变当前round的业务责任
    - 不删除输出或降低标准以绕过错误
    - 不为反馈修复新建替代Session
  fixtures:
    - JSON缺逗号，保留文件与行列定位
    - 检查器自身出错，不宣称业务FAIL
    - 同一反馈重复送达，不重复登记提交
  required_evidence:
    - 修改文件清单与原因
    - 实际运行的测试命令和结果
    - 未执行项目及原因
  forbidden_scope:
    - 更换默认模型
    - 删除必需评审
    - 新建并行的状态存储
```

评审开发提交时，检查新增机制是否复用了已有协议，是否有反向依赖、重复状态或任意兜底，是否仅让测试绿色而漏掉业务后果。源码、Schema、Prompt、Skill、UI 和示例不必每次全改，但每次涉及的几层必须保持一致。

**代码生成器也不是另一个规范制定者。** 它可以提出设计方案，但不能在看不到原依据时补造“团队默认同意”的规则；若任务材料不够，产出明确缺项，而不是先把字段做出来再倒推文档。

<a id="s19-07"></a>

### 19.7 将最昂贵的历史坑放到实现初期，而不是等真实大任务再遇见

| 早期检查点 | 最小实施动作 | 后续放大的风险 |
|---|---|---|
| 请求容量 | Provider 边界的 token／多模态／实际字节记录与准入 | 多成员和评审团累计图片，把恢复变成重复失败 |
| 精确诊断 | 错误代码、位置、对象、预期与恢复条件直达原 Session | 多个角色逐层猜测同一个语法错误 |
| 要求来源 | 区分原要求、规范义务、设计决定和建议 | 子任务把上游偏好再次升级为硬标准 |
| 受控产物 | 写工作区与封存分离，输入按授权输出物化 | 团队互相读取正在修改或未获准的内容 |
| 停止和提交 | 先撤资格，再确认停止；提交可结束本轮但不销毁责任 | 取消后仍产生文件／外部动作，多执行者抢同一结果 |
| 准出与完成 | 必需义务真实进入最终成功条件 | 功能越多，越容易有“配了但从不等待”的评审 |
| 身份与观测 | Node、Participant、Round、Attempt 与调用分别记录 | 恢复和团队产生不可追责的重复耗时／贡献 |

这些要求大多不需要大型平台：一个明确 DTO、一个唯一采用入口、一组准确文件映射、一种安全停止回执，就能避免以后大量补丁。没有必要以“暂时只做 Demo”为由让错误成为新实现的默认语义。

<a id="s19-08"></a>

### 19.8 存储选型按负载与恢复保证升级，不按流行程度升级

当前 Pi 已使用静态对象 codec、文件写锁、原子替换和独立遥测，不能继续描述为每次把所有大静态对象原样写进状态。[05-G52](appendices.md#ref-05-g52) 文件方案仍需要验证目标文件系统上的持久性、锁清理、索引和历史增长；也不能因为某次样本状态较小，就推断所有层级任务都无扩展问题。

| 情况 | 可采用的轻量起点 | 需要升级或明确限制的信号 |
|---|---|---|
| 单控制者、本地磁盘、小规模 | 文件事务＋不可变产物＋受控日志／索引 | 高频写放大、复杂查询、恢复对账成本过大 |
| 单宿主、多 Run、增量关系多 | 本地 SQLite 等事务存储＋文件产物 | 明确多个并发写者、跨主机、高可用与共享调度需求 |
| 多主机执行和统一持久命令 | 支持事务与认领的数据库／队列或成熟执行后端 | 只有在运维能力和实际规模需要时引入 |

采用 SQLite 不应只是把全部 state JSON 塞进一列，仍需按频繁变化的实体增量更新。WAL 可让读写更好并行，但仍只有一个写者，且不适合跨主机共享网络文件系统。[05-W47](appendices.md#ref-05-w47) 同步 API 可能阻塞宿主事件循环，应按实际接入方式测量并选择工作线程或合适驱动；这些是适配决策，不在协议里指定一种唯一库。

采用成熟工作流后端，也仍需承接不可变产物、Gate 和 Finding 等语义。不能因为后端有“Activity 重试”，就让它重放包含未知外部副作用的整个 Agent 工作包。先通过同一组故障夹具，再讨论替换收益。

<a id="s19-09"></a>

### 19.9 发布资产、代码与协议要形成同一可复现版本

每个发布候选包含：引擎与适配器构建身份、协议版本、支持画像、资产解析规则、必要 Prompt／Skill、环境配置、检查器及对应验收结果。依赖锁文件要进入构建；源码声明版本范围不等于运行时实际解析版本。

资产通过版本和摘要锁定，Run 的清单说明当时使用什么。升级默认模型、Skill 内容或工具 Schema，不静默改变已启动任务。安全撤销可以使旧运行失去某项权限，但必须明确撤销事件和处置，而不是伪装成普通资产更新。

重试、超时、缓存、并发、环境和日志设置应有一处明确来源和优先级。只记录配置文件不够，还要记录实际生效值；缓存 Service 或 Session 工厂时，应覆盖影响行为的配置身份，避免新 Run 继续复用旧思考模式、旧工具或旧授权。

已有不可变记录不要“原地修成新版本”。兼容层可以短期读取旧 Schema 后转为明确内部表示，但写入只能选定一个权威协议；有真实旧 Run 才有迁移需求，不为所有历史草案预建永久兼容层。

<a id="s19-10"></a>

### 19.10 以逐项证据报告成熟度，不使用一个含糊的“已支持”

一个能力至少区分：设计中、实现存在、有限契约测试通过、故障集成通过、真实任务已验证、对照收益已验证。状态不必做成复杂平台，但在发布说明中必须有固定含义。

例如“支持子流程”要拆成幂等创建、等待、事件对账、取消、输入失效、结果采用、父验收前保留责任、根级限制和恢复。只完成第一项，就写第一项；不能通过一个子 Run 演示便宣布完整支持。

“测试通过”还要注明环境、模型替身／真模型、命令、版本、跳过项及原因。前文数十项内存示例是指导书的逻辑校验，不是当前仓库全部对应机制已经通过的报告。对自己的实现做相同要求，不把之前生成的说明当成新的独立证明。

<a id="s19-11"></a>

### 19.11 迁移应该有明确的停止扩展条件

当跨 Harness 同一组领域夹具无法对齐、原生停止边界不清楚、外部动作结果不可对账、资源限制只写在 Prompt 中、数据格式悄然改变、或最小任务需要频繁人工修复时，应暂停新增团队与递归能力，先补齐基础。

这不意味着停做产品：可以发布明确限域的模板任务能力，同时保留复杂功能为实验开关。不能把实验用户不遇到边界当作正确性证明，也不能让新功能默认污染全部任务。

在时间紧张的迁移窗口，优先交付“一个新 Harness 上真实可跑、失败可解释、可重新进入的最小闭环”和“同一语义测试集”。不承诺一周内完成全部层级治理，也不要求在移植前先完成大型分布式平台。每个未实现项保持可见、可排序，防止缺口被移入模型提示词。

## 第 20 章　Harness 适配与运维发布

<a id="s20-01"></a>

### 20.1 适配的第一步是确定谁掌握正式控制权

不同 Harness 可能已有 Planner、Leader、SubAgent、Team、Workflow 和 Memory。名字相同不表示语义相同。适配前先画出实际控制路径，确认谁决定任务拆分、实例创建、重试、工具循环、最终成功和关闭。

推荐首条移植路径是：**IPD 负责已经冻结的组织与质量控制，Harness 提供受控的参与者执行能力。** 也可以将 IPD 编译到宿主原生图引擎，但必须证明其持久化、输入版本、局部返工、暂停和批准关系等价；不能同时由 IPD 和宿主 Leader 各自自由推进同一任务。

当前公开 jiuwenswarm Agent Team 文档描述了 Leader 分析、组队、拆任务、Teammate 执行回报和 Leader 汇总的路径。[05-G56](appendices.md#ref-05-g56) 这说明有可借用的协作入口，但不证明已有本方法全部 Gate、Finding、委派和恢复协议。本文只核对公开文档的这段说明，不代替你们内部极简分支源码或运行验证。

优先评估低层成员执行接口是否可独立使用。若只能调用一个带自主组织权的高层 Team，应先确认是否能冻结其规划、动态工具和结果提交行为；否则它是一个需要适配的有状态外部系统，不能直接当作透明 Worker。

<a id="s20-02"></a>

### 20.2 用五个边界复用已有能力，不建立第二套 Harness

| 接口边界 | 输入／输出重点 | 自身拥有的事实 | 不应拥有的权力 |
|---|---|---|---|
| **ParticipantSession** | 锁定身份和契约、派发、原生事件、候选、等待、停止与恢复回执 | 原生会话与当前执行状态 | 任意改任务、批准结果、替换基线 |
| **ExecutionEnvironment** | 租约、输入物化、受限操作、导出、进程与停止确认 | 实际文件／进程／网络能力 | 根据模型文字扩权或改审核标准 |
| **RunRepository** | 幂等命令、合法转换、待执行意图、结果采用、恢复索引 | 正式运行状态及其事务边界 | 替代模型执行专业任务 |
| **ArtifactEvidenceStore** | 封存原件、内容身份、清单、证据引用与保留 | 不可变内容和可核对存储结果 | 仅凭文件存在批准业务质量 |
| **AssetCapabilityCatalog** | 搜索摘要、精读、解析锁定、能力／资源可用性 | 注册资产与真实能力映射 | 临时为某 Run 放松资产边界 |

这五个接口可以是五组函数，也可以复用目标仓库已有服务，不强制五个独立进程。前文的 Compiler、治理状态转换和调度应用调用这些边界；日志与可视化订阅投影，不成为第六个任务状态写者。

接口应避免把原始宿主 Session 对象、数据库连接、Docker socket、带全部权限的 Tool registry 暴露给领域层。适配器需要的底层句柄保持私有，以可信引用在边界上传递；源码里可见这些句柄并不代表模型也应该拿到它们。

<a id="s20-03"></a>

### 20.3 Session 契约应规定行为，不只是给方法起相同名字

```text
open(identity, locked_binding) → same logical Session binding
advance(dispatch_intent, current_context) → DispatchOutcome
request_stop(attempt_ref, reason) → StopReceipt
inspect(binding_ref) → native state + reliable cursor
checkpoint(binding_ref, fence) → checkpoint reference or unsupported
restore(logical_identity, checkpoint, new_execution_fence) → restored binding
release(binding_ref, release_authorization) → resource-release receipt
```

这是行为清单，不要求一次性实现全部方法。`restore` 未实现时返回显式不支持；不能在内部调用 `open` 再发原任务来冒充。`request_stop` 不等于 `release`，停止某次 Attempt 不销毁仍承担返工的 Session；`advance` 返回候选也不等于节点准出。

`DispatchOutcome` 至少能区分有效捕获的候选、业务阻塞、已登记的持久等待、技术失败、以及停止后的有限状态。没有正式提交而模型结束，需要保留真实原因；Provider 报错不能统一覆盖成“员工未提交”。子任务等待是合法结果，不能被通用补正循环当成漏提交不断重新催促。

同一逻辑 Session 在同一时刻只有一个有效推进者。重复的派发意图命中既有执行或回执，不启动第二个模型循环。adapter 可在进程内用同一对象保证；灾后则依赖持久执行权、原生会话历史与新代际恢复。两者不能只靠一个 Map 中存在 sessionId 判断。

当前 Pi 的 `NodeSessionAdapter` 接口直接引用原生 `prompt/abort/dispose/subscribe/steer` 等能力，并按 run/node/participant 绑定。[05-G53](appendices.md#ref-05-g53) 这提供可参考的行为点，但不要求 Jiuwen 逐个拥有同名函数。应该让两边通过同一行为探针，而不是把 Pi 类型逐行翻译成 Python 类。

<a id="s20-04"></a>

### 20.4 先做原生适配探针，把隐含差异提前暴露

| 探针 | 具体动作 | 必须观察的事实 |
|---|---|---|
| 初次与返工 | 同成员两轮工作，中间等待评审 | 正常路径原 Session 不变、旧工具调用历史存在、当前输入已更新 |
| 同时派发 | 同一成员并发收到两个意图 | 只有一个合法推进者，另一请求不隐式新建实例 |
| 正式提交 | 模型调用受控提交工具后仍试图继续行动 | 工具回执已入历史，后续业务动作在安全边界停止 |
| 工具批次 | 同一模型响应同时提出提交与写操作 | adapter 明确执行顺序和拒绝／截止规则，不依赖列表偶然顺序 |
| 模型停止 | 网络流、工具、子进程分别正在运行时停止 | 分别确认停止状态，不能只观察 UI 停止输出 |
| 上下文变化 | 输入失效、新 round、压缩或局部 replan | 当前权威事实不被旧摘要覆盖，契约与实际授权一致 |
| 容量恢复 | 图片和历史导致请求超限 | 同 Session 合法修复视图后继续，最新必要证据没有丢失 |
| 等待让出 | 子流程返回前父成员暂停 | 父释放活动槽但保留历史与责任，子完成后唯一唤醒 |
| 主机重启 | 检查点前后、工具结果边界分别中断 | 恢复声明与事实一致，不重放已完成副作用 |
| 资源失效 | 绑定 Skill、工具、环境配置不可用 | 明确缺口，不静默载入全局资源或替换模型 |
| 事件重复／乱序 | 重放原生结束事件与工具回执 | 不重复提交、不重复统计、不恢复旧授权 |
| 原生自动机制 | 宿主开启自己的重试、记忆、选人或自动总结 | 与 IPD 主责不竞争；实际配置与能力边界记录清楚 |

随附[Harness 能力探针清单](source-snapshots/step-04-support/harness-capability-matrix.yaml)可作为记录起点，当前均明确为未执行。实际探针使用 Harness 内核，但可以使用受控模型响应。再补一次真实模型小任务，检查语义指令与工具可用性；不能把第二步的成功外推为第一个步骤所有故障都已覆盖。

<a id="s20-05"></a>

### 20.5 上下文映射保留语义，而不强求宿主有相同消息通道

第 09 章已经规定稳定规则、当前事实、工作历史、Skill 目录／正文和实际工具的职责。适配器只负责将其映射到宿主支持的通道，并验证最终请求视图。Pi 的 system sections 可以使用；其他 Harness 可能用系统上下文、可信事件或固定的任务更新消息。关键是权威来源、更新时点、顺序和重复控制，而不是一定出现同名 XML tag。

专业画像不覆盖用户原始目标；任务材料仍是资料，不因进入一个高优先级通道就变成新的系统指令。对动态内容使用明确的资料与事实包装；实际权限继续由工具后端保证。若宿主无法更新 system，应选择明确的可验证方案并记录限制，不能未经检查反复追加全量契约直至上下文膨胀。

保持原生历史与压缩的唯一责任。IPD 可以提供必须保留的当前对象、压缩锚点和请求准入策略，但不再维护一份随时可能与原生历史分叉的“影子聊天记录”。完整原件存储与请求选择另行管理；共享团队记忆不能自动包含其他节点的私有历史和未授权输入。

动态 Skill／Tool search 可以继续按极简方案渐进披露，但**发现不等于生效授权**。已锁定包中的 reference 可以按需读；新执行能力需要落在本次许可范围，或经过显式局部变更。原生 SearchAgent 不能以优化为由把一个未授权动作工具塞进参与者。

<a id="s20-06"></a>

### 20.6 统一工具与环境，不为每种 Harness 留一条宿主绕行通道

文件读取、grep/find/ls、图片读取、编辑、Shell 和后台进程必须使用同一套授权视图。不能将 Shell 隔离到容器，却让宿主自带搜索工具读取全部仓库或临时目录。输入映射到相同虚拟路径，输出经唯一导出边界封存；第 10、11 章的路径与一致快照规则保持不变。

宿主控制工具可能不在工作容器内执行，例如资产查询、受限子 Run 创建和对象读取。这些工具必须由可信 broker 校验身份、当前资格、范围和数据出入，不能让容器获得运行时内部对象、Docker socket 或数据库凭据。外部工具返回一个宿主文件路径，不自动授予该路径读取权；由 adapter 验证来源并物化到被授权空间。

原生工具错误、子程序退出、检查结果和业务判定分别映射，保留诊断的对象、代码、位置和原因。`tool_result.isError=false` 只能证明工具协议层没有报告错误，不能推断目标产品通过；Shell 管道、后台进程和异步外部任务尤须如此。

对宿主自带重试，明确它是否重试 HTTP 请求、Tool 操作或整个 Agent loop。与第 14 章的唯一重试主责对齐；不能由模型、Harness、IPD 和队列四层各重试三次。已发生但回执未知的外部动作保留原业务操作身份，对账后再处理。

<a id="s20-07"></a>

### 20.7 用可验证的序列化规则跨语言，不以“都用 JSON”代替兼容

需要统一的不是漂亮缩进，而是缺失值和 null、默认值、额外字段、数字精度、Unicode、属性顺序、时间、枚举与错误码的含义。JavaScript 和 Python 都能解析 JSON，不代表它们对大整数、浮点数、重复键和字符串排序的处理可以直接用于同一个内容摘要。

选择一种版本化规范化方案。RFC 8785 JCS 定义了适用于哈希／签名的 JSON 规范化，包括确定属性排序、ECMAScript 数字表达和字符串保持；它是 Informational RFC，不是本方法强制采用的实现。[05-W46](appendices.md#ref-05-w46) 也可明确规定一个更受限的领域 profile，例如禁止任意浮点数、精确数量使用十进制字符串、整数只在约定安全范围内。**选择受限子集可以，声称实现了完整 JCS 却只调用 `sort_keys=True` 不可以。**

原资产格式到领域对象的归一化发生一次，并有版本；运行中比较摘要时不得反复补不同默认字段。`id+version` 和内容 hash 分别保存，不能用显示名或语义摘要替代。跨语言验证既要测“应相同”，也要测“本应不同”。

| 兼容向量 | 期望 |
|---|---|
| 相同对象，不同 key 插入顺序 | 规范化字节和 hash 相同 |
| 相同字符串，不同 JSON 转义书写 | 解析后内容相同则规范化一致 |
| 数组元素交换 | 有序数组不得被自动排序成相同内容 |
| `null` 与缺失字段 | 除协议明确规定默认外，不自动等同 |
| 组合字符与预组字符 | 不擅自 Unicode 归一化，原件身份保留 |
| ASCII、中文、补充平面字符、控制字符 | 明确编码和排序，禁止孤立代理项 |
| 大整数与高精度小数 | 按 profile 接受字符串或拒绝，不能静默舍入 |
| 重复 key、NaN、Infinity、非规范 ID | 明确拒绝或既定解释，不容忍两边产生不同对象 |
| 字节相同但授权／来源不同 | 内容可相同，采用与批准身份仍分别核对 |

随附 [`compatibility-vectors.json`](source-snapshots/step-04-support/compatibility-vectors.json) 给出有限的共享向量，并使用一个显式受限 profile 在 Python／Node 侧核对。它不覆盖 RFC 8785 全部数值语义，也不代表已经接入真实 Pi／Jiuwen 解析器；实际适配仍需把对应验证加入各自入口。

<a id="s20-08"></a>

### 20.8 共享的是语义测试向量，不是两份不断漂移的实现

语言和 Harness 适配可以分别实现，但应消费同一版本的协议与 conformance pack。向量包括输入、命令序列、允许的正式结果、不允许的副作用，以及应该保留的对象；不要只比较日志字符串或内部类名。

对有不同合法调度顺序的并行流程，比较可接受的因果关系与最终语义，不要求时间戳和所有事件逐条完全一致。对顺序有安全意义的步骤，如撤销资格先于采用、正式批准先于跨阶段消费，则必须严格验证。

关键适配向量至少包含：原 Session 返工，停止与释放分开，A/B/D/R 局部影响，必需 Review 缺失，输入权限、同 operation 重复和冲突，结果登记中断，父子等待，局部变更续接，以及确切最终包采用。方法未支持的项返回明确 unsupported，不能从测试清单删除后继续宣称全能力兼容。

差异应记为有责任人的 adapter gap：缺什么、影响什么、最小复现、拟采用方式、替代方案和验收。只在看板显示的名称不同不值得重构；正式状态权力、输入版本或副作用语义不同必须先解决。

<a id="s20-09"></a>

### 20.9 构建与安装需要验证“装出来的产品”，不只检查源码

发布候选应在干净且符合目标条件的环境中安装和启动。锁定依赖、构建生成文件、Prompt、Skill、模板、环境资源和检查器必须实际进入分发包；开发工作区能运行，不代表安装后相对路径、权限或生成脚本仍正确。

当前 Pi 的 `package.json` 声明了仪表板与桥接生成步骤、浏览器与服务端构建，并打包 assets/environments/prompts 等资源。[05-G54](appendices.md#ref-05-g54) 这可以说明源码之外仍有发布链条，不能据此宣称该构建本轮已通过。迁移时不要把这些步骤藏在某个开发者电脑的历史操作里。

建议提供一个只读或隔离的预检入口：核对模型连接配置、必需工具 Schema、资产解析、环境镜像／平台、命令与依赖、存储可写、最小权限和本地观察接口。预检不自动对生产系统做真实写操作，也不把打印“工具可用”当作业务功能已经验证。

构建产物和运行清单记录 engine、adapter、native Harness、protocol、asset catalogue、环境与模型配置的确切身份。只标 `latest` 或分支名不足以复现。也不要求把全部依赖详情塞入每个 Agent 上下文，审计清单与模型工作视图各有用途。

<a id="s20-10"></a>

### 20.10 升级、回退和数据迁移先考虑在途责任

默认策略可先采用：新 Run 使用新版本；旧 Run 继续旧绑定；不支持混版本恢复时先停止接入并在可恢复边界排空。不要让运行中的节点在下一模型轮自动加载新 Prompt 或新工具版本，也不要在新镜像中恢复旧状态时跳过兼容性检查。

数据迁移先备份一致的状态、资产引用、产物与原生会话位置；在副本上做 schema 和引用完整性检查，再切换唯一写入口。不要同时写旧 JSON 和新数据库，再按更新时间选择“看起来最新”的一份。只读兼容层可以保留有限时期，并说明淘汰条件。

回退代码不等于回退世界。新版本已经产生真实外部动作时，保留操作账本、版本和处置，按第 14、16 章处理补偿或更正；不能回滚状态文件后让动作再发生一次。关闭子 IPD 开关只能阻止新的不允许委派，不应抛弃已经合法创建、仍承担责任的子 Run。

局部 replan 与软件升级也不同。前者是任务内明确的基线变化，后者是引擎／适配实现变化；二者都需要保留既有事实，但不能通过同一个“重启”按钮混用。未实现在线兼容时，采用明确的停机恢复窗口比冒险热替换更可靠。

<a id="s20-11"></a>

### 20.11 故障操作手册要让人能采取安全动作，而不是一律重启

| 观察到的问题 | 先确认 | 合法处置方向 | 不应执行 |
|---|---|---|---|
| 看板停在旧状态 | 权威状态、API、客户端脚本与游标 | 修复投影或重新连接 | 因页面不动重复创建业务 Run |
| 请求体超限 | 最终字节、多模态与当前请求视图 | 同责任修复容量条件后恢复 | 原历史原样无限重发 |
| 成员长时间没有新事件 | 实际工具／进程、等待条件、网络和观测缺口 | 诊断或有界停止，保留工作 | 只凭“没说话”就创建替代成员 |
| 存储锁冲突 | 当前控制者身份、代际、活跃写者 | 验证接管或等待 | 仅凭旧 PID／文件年龄强删锁 |
| 外部动作结果未知 | 原业务 operation ID 与目标系统回执 | 对账、隔离、必要人工运营处理 | 换 ID 重做或填成功 |
| 取消后工具仍写入 | 停止回执、进程树、环境隔离 | 先可靠停止／隔离旧写者 | 启动同责任新 Attempt 竞争工作区 |
| 恢复时 Skill／镜像不同 | 原锁定摘要与当前可用版本 | 找回原版本或授权迁移 | 用最新版本假装旧环境 |
| 漏了最终通知 | 正式结果是否已登记、通知责任是什么 | 重试通知／提供结果入口 | 重开已成功的生产和评审 |

人工运营对账是系统故障处置，不等于引入每个业务节点的强制 HITL。仍应记录谁做了什么、依据什么、是否改变任务。观察和下载接口默认只读；分享 HTML 或开放网络访问前处理原任务、客户信息、内部地址和证据权限，不能因为是本地页面就假设可公开。

### 20.12 最小发布包同时面向使用者、开发者和未来维护者

一个可交付版本至少包含：安装与预检说明、支持画像、最小任务示例、失败与恢复示例、版本清单、契约及适配测试结果、已知限制、启动与停止方法、结果位置、日志与安全操作说明。无需几十份文档；这些内容可以组织在一份清晰 README 和少量机器可读清单中。

```yaml
# 发布清单模板；具体引用须在构建／验收时生成。
release_manifest:
  release_id: minimal-governed-runtime-candidate
  protocol_ref: governed-collaboration-v1
  engine_build_ref: exact-build-id
  harness_adapter_ref: exact-adapter-build-id
  harness_revision_ref: exact-native-revision
  capability_profile_ref: local-governed-v1
  assets_snapshot_ref: locked-assets-snapshot
  environment_profile_ref: isolated-local-profile-v1
  conformance_report_ref: pending
  real_task_report_ref: pending
  recovery_guarantee: process-restart-unsupported
  data_upgrade_plan_ref: none-for-first-release
  rollback_policy_ref: stop-new-runs-and-preserve-existing
  known_limitations:
    - 本例尚未填写实测验收；不得以其存在宣称候选可发布。
```

字段不要求所有实现原样采用；其作用是让使用者知道这个版本能保证什么，开发者知道哪里未实现，维护者知道怎样升级和恢复。`pending` 是示例占位，不是通过状态。最终发布器应拒绝缺少关键验收证据的候选，除非明确作为非生产实验版本并限制使用范围。

## 全文收束与交付边界

第 01—20 章组成同一条实施路径：方法说明为何控制，资产说明如何复用，运行时说明怎样执行，效率与验证说明怎样判断收益，落地部分说明怎样在具体 Harness 中兑现这些要求。**本合稿完成文本级贯通和编排，不等于目标能力已由真实系统全部证明。**

本次统一与澄清见独立的《贯通检查与修改记录》。完整自研提交／合并历史的逐项差异审阅仍是明确的资料覆盖缺口；已读源码、历史实验、目标建议和纯示例测试继续分别标记，不以合稿覆盖它们。

开发落地从 M0 的真实纵向切片开始，而不是把全文每个名词都建成类和服务。团队、层级、复杂变更的入口只在对应机制通过测试后开放；不需要复杂组织时，让系统保持简单。
