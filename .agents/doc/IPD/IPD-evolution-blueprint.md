# IPD 层级受控协作演进蓝图

**面向：Nepham / Pi IPD 团队**  
**代码基线：`Nephamaster/pi@3f175f76dcd372d51834e3c9e71a8fbade277a45`（2026-09-16）**  
**性质：任务二的建议蓝图；不是已实现功能说明，不代表完整代码审计或性能实测结果。**

## 0. 总体决策

建议把当前系统逐步演进为：**运行在 Pi AgentSession 之上的、以职责契约和版本化证据为核心的层级受控协作运行时**。IPD Tool 继续只是入口；增加能力的是治理与执行内核，而不是 Tool 提示词。

推荐路线：

> **当前可靠性基线收口 → 生命周期与持久状态底座 → 单人节点下的阶段评审 → 静态多人工作包和评审团 → 一层受控子 IPD → 治理团队与评审内部工作流 → 经评测开放更深层委派和受控重规划。**

不建议同时放开多成员、动态建图、递归、评审聚合和崩溃恢复。每一步应有独立可用版本、明确准出测试和回退边界；后续能力只对新 Run 开启。

以下 `StageScope`、`TeamPlan`、`ReviewBundle`、`Finding`、`DelegationContract` 等名称是本蓝图提出的工程概念，不是华为原有术语，也不是当前仓库已经支持的完整 Schema。

## 3. 目标架构：一个内核，两种组合，三条清晰边界

```text
外部 Pi / 交互式启动器 / 获准的内部参与者
                      │
                 IPD Tool 适配器
                      │
          治理入口：选择规范 → 设计 → 编译
                      │
     统一 Runtime：执行所有权、就绪、等待、取消、收口
           ┌──────────┼──────────┐
           │          │          │
       单人工作包   团队工作包   有契约的子 Run
           └──────────┼──────────┘
                      │
           Pi Participant Executor
      原生 Session / 模型 / Tool loop / 上下文
                      │
      EnvironmentManager / Docker / 受控工具代理
                      │
         元数据事务库 + 不可变产物 + 遥测
```

### 3.1 不把语义角色和执行方式绑成同一个枚举

`execution`、`review` 回答“承担什么责任”；单人、团队回答“如何实现责任”；`delegation_policy` 回答“是否允许把部分工作委派给子 IPD”。三者分开。

因此，一名执行者可以在授权范围内委派；一个团队也可以在明确成员权限下委派。评审团也可以组织内部验证，但不能因此获得生产者的修改权限。

节点始终保留唯一的外部契约和正式提交边界。团队成员的工作不是多次互相覆盖 `submit_artifact`，而是先形成内部贡献，再按固定规则形成该节点的一份正式提交。

### 3.2 两种组合必须区分

**局部 TeamPlan**：当前节点内已经能确定的分工、依赖和汇总方法。它继承当前节点契约，无须再运行一套 ST—Designer。两名研究员分工搜集证据后由整合者汇总，就是这种情况。

**完整 Child IPD Run**：当前工作确实需要新的局部任务组织、规范选择或独立过程管理。它有派生任务、独立基线、状态和结果，但权限与质量义务受父级约束。

二者复用调度、产物和等待机制，却不承受相同治理开销。不能让“多个成员”自动等于“重新启动完整 IPD”。[R5–R7]

### 3.3 定义身份，避免以后各层自行拼字符串

| 对象 | 唯一含义 |
|---|---|
| Run | 一次治理执行，根 Run 或子 Run |
| Node | 对外有目标、交付与准出责任的工作单元 |
| Participant | 节点内具有明确职责和授权的成员，不等于 AgentCard 模板 |
| SessionBinding | Participant 的持续 Pi 会话与模型/资源绑定 |
| WorkRound | 输入或质量返工带来的逻辑工作轮次 |
| Attempt | 同一轮次中的技术执行尝试，不消耗同一语义的质量返工额度 |
| ExecutionEpoch | 执行所有权代际；旧执行者不能在新代际提交 |
| StageScope | 若干相关工作与阶段出口的质量控制范围，不必创建一个 Agent 来“执行阶段” |

环境层已有 lease generation，不应删除重写；需要补的是跨运行时、回调和持久状态的一致提交检查。不要把环境 generation、技术 attempt 和质量 round 强行合并。

## 4. 阶段评审：先改变交接与批准语义，再减少评审节点

### 4.1 分离“已封存”“仍有效”“可以放行”

当前 `submitted/approved` 的二分过于贴近逐输出门禁。建议保持产物不可变身份，并把以下维度独立建模：

- **完整性**：文件已形成并通过相应确定性检查。
- **有效性**：它实际依赖的输入版本没有失效。
- **批准范围**：它获得了哪些标准、哪些组合对象、哪个阶段出口的批准。

`sealed` 不是低质量通行证，也不是批准。阶段内可消费，是一个单独的、事前编译的使用许可。工作执行完成和质量准出应分别表达：前者可以使阶段内下游获得候选输入，后者控制跨阶段出口和最终交付；不能继续用一个 succeeded 同时表示这两件事。

### 4.2 首版只开放显式阶段内暂准交接

设同一阶段内有 A、B，B 需要 A 的结果，阶段末 R 联合评审二者：

```text
同一阶段：A --封存的阶段内输入--> B
                 A、B --固定版本组合--> R
R 通过后：阶段出口 ------------------> C
```

建议规则：阶段内部可以按显式声明消费已封存、完整且有效的候选；跨阶段和最终交付仍要求对应 Gate。接收者上下文必须标识“尚未完成阶段准出”，并记录精确输入血缘。未声明阶段的旧工作流仍按原有严格模式执行。

Compiler 同时检查数据依赖、评审对象和放行依赖，不另造手写 `dependsOn`。同一阶段内也可为重大节点设置更早的独立 Gate；阶段不是取消局部高风险控制。

新模式不再强制每个中间输出单独配置 semantic criterion 和专属 Reviewer；而是要求 ProcessSpec 的必要质量义务、跨阶段出口和最终交付得到完整覆盖。确定性文件检查仍按产物性质保留，不能把减少人工式评审理解为取消完整性与事实验证。

当前 Compiler 还禁止同一 Review criterion 隐含覆盖多个输出。未来整体一致性标准应显式绑定一个多对象 ReviewBundle，而不是把同一 criterion 偷偷重复挂到多个 target 上。[C2、C4]

### 4.3 用 ReviewBundle 固定评审对象，而不是只写“评审整个阶段”

一次评审固定：目标产物及精确版本、必要背景输入、标准集合与版本、所对应的基线。阶段整体属性，例如“数据口径与报告结论一致”，绑定整个组合，而不是某一个文件。

建议输出分为三类记录：

| 记录 | 含义 |
|---|---|
| Assessment | 某个专业成员针对确定对象和标准的证据判断 |
| Finding | 可持续跟踪的问题、责任和修复要求 |
| GateDecision / ReleaseCertificate | 由固定聚合规则形成、由 Runtime 登记的阶段或输出准出 |

原始 Assessment 保留不覆写。ReviewBundle 改变时，旧决定不再用于批准新版本；Finding 仍可待处理，直到修复并复核，而不是跟着旧 Review 一起丢失。华为公开评审意见闭环功能为这种“决定与问题分别管理”提供了现实参照，但本数据结构属于项目设计。[R1、R2]

### 4.4 “保守撤销批准”和“精确重做工作”采用不同策略

第一版联合评审只要任一依赖变化，就撤销整个组合批准，最容易保证正确性。但是重做工作按实际输入血缘传播：A 变更时，只重做依赖旧 A 的成果，不因为 R 同时看过独立的 D 就重新生产 D。

之后才引入按标准声明的依赖集合，允许携带旧版本中仍适用的评审证据。复用必须检查对象、标准、方法及依赖版本一致，不能由整合者口头宣布“应该没影响”。

Finding 至少关联：标准、缺陷位置、证据、受影响输出、责任节点/成员、修复条件、复审状态。修复建议被提交为已处理，不等于已通过复审。对于跨多个节点的责任争议，可以先补充诊断；不能凭允许列表随便挑节点返工。

## 5. 多人节点：先实现可预测的团队，不先实现群聊

### 5.1 第一种团队只做“并行分工—固定汇总”

TeamPlan 明确成员、职责、输入、内部贡献、依赖、必要完成条件和唯一提交者。可选成员失败的容忍条件也事先明确；缺失必需贡献时不能汇总为完成。

各成员拥有自己的持续 Session、环境租约和输入视图。现有 EnvironmentManager 已按 run/node/participant 建立身份，是可复用基础；需要补齐的是 participant 级派发、产物归属、上下文和生命周期，而不是重新写容器后端。[C5、C6]

外部节点契约不变，内部成员提交不可变 contribution；整合者读取贡献，生成节点正式产物。默认禁止多个成员直接编辑同一路径。代码类协作使用独立分支/工作树或补丁，由整合步骤处理冲突并验证；不能仅凭共享 workspace 期待模型主动避免覆盖。

### 5.2 评审团先采用分项判断，不采用多数票

评审计划为各标准绑定必需专业意见。不同专家可以评不同维度；多个专家评同一标准时，先独立判断，再进入必要的冲突澄清。

默认规则：必需标准和必需专业意见齐备；未解决的实质 FAIL 不得被 PASS 票数抵消；无法完成必要核验则阻塞。主持人负责组织证据与分歧，不具有覆写事实、降低标准或强制通过权限。达到讨论上限也不能变成通过。

“独立性”逐步由仅比较 AgentCard ID，升级为检查实际贡献历史、参与者身份和授权。模板相同不必然是同一个参与者；模板不同也不能洗掉实际生产贡献。旧规范的更严格限制在迁移前保持不变。

### 5.3 评审内部工作流的允许范围

复杂验证可以包含专门的测试、计算、渲染或证据收集成员。它们只写隔离的验证衍生物，不写被评成果。最后由评审者依据冻结标准形成结论。

这样支持“评审团内部有工作流”，但不把 Reviewer 的只读限制直接解除，也不让同一个人一边修原件一边批准它。

## 6. 受控子 IPD：开放的是委派能力，不是根权限

### 6.1 一个正式 DelegationContract

父节点允许某个 Participant 委派时，预先冻结：可委派的责任范围、可传递输入、必须满足的输出/证据要求、允许的规范集合或选择规则、资源上限、子 Run 数量、深度和取消/结果回收策略。

Agent 提交子任务需求，系统注入 rootRunId、parentRunId、parentNodeId、participantId、parentRoundId、baselineId、generation、depth。模型不能自行设定自己属于哪个父级，也不能自行声称有剩余授权。

可以继续对模型显示一个 `ipd` 工具，但内部入口与外部根任务入口必须采用不同能力上下文。内部创建不允许伪装成根 Run 以重置深度或预算。

当前默认 Docker 禁网并拒绝未经声明的宿主工具闭包。内部 IPD 调用应作为宿主控制面的受限代理能力提供，不能挂载 Docker socket，也不能让容器自行创建宿主容器；获得委派能力不自动获得联网能力。[C1、C5]

### 6.2 子任务输入不是完整根任务的复制

保留用户原始任务作为根来源；子任务是当前父契约范围内的派生请求，携带来源锚点、必要材料、明确约束和预期结果。禁止不断把完整根任务交给下一层重新规划。

子 ST 选择规范，子设计师按该规范与继承契约组织局部工作；父输出的必需标准不能因选择更宽泛的子规范而被删除。结构/权限可确定性检查，业务语义是否真正为子问题还需设计审查，不能假称一个 Schema 就能证明语义包含关系。

对已有适用 Workflow 模板可以复用当前“绑定当前输入并重新编译”的快速路径，减少重复规划。它必须满足子任务契约和授权，不能绕过当前标准。[C7]

### 6.3 子流程创建必须持久幂等

建议将委派意图与一个稳定 delegation slot 绑定；系统签发 operation ID，关联父轮次和基线。同一 ID 同一请求返回同一个 Child Run；同一 ID 不同请求拒绝。仅使用模型每次新生成的 tool_call_id 不能阻止重试时重复创建。

创建意图、子 Run 记录和待执行命令需进入可靠事务/待办机制。设计启动确认、结果通知、重连查询和去重，不把某次进程内 Promise 当成唯一等待事实。[R5、R6]

### 6.4 父节点等待不是失败，也不能占满子任务需要的执行槽

第一版可先支持“创建一个子 Run，然后挂起父级当前模型循环”。在合法工具回执边界落盘 waiting-child 条件，保留同一 Pi Session，释放活跃模型/工作调度槽；子结果到达后由 Runtime 重新唤起该 Session。

这里要改造现有 Worker 的返回语义：无 submit_artifact 但合法等待子 Run，不是漏提交协议错误。必须验证 Pi 原生工具消息成对完整、等待可取消、不会继续让模型调用轮询工具。这是实现前需要做的小型适配原型，不假设当前 Pi 已提供现成的任意点挂起接口。

等待仍消耗 Session 内存、可能的容器保留资源，因此活跃槽、保留实例、环境内存要分别计量。资源不足时拒绝或排队，不能为了腾内存偷偷销毁正常返工还需要的 Session。

### 6.5 子结果可用不等于子责任已经永久关闭

这是与同 Session 返工要求密切相关的状态边界。建议区分：

```text
child running → result_ready → awaiting_parent_acceptance → committed/closed
                      ↑                    │
                      └─ 定点返工，同一Session ┘
```

`result_ready` 表示子流程已形成内部合格、可供父级消费的固定版本结果；并非父任务也已经通过。需要继续承担返工责任的子成员保持绑定。父级完成相关验收后，才允许关闭责任和释放资源；保守实现可延续到根 Run 最终收口。

父级返工请求经过 DelegationContract 定向回到对应子责任，不直接任意修改子图状态。子结果更新使实际依赖旧版的父产物和批准失效。取消父节点则取消所辖未结束子工作；第一版不开放脱离父级继续运行的模式。

### 6.6 限制整个执行树，而不只限制深度

起步建议根深度为 0、最多创建到第 1 层；这是默认启用策略，不是永久架构上限。还必须限制每次委派的分支数、累计子 Run 数、团队成员数、总活动参与者、模型请求、容器内存/CPU/PID和无进展执行。

同时限制执行作用域深度与子 IPD 深度，防止通过不断嵌套 TeamPlan 绕过 child-depth 限制；累计子 Run 数也不能在一次返工后清零。

这些额度由根执行树统一归集，父子/团队/治理角色不能各自重新领取一份满额配额。子授权只能收缩，不能扩张：

> child 可用权限 ⊆ 部署允许范围 ∩ root grant ∩ 父级可委派范围 ∩ 子任务实际需求。

对父成员工具集与可委派权限可以显式区分：协调者自身不一定需要某种生产工具，但获准委派的专业工具集合必须由根策略明确批准，不能由模型临时扩大。

## 7. 治理团队：先改变工作协议，不默认增加人数

### 7.1 用固定 GovernanceProfile 引导，避免无限元规划

谁组织 ST 团队和设计团队？先由可信的 GovernanceProfile 定义：单人、选择者+专业顾问、主设计师+领域专家+验证者等少量受控模板。它不调用另一个完整 IPD 来设计自己的存在。

团队运行仍使用同一 ParticipantExecutor、产物、事件和等待机制；只是启动前的控制步骤由可信配置给定。不要复制第三套团队运行时。

### 7.2 ST 的正式职责不扩张

ST 团队共同评估候选规范，但只有指定提交者输出一份 ProcessSelection。顾问可以检查适用条件、关键风险、职责匹配；不能设计完整任务图，也不能因人员不足裁剪规范。当前控制面已经有选后 staffing 检查，应将适用性与可实现性诊断分别呈现。[C7]

默认仍用单 ST。只有候选冲突或专业跨度确有必要才启用顾问，不能所有任务都固定多轮会议。

### 7.3 设计团队采用提案—整合—校验，不多人竞争覆盖草稿

主设计师持有唯一正式草稿提交权。领域专家提交带 base_revision、修改范围、理由、影响与证据的 DesignProposal；主设计师通过现有 draft 工具整合；Compiler 校验；独立设计检查者判断是否过度设计、覆盖空洞或评审遗漏。

先不要让每名专家直接整项替换相同 node/coverage/completion。只读同一基线不等于可以无冲突共同写同一草稿。治理层最终各有一个正式输出，保留专家意见和未采纳原因。

系统工程师或架构师是可以承担的专业职责，但不据此声称复制了华为某个唯一标准组织。[R3]

### 7.4 Prompt/Skill 与引擎能力版本绑定

为治理角色提供只读 `EngineCapabilities` 投影：支持的节点实现方式、阶段交接模式、成员数、最大深度、可委派角色、环境条件、支持的提交类型等。新能力未启用时，不在 Prompt 中提前宣称它可用。

common 只保留统一权限/信任边界；专业角色保留专业方法；节点成员获得自己的职责契约和必要团队接口；当前轮次注入等待/贡献/评审/返工事实。角色方法不能覆盖契约，子上下文不复制全体对话，Pi 仍是唯一会话/压缩实现。

## 8. 运行底座与技术选型

### 8.1 近期继续 TypeScript + Pi + Docker，不换大型编排平台

保留 Compiler、原生 Pi 会话、环境 Provider、资产体系和轻量看板。Runtime 抽出实际会被单人、团队和 Child Run 共同使用的少量执行原语：认领执行、准备输入、派发成员、等待结果、提交、取消、收口。

不为了“统一”立即引入任意脚本路由、通用规则 DSL、Kafka、Kubernetes 或分布式 Worker。将来如果明确要求跨主机高可用，再评估外部持久工作流后端；不要让自己的 Runtime 和外部引擎同时控制同一状态。

### 8.2 推荐 SQLite 承担本地权威元数据，但必须真正改变写入方式

目前 FileRunStore 每次 mutation 会读、clone、序列化并写回整份状态，包含不断增长的事件和操作记录。加锁解决竞争，不解决长历史的写入放大。[C8]

建议逐步改为：SQLite 保存 Run、参与者、轮次、等待、产物索引、评审、问题、批准、幂等操作和待执行命令；大产物、锁定资产和会话内容保留外部文件；高频遥测独立保存。

**仅把整份 JSON 塞进 SQLite 一个字段，不算完成优化。** 必须有增量修改、索引和短事务。数据库事务内不等待模型、容器或网络；外部操作采用持久命令和回执对账。

SQLite WAL 支持读写并行，但仍只有一个写者且不适用于跨主机共享网络文件系统。数据库应位于运行时宿主的本地盘。[R9] Node 的 DatabaseSync 是同步 API，可用专门 Worker 线程承接数据库工作；固定实际支持的 Node 小版本，并评估当前接口稳定级别，不把“Node 24”当成所有小版本接口完全一致的保证。[R10]

文件与数据库不组成一个跨系统原子事务。产物先稳定封存、校验和发布到不可变位置，再在元数据事务登记；失败产生的未登记产物可回收，绝不能先批准一个还没可靠存在的文件。

迁移时同一 Run 只使用一种权威 Store。旧 JSON 可只读导入或在停止状态迁移，不长期双写，也不让看板继续从旧文件反推状态。

### 8.3 同一活跃 Session 与崩溃恢复要分别承诺

正常返工、团队协作和父级等待：继续同一活跃 Session，不用“重新加载快照”替换。

宿主崩溃：原 JavaScript 对象已经不存在。先实现检测、冻结未确定副作用、对账和可解释 interrupted 状态；不能把失败简单改为 running。

若要实现崩溃后继续，需要单独明确“同一逻辑会话”恢复契约：绑定原会话历史、相同资产版本与参与者身份、新执行代际、环境/产物检查、未确定 Tool 副作用对账。先只允许已提交回执的安全边界恢复。不承诺任意点无损恢复，也不把普通恢复作为常态压缩资源手段。

如果坚持进程崩溃后也绝不能创建新的会话对象，则应明确该执行不可自动恢复；这是产品保证的取舍，不是补一个 checkpoint 字段就能同时满足。

### 8.4 全局资源控制是递归前置条件

当前 maxConcurrentNodes 挂在单个 WorkflowRuntime 上。未来新增 Project/Root 级准入，覆盖 ST、设计、执行、评审、验证助手和子 Run。模型、CPU/IO、活跃容器、保留 Session 分别计量，公平调度，等待子任务不占据子任务启动所需全部槽。[C3]

重试、结构化补正、质量返工和设计修订采用独立策略；无进展达到保护阈值是阻塞/终止，不是自动通过。递归深度高且工作量不减少、重复委派相同材料/范围，是风险信号；启发式可以要求更强理由，但不能假称哈希就能证明两个自然语言任务等价。

## 9. 分阶段实施计划

每一阶段至少拆成“契约/确定性实现/适配接入/回归与资产同步”几批改动，不要求一个 PR 完成整阶段。

| 阶段 | 可交付版本 | 前置 | 明确不开放 |
|---|---|---|---|
| M0 | 当前单层运行的可信基线和测量包 | 最新 main | 新增多人和递归 |
| M1 | 成员级身份、执行所有权、持久等待和全局准入 | M0 | 动态成员、自动深层委派 |
| M2 | 单人节点下的阶段门禁和定点返工 | M1 关键生命周期部分 | 评审团、子 Run |
| M3 | 静态多人工作包与分项评审团 | M1+M2 | 自由群聊、自主招人 |
| M4 | 授权执行者的一层 Child IPD | M1+M2，默认基于 M3 验证 | 子流程脱离父级运行、任意内部角色委派 |
| M5 | 固定治理团队、受控评审内部工作流 | M3+M4 | 无限元规划、默认全员协商 |
| M6 | 受控结构重规划、证据驱动的更深层委派 | 前述版本质量和资源实测 | 自动降标、未经验证的全自治自演进 |

### M0：收口当前基线，不重复“建设已经建设的模块”

针对现有取消、并发、Approval 失效、独立输出视图、Docker 路径和环境代际，建立贯穿层级的回归；补齐控制角色到 Runtime 的耗时和失败来源采集。冻结当前接口与小型端到端样例。

**准出**：必需评审未完成不能成功；失效判断不能继续批准；取消后的迟到回执不能推进；各本地工具遵循同一输入视图；真实浏览器运行生成脚本并更新 DOM；连续运行的性能与资源分解能被解释。

**主要代码**：`runtime-state.ts`、`workflow-runtime.ts`、`review-validation.ts`、`environment/*`、`visualization/*` 与对应测试。已有保障作为测试起点，不预设仍全部有缺陷。

### M1：建立扩展所需的身份和生命周期，不立即开放多人

先把 ParticipantExecutor 从以 `agents[0]` 为中心的 Worker 中提取；Compiler 用 node+participant 解析资产；所有事件、提交、环境和取消带有一致身份。此时仍用单成员运行，确保行为不变。将控制面依赖的具体 FileRunStore 解耦到实际所需的 Store/订阅接口。[C4–C8]

再交付 SQLite 增量 Store、持久命令/等待、根请求去重、执行认领代际、资源准入和启动对账。优先做到“不会重复、不靠偶然回调唤醒、丢失能解释”；安全边界的逻辑 Session 恢复可在该阶段子版本推进，但正常返工仍保持原对象。

**准出**：并发创建同意图只产生一个执行；旧代际拒绝提交；通知丢失后依靠持久结果仍可唤醒；准备环境/写入产物/登记回执各断点均可解释；多 Run 不会把同一并发上限各自乘开。

### M2：先在单人节点上改变评审粒度

发布支持 StageScope、阶段内候选使用和 ReviewBundle 的新 Workflow 协议；保留旧 v3 严格模式。把“数据可用”和“阶段可放行”拆开；引入整体属性标准和持续 Finding。

**准出样例**：A→B 同阶段且无逐点人工式审查；R 审 A+B 后 C 才可启动。A 返工导致 B、R、依赖的 C 精确失效，独立分支 D 不重新生产。旧 R 结论不能批准新版本，旧问题又不能被丢掉。

现有内容 ProcessSpec 明确规定多次独立评审，不能偷偷变成一个终审。发布经过明确设计的新规范版本或明确规定“哪些审查责任可由同一评审节点合并履行”，同时保留所有必需标准、对象和成熟度时点。[P1]

### M3：静态多人工作包，然后分项评审团

先支持两到三个固定成员的分工+整合模式；新增成员贡献协议、唯一节点提交者、内部依赖与成员环境。再支持固定分项评审和冲突处理。参与者数量属于配置，不硬编码成固定团队规模。

**准出**：一个成员失败不重跑不相关贡献；同一成员不可双重并发派发；贡献遗漏不能被整合声明掩盖；成员不能修改其他成员材料；不同专业 FAIL 不能被多数 PASS 抵消；成员和环境身份均可追踪。

### M4：受控子 Run，初始仅一层

先交付父子关系、DelegationContract、启动幂等、等待、取消、结果交回、父级返工到子责任；只允许冻结权限中获准的执行者调用。子 Run 可以运行当前单人或静态团队策略，但不能继续嵌套。

**关键验收**：只给系统一个活动工作槽时，父等待不会导致子永远无槽；工具返回丢失不重复建子；子结果先到、等待登记后到不会丢唤醒；父取消/输入失效后，子旧结果不会被采用；父返工保持对应子责任 Session；子成功不能直接使父 Gate 通过。

默认依次推进“指定子模板的静态调用 → 执行者在授权范围选择是否调用完整子 IPD”，避免第一次就让所有人自由选择和修改局部拓扑。

### M5：治理团队与评审内部工作流

使用固定 GovernanceProfile 运行 ST 顾问、主设计师/专家/验证者；提案是内部产物，正式草稿仍单一提交。对有复杂验证必要的 Review 开放验证专用子流程，继承只读目标与输出限制。

**准出**：团队意见不同仍形成唯一可审计输出；其他成员不能抢占提交权；陈旧提案无法覆盖新草稿；治理过程不会先调用 IPD 来规划自己；验证助手不能修改被评产品或冒充其生产者。

### M6：有限动态重规划与更深嵌套

先补全显式 replan 的控制链：暂停影响范围、保留任务/spec/标准、检查输出和依赖改变、编译新版本、处理原成员责任与会话、恢复。动态局部计划也通过相同机制，不靠修改内存数组绕过 Compiler。

随后基于可对照的数据，按任务族开放深度 2 及更高上限。每提高一层都测试累计宽度、资源、公平调度、取消和跨层失效。后续如果真的要求跨主机高可用，再评估分布式执行或成熟工作流后端，不能把它当本路线的第一项。

## 10. 性能与评测：保证复杂能力有净收益

### 10.1 从分解时延开始

记录接入/选规范/设计/编译/环境启动/队列等待/模型/工具/封存/校验/评审/返工/最终交付。模型记录调用数、输入输出 tokens、可得的缓存信息和请求字节；环境记录启动、导入、导出、内存和活跃/保留数量；存储记录事务耗时和读写量。

不要仅使用 Run 总时长，也不要把“更多 Token”自动当成低效。比较必须同时看最终质量和成本。

### 10.2 先做这些优化，后做复杂调度算法

复用锁定资产和内容寻址输入；同 revision 的验证缓存绑定全部 Compiler 输入与规则版本，提交时重核版本而不是盲信旧 PASS；准备环境可受控预热但不复用带有其他任务数据的脏实例；看板用 revision/增量读模型而非每个观察者读整份历史。

当前轮次只注入本成员需要的状态、输入引用和反馈；团队沟通使用贡献/意见/决策摘要，不广播所有历史。多模态请求同时受 token 与字节限制，避免增加 Reviewer 后重现历史图片累积问题。

### 10.3 基准组和判定

至少比较：单 Pi；当前单成员 IPD；阶段评审 IPD；静态团队；受控委派。使用同一任务材料、版本、基础模型条件和冻结最终标准，记录每个系统实际获得的资源。

任务覆盖：低复杂串行、真实可并行、跨成果一致性、必需事实不足、评审分歧、定点返工、单层委派和故障注入。不能仅证明 PPT 一个场景能跑。

核心指标：最终任务可用率、严重缺陷逃逸、误打回、实际受影响与被重跑范围、成功任务耗时/调用量、总尝试成本、队列等待、无进展次数、取消残留、重复副作用、恢复成功率。研究性质比较用独立隐藏问题/标准验证，不能让系统自己的 Gate 同时作为唯一裁判。

确定性正确性用例必须全部通过。模型质量与性能阈值应在 M0 基线后按任务族预先约定，并给出重复运行范围与不确定性；不在没有测量时承诺“提速 50%”。

## 11. 迁移、回退和发布纪律

每个能力必须带一组完整变更：Schema/Compiler、Runtime、适配与环境、Prompt/Skill、样例/测试、只读可视化。只更新治理 Prompt、但 Runtime 未支持的能力不得开放。

现有 v3 工作流继续保持旧严格语义；新协议由版本分支解析后进入同一内部模型。兼容性不意味着旧规范自动采用更宽松交接。正在运行的 Baseline 不随代码发布热变更，先排空或运行固定版本；失败回退禁用新 Run 的新特性，而不是在途中把多人降为单人。

SQLite 迁移只保留一种权威状态源。旧状态不可理解时只读展示并报告版本，而不是用默认值伪造恢复。旧 legacy-srt 保留独立兼容测试，但多人和子流程首版优先只在受控 Docker 模式启用，避免同时证明两套权限边界。

看板跟随里程碑提供 Stage、成员贡献、Gate 对象版本、Finding、父子树和资源等待；阶段与角色没有实际运行时记录时不显示为“已完成”。快照保留当时的状态序号与版本，外部分享仍需要数据脱敏或访问控制。

## 12. 最先启动的工作包

第一批并不是“启用多个 agents”。建议先写入项目的决策记录和可执行测试：

| 工作包 | 结果 | 归属里程碑 |
|---|---|---|
| 更新基线与回归包 | 最新修复状态、真实端到端运行、耗时分解 | M0 |
| 定义身份与输出生效条件 | Node/Participant/Session/Round/Attempt/Epoch；提交守卫测试 | M1 |
| 定义持久状态与恢复保证 | Store 迁移设计、命令/等待生命周期、恢复安全边界 | M1 |
| 阶段评审小型状态模型 | 阶段内 A→B、R 审组合、C 跨出口、定点返工 | M2 先做设计和纯函数原型 |
| 定义团队与子 Run 的分界 | 何时 TeamPlan，何时完整 IPD；不产生第三套引擎 | M3/M4 的设计前置 |
| 定义父级验收与子责任关闭 | result_ready≠closed；同 Session 返工与资源保留政策 | M4 的设计前置 |

这些方案可以并行设计，但代码启用遵循依赖。用每个版本已经证明的能力推进下一步，不用一张最终愿景图替代所有中间验收。
