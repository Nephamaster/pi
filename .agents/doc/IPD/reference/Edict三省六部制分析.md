# edict 未成功原因与 IPD 经验教训分析

> 面向 IPD 风格的多智能体长程任务范式  
> 分析基线：`cft0808/edict` `main` 分支，提交 `14a2075`（2026-05-06）；分析时间 2026-08-23。

## 1. 核心结论

把 edict 简单归类为“失败项目”并不准确。它在概念传播和开源影响力上相当成功：用“三省六部”把多智能体中的职责分离、前置审议和执行调度讲得直观易懂，2026 年 6 月已有 1.6 万以上 GitHub Star。[第三方研究](https://rywalker.com/research/edict)也将“门下省否决权”视为其最有辨识度的设计。

但若成功标准是：**成为一套可泛化、可验证、可稳定恢复、可用于长程复杂任务的生产级多智能体范式**，edict 尚未成功。其根本问题不是“三省六部”这个隐喻不好，也不只是模型能力不足，而是：

> **项目提出了制度化控制的正确问题，却没有把关键制度完整固化为确定性运行时；不少控制仍依赖 Agent 理解提示词、按顺序调用命令并正确维护状态。**

这造成了四个直接后果：

1. 固定单线流程不能适配异构任务，简单任务付出额外审议成本，复杂任务又缺少足够的分支、汇聚和验收语义；
2. “必须经过审议”“完成后必须关单”等规则在提示词中很强硬，在执行层却可能被漏掉；
3. 看板能够显示大量过程信息，但显示的状态不一定等于任务的真实语义状态；
4. 第一版 JSON/脚本架构暴露可靠性问题后，项目开始建设 PostgreSQL + Redis Streams + Outbox 的第二套架构，但新旧两套尚未完成收敛。

对我们的意义是：**应学习 edict 的分权、审议、权限边和审计意识，但不能复制其固定官僚流水线和 prompt 驱动的流程控制。我们的主线应是“可选择的 IPD 流程模板 + 可编译流程 IR + AgentCard 匹配 + 运行时强制质量门”。**

## 2. edict 实际上做了什么

edict 将任务组织为：

```text
用户（皇上）
  → 太子：区分闲聊与正式任务
  → 中书省：分析、拆解、起草方案
  → 门下省：审议，准奏或封驳
  → 尚书省：选择并调度执行部门
  → 六部：专业执行
  → 汇总并回奏用户
```

其工程实现可分为两代：

| 层次 | 第一代/默认主链路 | 第二代/重构链路 |
|---|---|---|
| Agent 运行 | OpenClaw workspace + `SOUL.md` | 仍以 OpenClaw CLI 为执行后端 |
| 流程控制 | Agent 按提示调用 `kanban_update.py` | FastAPI 服务、集中状态迁移、Worker |
| 状态存储 | `tasks_source.json` 等 JSON 文件 | PostgreSQL |
| 调度 | 轮询、脚本、子进程和停滞扫描 | Redis Streams、Orchestrator、Dispatcher |
| 一致性 | 文件锁、原子写和软约束 | 数据库事务、行锁、Transactional Outbox |
| 展示 | React 看板与 Python 单体服务 | 独立前后端与 WebSocket |

第二代方向明显更合理，但仓库默认安装、根目录演示镜像和大量测试仍围绕第一代；两代代码、状态定义和部署方式同时存在，说明项目正处于架构迁移而非稳定收敛状态。[源码基线](https://github.com/cft0808/edict/tree/14a207557719c046af0f993a7bff1cc5a5015b33)

## 3. edict 已经成功验证的设计价值

### 3.1 用职责分离替代自由聊天

edict 把规划、审议和执行调度分给不同角色，避免一个 Agent 同时提出方案、批准方案并宣布完成。这个方向与 IPD 中跨功能团队、阶段评审和决策评审点一致，也比无约束的群聊式 Multi-Agent 更容易追责和定位故障。

### 3.2 把“反对者”设为正式角色

门下省不是可选的建议者，而是专职审议角色；它从可行性、完整性、风险和资源四个维度评审方案，可以封驳并要求重拟。[门下省角色定义](https://github.com/cft0808/edict/blob/14a207557719c046af0f993a7bff1cc5a5015b33/agents/menxia/SOUL.md)

这比让执行 Agent 自检更好。对我们而言，应进一步将其从“审议人格”升级为**有固定准出标准、证据要求和路由权限的 Gate**。

### 3.3 状态机、审计轨迹和人工干预是必要基础设施

edict 将任务状态、流转记录、当前进展、停滞重试、升级、回滚、取消和恢复集中展示。即使当前实现仍有问题，它至少正确识别出：长程任务不能只保存对话，必须有独立任务账本和控制面。

### 3.4 权限拓扑应显式定义

项目为角色规定可调用的下游 Agent，试图避免任意互调。这个思路值得吸收：流程图不仅描述“应该如何协作”，也应编译成运行时可验证的通信边、工具权限和数据访问范围。

### 3.5 自动恢复不能只靠“重新问一次”

项目加入停滞检测、有限重试、升级和快照回滚，说明作者已经把多智能体执行视为需要故障治理的长运行系统，而不只是一次模型调用。这是正确方向，但恢复依据和状态语义仍需加强。

## 4. 为什么它尚未成为成功的长程多智能体范式

### 4.1 固定组织隐喻被直接等同于通用任务流程

正式任务基本都要经过“太子—中书—门下—尚书—六部”。这套线性骨架容易理解，却把**组织角色、任务类型和流程拓扑**绑定在了一起。

问题在于：

- 简单、低风险、可逆任务也承担规划和审议的固定延迟及 Token 成本；
- 技术预研、缺陷修复、版本演进、定制交付等任务需要的阶段和质量门不同；
- 软件研发常需要需求、架构、开发、测试并行迭代，而非所有工作都通过同一行政链串行推进；
- “六部”是静态领域映射，不是根据任务节点所需能力从 AgentCard 池动态组队。

外部实践文章也承认固定层级会限制协作模式、简单任务可能过于正式，并尝试合并角色以减少跳数；这恰好说明单一流程与任务差异之间存在内在矛盾。[相关实践分析](https://www.cnblogs.com/mingtingspring/p/19799198/ji-yuopenclaw-de-zhi-du-huaai-xie-zuo-san-sheng-li)

**根因**：项目从历史组织形式出发设计流程，而不是先从任务类型、风险、依赖和验收成本推导流程。

### 4.2 强约束写在 prompt 中，控制权仍在 LLM 手里

中书省的 `SOUL.md` 反复强调“门下准奏后必须调用尚书省”，甚至明确写出“这一步是最常被遗漏的”和“防卡住检查清单”。[中书省角色定义](https://github.com/cft0808/edict/blob/14a207557719c046af0f993a7bff1cc5a5015b33/agents/zhongshu/SOUL.md)

这是一条很重要的反向证据：如果流程转换真正由状态机和调度器原子执行，就不需要靠大量醒目文字提醒 Agent 不要漏掉下一步。当前主链路中，Agent 需要自行连续完成：

1. 更新状态；
2. 写入流转日志；
3. 调用下游 Agent；
4. 上报 progress；
5. 最终执行 done。

任何一步遗漏都可能产生“消息已经发出、业务已经完成、账本却仍未收口”的分裂状态。2026 年 8 月的 [Issue #334](https://github.com/cft0808/edict/issues/334) 正好记录了这一故障：Agent 已向用户回奏，旧任务却未原子进入 `Done`，十分钟后又被停滞巡检重新派发。

**根因**：Agent 同时承担业务推理和流程事务提交；自然语言服从性被误当成工作流原子性。

### 4.3 “门下省”是前置方案评审，不是完整质量闭环

门下省评的是执行方案，结论主要是“准奏/封驳”，而最终产物并不必然经过独立验收。尚书省可以自行调用六部并直接 `done`，是否调用刑部测试取决于其判断。[尚书省角色定义](https://github.com/cft0808/edict/blob/14a207557719c046af0f993a7bff1cc5a5015b33/agents/shangshu/SOUL.md)

此外，门下省规则规定“最多 3 轮，第 3 轮强制准奏”。这能够防止无限循环，却把“超过重试次数”错误地映射为“通过”：一个仍不合格的方案可能因次数耗尽而被批准。

一个可用的质量门至少还需要：

- 启动前固化的准出标准，而不是评审时临场生成；
- 与标准逐条对应的证据和产物定位；
- `PASS / FAIL / INCONCLUSIVE / BLOCKED`，而非只有二元判断；
- 失败后的明确路由：局部修改、退回前阶段、换方案、人工裁决或终止；
- 最终产物的独立验收与端到端验证。

**根因**：项目实现了“角色上的制衡”，但尚未实现“契约和证据上的制衡”。

### 4.4 任务状态不能充分表达并行执行

尚书省可以把工作派给多个部门，但主链路仍围绕一个任务状态推进。多个执行分支可能分别把同一父任务写为 `Doing`、`Blocked` 或 `Done`，难以严谨表达：

- 每个子任务自己的输入、状态、产物和重试次数；
- 并行分支的 `all / any / quorum` 汇聚条件；
- 部分成功、部分失败和可接受降级；
- 一个分支取消后对其他分支的影响；
- 汇聚后的独立验收。

后续代码增加了 delegate、父子任务和审核字段，说明作者已经意识到这一缺口，但其仍叠加在第一代 JSON 任务模型之上，尚未形成统一的 DAG/事件语义。

**根因**：将“行政阶段状态”同时当成“执行进度状态”，流程阶段、工作项和 Agent 会话没有彻底分层。

### 4.5 看得见不等于控得住

edict 的十个看板面板、思考过程展示、官员统计、天下要闻和上朝动画极具传播效果；但核心遥测有相当部分来自 Agent 主动执行 `progress`，或从 OpenClaw session JSONL 和会话年龄推断状态。停滞调度主要根据一段时间内是否有“进展”判断重试、升级和回滚，而非验证关键产物是否真实推进。

这会产生三个问题：

- Agent 上报了一句话，不等于完成了可验证工作；
- Agent 做完工作但漏报状态，会被系统误判为停滞；
- 展示模型的内部文字不能替代产物、测试结果和外部副作用的真实证据。

[Issue #56](https://github.com/cft0808/edict/issues/56) 曾出现 Agent 写入 workspace 数据、Dashboard 读取仓库数据的路径分裂，导致看板长期显示旧状态，并可能触发错误的停滞重试和升级；[Issue #334](https://github.com/cft0808/edict/issues/334) 又显示“回奏完成”和 `Done` 状态可以分离。

**根因**：项目较早优化了控制面的可视化，却没有先建立唯一事实源和由运行时采集的语义进度。

### 4.6 第一代可靠性基础不足，补丁增加了部署耦合

第一代以共享 JSON、文件锁、轮询脚本、符号链接和本地 OpenClaw 目录为核心。Issue #56 修复后，安装脚本把每个 Agent workspace 的 `data`、`scripts` 链接到仓库目录，解决了特定部署中的数据分裂，却也加深了对目录布局、操作系统能力和 OpenClaw 配置格式的依赖。

安装脚本还需要设置全局 session 可见性、同步模型认证文件并维护 11 个 workspace。OpenClaw 版本变化后已有用户报告只有太子可用、其他部门不可用，[Issue #246](https://github.com/cft0808/edict/issues/246) 体现了这种底层平台耦合风险。

**根因**：多智能体流程、通信运行时、数据存储和具体 OpenClaw 安装形态没有通过适配器边界解耦。

### 4.7 第二代架构方向正确，但迁移尚未闭环

第二代已经加入许多正确机制：

- PostgreSQL 集中任务状态；
- 状态转换服务和数据库行锁；
- Redis Streams 事件总线；
- Transactional Outbox；
- Orchestrator、Dispatcher、重试与 DLQ；
- 审计事件和 WebSocket。

但是，仓库中的 [`edict/docker-compose.yml`](https://github.com/cft0808/edict/blob/14a207557719c046af0f993a7bff1cc5a5015b33/edict/docker-compose.yml) 只启动 backend、orchestrator 和 dispatcher，没有启动已经实现的 [`outbox_relay`](https://github.com/cft0808/edict/blob/14a207557719c046af0f993a7bff1cc5a5015b33/edict/backend/app/workers/outbox_relay.py)。这意味着服务写入 outbox 后，默认 Compose 链路缺少把事件投递到 Redis Streams 的常驻进程。

CI 对第二代只做语法检查、数据库迁移和 FastAPI 导入，没有覆盖 TaskService—Outbox—Orchestrator—Dispatcher 的端到端测试；仓库现有测试主要针对第一代 Dashboard、JSON 看板、文件锁和状态映射。[CI 配置](https://github.com/cft0808/edict/blob/14a207557719c046af0f993a7bff1cc5a5015b33/.github/workflows/ci.yml)

**根因**：在第一代问题尚未完全收口时启动大规模重构，形成“双架构共存”，工程资源被兼容、迁移和新增功能同时消耗。

### 4.8 演示成功与真实执行成功被混在了一起

根目录一键 Docker 演示运行的是预置模拟数据和 `DEMO_MODE=true` 的 Dashboard，并不包含一次真实 OpenClaw 多 Agent 长程执行。[根目录 Compose](https://github.com/cft0808/edict/blob/14a207557719c046af0f993a7bff1cc5a5015b33/docker-compose.yml)

因此，用户可以快速看到漂亮看板，但不能据此验证：

- Agent 是否在真实失败下正确恢复；
- 审议是否提升最终质量；
- 多 Agent 是否优于单 Agent；
- 增加的 Token、延迟和运维成本是否值得；
- 不同任务是否需要同一套三省六部流程。

项目存在 Dashboard 性能测量计划，但没有提交对应的实际基线/对比结果；也未提供面向任务质量的单 Agent、自由协作、固定流程和裁剪流程对照实验。Roadmap 中人工审批、Agent 绩效、知识沉淀仍未完成。[Roadmap](https://github.com/cft0808/edict/blob/14a207557719c046af0f993a7bff1cc5a5015b33/ROADMAP.md)

**根因**：产品展示指标先于研究验证指标，缺少可证伪的成功标准。

### 4.9 项目范围扩张快于核心闭环成熟

仓库在约两个多月内快速加入十面板、模型热切换、新闻、早朝、技能管理、会话监控、朝堂议政和第二代事件架构。提交历史高度集中于主要维护者，当前基线没有正式 tag/release；最新主分支提交停在 2026-05-06，而 8 月仍有新的流程状态问题被提交。

这不等于项目已经被放弃，但说明维护能力、功能范围和架构复杂度之间出现失衡。第三方研究也将其概括为“理念强于运营成熟度”，并认为长期可行性依赖稳定版本和维护者精力。[第三方评估](https://rywalker.com/research/edict)

**根因**：先证明“概念吸引人”，尚未完成从概念原型到可靠核心、再到扩展功能的阶段收敛。

## 5. 更深一层：它为什么会自然走到这些问题

### 5.1 历史制度解决的主要是权力问题，Agent 系统还要解决计算问题

三省六部强调授权、制衡和问责，但 LLM Agent 还存在上下文丢失、非确定输出、幻觉、Token 成本、工具副作用、并发竞争、幂等和恢复等问题。历史类比可以启发职责分离，不能自动给出分布式系统的正确实现。

### 5.2 角色分离不自动带来认知独立

如果规划者和评审者使用相同模型、相似上下文和相同知识源，两者可能共享盲点。仅换一个角色名不能保证真正的独立评审；关键 Gate 需要不同证据源、规则检查器、不同模型配置或人工裁决。

### 5.3 增加步骤不自动增加质量

每增加一次 Agent 交接，都会增加一次信息压缩、误解、延迟和成本。只有当该节点能发现足够多的缺陷、降低足够大的返工代价时，它才有净收益。固定全流程无法根据风险动态判断这笔账。

### 5.4 自动重试不能修复语义错误

按超时重试适合瞬时网络故障，不适合错误方案、缺少依赖和验收标准不清。对语义失败重复调用相同 Agent，往往只是提高成本并产生更多相似错误；需要换路线、换角色、补充信息或升级人工。

## 6. 对我们的直接经验与教训

### 6.1 应继承的原则

| edict 的有效思想 | 在我们的 IPD 架构中如何落地 |
|---|---|
| 规划、审议、执行分离 | 将角色职责写入 AgentCard，并由流程 IR 指定谁能生产、谁能批准 |
| 门下省否决权 | 独立 Gate 节点，依据预置标准和证据决定路由 |
| 显式流转和审计 | append-only 事件 + 任务快照 + `trace_id` + 产物清单 |
| 权限矩阵 | 从流程图编译 Agent 通信边、工具权限、数据范围和外部操作审批 |
| 停滞、重试、升级、回滚 | 区分技术失败、质量失败、阻塞和部分失败，分别配置策略 |
| 专业部门 | 从 AgentCard 池选择模型、Skill、工具和知识库合适的数字员工 |
| 看板控制面 | 展示节点、产物、证据、成本、风险和人工决策，而非展示“思考文本” |

### 6.2 必须避免的设计

1. **不要固定一条流程覆盖所有任务。** 任务类型和风险先决定流程模板，再由模板决定角色与拓扑。
2. **不要让 Agent 直接决定并写入任意状态。** Agent 只能提交结构化结果或状态迁移提议，运行时校验后提交。
3. **不要把提示词中的“必须”当成机制。** 必经节点、权限、重试上限、汇聚条件和终态收口必须由代码保证。
4. **不要用重试耗尽代替质量通过。** 超过重试次数应升级、换路线、暂停或终止，绝不能“第 3 次强制 PASS”。
5. **不要以自报 progress 作为真实进度。** 进度应由产物登记、测试执行、工具回执和状态事务自动产生。
6. **不要展示或存储无必要的模型思考文本。** 保存决策摘要、依据、证据和结果即可。
7. **不要同时维护多份状态真相。** 数据库是唯一事实源，会话和看板是派生视图，不能反向猜测业务状态。
8. **不要在核心可靠性未验证时扩展仪式性功能。** 首版只保留执行、质量门、恢复、审计和最小看板。

## 7. 建议的 IPD 风格实现方式

### 7.1 三层解耦

```text
任务分类层
  根据任务类型、复杂度、风险、可逆性、验收成本选择流程模板

流程控制层
  Process IR 定义阶段、节点、I/O、Gate、路由、并行汇聚、预算和恢复策略

Agent 执行层
  根据 AgentCard 为节点选择实例；Agent 只在节点授权范围内自治执行
```

这里的关键不是“组织先验约束下的自治 Multi-Agent”，而是：**显式流程作为长程任务骨架，专业 Agent 在节点契约和权限边界内发挥自治。**

### 7.2 节点 IR 的最小字段

```yaml
node:
  id: developer_test
  objective: 验证实现满足需求和接口契约
  entry_conditions: [build_artifact_exists, test_plan_approved]
  input_schema: DeveloperTestInput
  required_capabilities: [test_design, repo_execute]
  permissions: [repo_read, test_execute]
  budget: {tokens: 12000, timeout_s: 900, retry: 1}
  output_schema: TestEvidencePackage
  exit_criteria:
    - required_tests_pass == true
    - critical_defects == 0
  routes:
    pass: software_build
    fail: implementation
    inconclusive: human_triage
    blocked: project_manager
```

流程运行时负责检查 entry/exit、提交状态和执行路由；Agent 只负责产生 `TestEvidencePackage`，无权自行宣布整个任务完成。

### 7.3 Gate 合同

每个决策评审点至少包含：

```yaml
gate_decision:
  decision: PASS | FAIL | INCONCLUSIVE | BLOCKED
  criteria_results:
    - criterion_id: C-01
      result: PASS
      evidence_uri: artifact://run-123/test-report.json
  unresolved_risks: []
  required_rework: []
  next_route: software_build
  reviewer: quality_reviewer_v2
```

关键 Gate 可组合三类裁判：确定性规则、独立评审 Agent、按风险触发的人工审批。这样才是真正的“门下省”，而不是换了人格的第二次模型调用。

### 7.4 一等公民的 DAG 与汇聚语义

并行任务必须各自拥有 `work_item_id`、状态、产物、预算和失败策略。汇聚节点明确：

- `ALL`：所有必需分支通过；
- `ANY`：任一可用方案通过；
- `QUORUM`：达到指定数量或权重；
- `CUSTOM`：由确定性表达式判断。

父任务不能被任一子 Agent 直接写成 `Done`；只有汇聚条件和最终 Gate 同时满足，运行时才能原子收口。

### 7.5 单一事实源与事件日志

推荐：

```text
PostgreSQL：任务、节点实例、Gate 决策、预算、产物索引的唯一事实源
Event Log：不可变事件，用于审计、恢复和派生视图
Object Store：原始产物与证据
Queue/Event Bus：传递可重放的执行命令
Dashboard：只读派生视图 + 经授权的控制命令
```

状态更新采用幂等键、乐观/悲观并发控制和 Transactional Outbox；“发送最终结果 + 任务 Done + 停止调度”必须是同一收口事务或具备可恢复的一致性协议。

### 7.6 AgentCard 应替代固定“六部”

AgentCard 至少描述：职责与非职责、输入输出 schema、模型档位、Skill/工具、知识库、权限、预算、适用节点、历史成功率、返工率和缺陷逃逸率。流程只声明所需能力，运行时从合格实例中选择，不把某类任务永久绑定到一个古代部门名称。

## 8. 首版软件开发 Demo 的验证建议

首版不要先做完整 IPD，也不要先做大看板。选择一个有明确仓库、自动测试和可检查产物的软件变更任务，比较四组：

| 组别 | 编排方式 | 目的 |
|---|---|---|
| A | 单 Agent | 建立成本与质量基线 |
| B | 自由协作 Multi-Agent | 验证无流程协作的问题 |
| C | 固定线性流程 | 验证结构化流程的收益和流程税 |
| D | 按风险裁剪的 IPD 流程 | 验证我们的核心假设 |

建议至少记录：

- 端到端任务成功率；
- 需求覆盖率和测试通过率；
- Gate 缺陷发现率、误报率、缺陷逃逸率；
- 返工次数与返工距离；
- 非法状态迁移和重复副作用次数；
- 故障恢复成功率；
- Token、调用次数、墙钟时间；
- 人工介入次数；
- 相对单 Agent 的质量增益/成本增量。

首版只需实现：流程选择、3—5 个节点、一个独立质量门、结构化交接包、任务账本、有限重试/升级、最终原子收口和最小追踪页面。只有这些指标证明结构化流程具有净收益后，再增加动态资源分配、资产库自演进和更复杂 IPD 模板。

## 9. 最终判断

edict 的最大贡献，是把一个重要问题讲清楚了：**Multi-Agent 的核心不只是多几个会话，而是职责、权力、交付和反馈如何被组织。** 它也证明“规划—审议—调度—专业执行”的制度隐喻具有很强的产品表达力。

它尚未成功的关键，则是没有彻底跨过这条边界：

```text
制度写进角色提示词
          ↓
制度编译为可验证、可恢复、可度量的运行时协议
```

我们的机会并非再造一套更复杂的“数字官僚体系”，而是将 edict 的制度直觉工程化：**任务选择流程，流程定义节点契约和质量门，AgentCard 提供专业执行者，运行时掌握状态与权限，证据而非自述决定准出。** 这也与极简 Agent 设计相容——Agent 本身保持轻量，复杂性集中在可复用、可检索、可编译的 IPD 流程资产与确定性控制面。
